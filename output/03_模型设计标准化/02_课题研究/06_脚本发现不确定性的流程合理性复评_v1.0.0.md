# 脚本发现不确定性的流程合理性复评

> 本文重新评估“脚本的责任是发现不够确定，而不是发现正确答案”这一流程假设是否合理。  
> 结论：原说法需要收窄。脚本不能发现语义不确定本身，但可以在预设模板、标准、候选集合和证据规则下，发现“形式化不可判定”。

---

## 1. 先承认用户质疑成立的部分

用户质疑：

> 脚本发现不了确定，所以也发现不了不够确定。

这句话在“没有预设规则、没有标准库、没有候选集合、没有证据模型”的情况下是对的。

如果脚本只看到：

```text
字段描述：商品
参考字段：id
```

且没有任何术语库、模板规则、参考表、业务主键、依赖图、历史样例，那么脚本既不能判断它是 `product_id`，也不能判断它“应该不确定”。它只是看到两个字符串。

所以，不能说脚本天然能发现不确定。更准确的说法是：

```text
脚本只能在一套已定义的判定框架内，发现证据不足、候选冲突、模板异常或规则不满足。
```

---

## 2. 重新定义“确定”和“不确定”

这里必须分两种确定性。

### 2.1 语义确定性

语义确定性是：

```text
这个字段在业务上到底是什么意思。
```

例如：

```text
商品 到底是 product、sku、msku、asin 还是 listing？
```

脚本没有语义理解，不能判断这个。

### 2.2 形式化确定性

形式化确定性是：

```text
在既定规则和证据下，是否存在唯一可执行结论。
```

例如：

```text
字段描述命中 1 个标准词根，参考字段也命中同一词根，字段名格式合法。
```

或：

```text
字段描述命中 5 个候选，参考字段是 id，参考表为空，业务主键为空，因此没有唯一可执行结论。
```

脚本能判断的是后者。

所以流程应改成：

```text
脚本发现形式化不可判定，AI 判断语义，用户确认标准。
```

而不是：

```text
脚本发现语义不确定。
```

---

## 3. 可以反驳用户的例子

下面这些例子可以反驳“脚本完全发现不了不确定”。但注意，反驳的是“形式化不确定”，不是“语义不确定”。

### 3.1 例子一：候选集合大于 1，且没有消歧证据

输入：

```text
字段描述：商品
参考字段：id
参考库表：空
业务主键：空
```

如果系统有一个预设术语表：

```json
{
  "商品": ["product_id", "sku_id", "msku_id", "asin", "listing_id"]
}
```

脚本可以计算：

```text
候选数 = 5
消歧证据 = 0
唯一结论 = 否
```

这时脚本不是理解“商品”，而是根据候选集合和证据数量发现：

```text
这是不可判定任务。
```

这就是脚本能发现“不够确定”的一个例子。

### 3.2 例子二：参考字段过于泛化

输入：

```text
字段描述：商品ID
参考字段：id
参考库表：cbebg.xxx_product
```

脚本可以有一张弱字段名表：

```json
["id", "name", "code", "type", "status", "date"]
```

命中 `id` 后，脚本可以判断：

```text
reference_field=id 只说明它是某种 ID，不提供实体粒度。
```

它仍然不知道答案，但它能知道：

```text
参考字段证据弱，不能直接继承为字段名。
```

这也是形式化不确定。

### 3.3 例子三：多个证据源冲突

输入：

```text
字段描述：商品ID
参考字段：product_id
参考库表：dws_fin_shop_msku_subject
业务主键：shop_id + msku_id + biz_date
```

脚本可以拆 token：

```text
字段描述候选：商品 -> product/sku/msku/asin
参考字段 token：product
参考表 token：msku
业务主键 token：msku
```

脚本可以发现：

```text
product 与 msku 证据冲突。
```

它不是判断谁对，而是发现“不能自动拍板”。

### 3.4 例子四：确定性规则失败

输入：

```text
字段名：Product ID
```

规则：

```text
字段名必须小写英文和下划线。
```

脚本可以确定：

```text
当前字段名不合规。
```

如果标准库和候选都无法给唯一修复结果，脚本可以进一步判断：

```text
需要 AI 或人工确认推荐名。
```

### 3.5 例子五：模板结构异常

输入：

```text
实体设计 sheet 缺少“字段描述”列。
```

脚本可以确定：

```text
缺少核心语义输入，无法执行字段标准化。
```

这不是语义判断，但它是明确的不确定来源：输入不完整。

---

## 4. 反驳成立的前提

上面的反驳必须依赖几个前提。如果这些前提不存在，用户质疑就完全成立。

### 4.1 必须有候选集合

脚本要发现“不能唯一判断”，前提是它知道可能有哪些候选。

例如：

```json
{
  "商品": ["product", "sku", "msku", "asin", "listing"]
}
```

没有候选集合，脚本无法知道“商品”是宽泛词。

### 4.2 必须有弱证据规则

脚本要知道 `id` 很弱，需要一张弱字段名表：

```json
["id", "name", "code", "type", "status", "date"]
```

没有这张表，脚本不会知道 `id` 不足以消歧。

### 4.3 必须有 token 抽取规则

脚本要发现 `msku_id` 和 `product_id` 冲突，必须能拆字段名：

```text
msku_id -> msku + id
product_id -> product + id
```

没有 token 规则，脚本只能看到字符串。

### 4.4 必须有判定策略

例如：

```text
如果候选数 > 1 且没有强证据，则进入 AI 判断。
如果证据源冲突，则进入 AI 判断或人工确认。
如果参考字段是弱字段名，则不得自动继承。
```

没有判定策略，脚本无法决定什么算“不够确定”。

---

## 5. 流程方案是否仍合理

复评后，我认为流程仍然合理，但需要改名和改定位。

### 5.1 不合理的说法

不应再说：

```text
脚本发现可疑语义关系。
脚本发现语义不确定。
```

这会误导人，以为脚本有语义理解。

### 5.2 合理的说法

应该说：

```text
脚本执行确定性校验与证据覆盖度检查。
当脚本无法在规则内得到唯一可执行结论时，生成 AI 语义判断任务。
```

也就是：

```text
脚本不是发现“不确定”，而是发现“规则系统无法收敛到唯一结果”。
```

这个说法更严谨。

---

## 6. 修订后的流程架构

旧流程：

```text
脚本发现不确定 -> AI 判断 -> 用户确认
```

修订后：

```text
脚本做四类检查：
  1. 模板完整性检查
  2. 格式规则检查
  3. 候选生成与候选数量检查
  4. 证据覆盖度与证据冲突检查

如果唯一候选且证据充分：
  进入自动建议或自动回写

如果多候选、弱证据、证据冲突、输入缺失：
  生成 AI 判断任务

AI 判断后仍低置信度：
  进入人工确认
```

### 6.1 自动处理条件

只有满足类似条件时，才允许自动处理：

```text
候选唯一
命中标准库
无冲突证据
字段名格式合法
参考字段或样例支持
```

例如：

```text
字段描述：创建时间
参考字段：create_time
标准库：创建时间 -> create_time
```

脚本可以给高确定性建议。

### 6.2 必须进入 AI 的条件

```text
候选多个
候选为空
参考字段过弱
证据冲突
描述为宽泛词
标准库无覆盖
模板输入不完整
```

例如：

```text
字段描述：商品
参考字段：id
```

必须进入 AI 或人工确认，不能自动生成。

## 7. 对“商品 + id”的重新评估

输入：

```text
字段描述：商品
参考字段：id
```

脚本能做：

```text
1. 命中“商品”为宽泛词。
2. 命中 `id` 为弱参考字段。
3. 候选集合可能有 product/sku/msku/asin/listing。
4. 没有参考表、业务主键、依赖图证据时，无法消歧。
5. 生成“语义消歧任务”或“人工确认项”。
```

脚本不能做：

```text
商品 -> MSKU
```

AI 合理输出：

```text
证据不足，无法判断商品具体粒度。不建议自动生成字段名。请补充参考库表、业务主键或将字段描述明确为产品/MSKU/ASIN等。
```

如果 AI 直接输出 `msku_id`，那是流程失败。

---

## 8. 这个复评对整体设计的影响

### 8.1 标准库索引必须包含候选和歧义

标准库不能只是：

```text
中文名称 -> 标准词根
```

还需要：

```text
宽泛术语 -> 可能候选
弱字段名 -> 不可直接继承
语义关系 -> 生效上下文
```

否则脚本没有能力判断候选数和证据覆盖度。

### 8.2 脚本输出应从“可疑关系”改名

建议改成：

```text
semantic_resolution_tasks.jsonl
```

不要叫：

```text
semantic_relation_tasks.jsonl
```

因为很多任务不是“关系判断”，而是“语义消歧”。

### 8.3 评审项要区分原因

评审原因应分成：

| 原因 | 含义 |
|---|---|
| `missing_context` | 上下文缺失 |
| `weak_reference` | 参考字段过弱，如 id/name/type |
| `multiple_candidates` | 多候选无法收敛 |
| `evidence_conflict` | 证据源冲突 |
| `standard_gap` | 标准库缺失 |
| `template_error` | 模板结构异常 |

这样用户能知道为什么 AI 不自动填。

---

## 9. 最终结论

用户的批评迫使流程更严谨：

```text
脚本不能发现语义确定或语义不确定。
脚本只能发现规则系统是否能收敛。
```

所以这句话应废弃：

```text
脚本的责任是发现不够确定。
```

改成：

```text
脚本的责任是执行可计算规则，生成候选，检查证据是否足以收敛到唯一结果；不能收敛时，交给 AI 做语义判断，或交给人工确认。
```

这能反驳“脚本完全发现不了不确定”的地方在于：只要有候选集合、弱证据规则、token 抽取和判定策略，脚本就能发现形式化不可判定。

但这也承认用户的核心担心：脚本发现的不是业务语义不确定，而是规则和证据层面的不可判定。这个限定必须写进后续 Skill 设计。
