# 模型设计标准化需求理解

> 本文记录对“基于标准库与已有完结模型设计文档，自动生成标准化模型设计 Excel”的需求理解。  
> 输入样例：`input/标准库.xlsx`、`input/模型设计 - 利润核算（快报）.xlsx`。

---

## 1. 本轮确认

我能读到两个 Excel 的有效内容，但需要注意读取方式：

- `input/标准库.xlsx` 可读到 2 个 sheet：
  - `规则标准库`：当前识别到字段命名规则，例如字段名统一使用字段描述标准翻译、小写英文、下划线分割；枚举字段增加 `cd` 后缀。
  - `映射标准库`：当前识别到 130 行标准词根映射，字段包括序号、业务域、中文名称、标准词根、释义、适用场景、示例。
- `input/模型设计 - 利润核算（快报）.xlsx` 可读到 34 个 sheet，属于已完结样例文档，包含：
  - 标准沉淀流程、评审清单、内容概览。
  - 模型设计目录、模型依赖说明、模型实体设计模板、OneData 指标录入。
  - 多个已完成模型实体 sheet，例如领星结算报告映射结果、结算成本汇总、管理快报-金额、管理快报-数量等。
  - 附录类标准信息，例如数据域、数据资产分层、表命名规范、表命名规则、维度实体、业务过程。

技术观察：普通 Excel 读取库对这两个文件的维度识别不完整，容易误判为每个 sheet 只有 `A1`。但直接解析 xlsx 内部 worksheet XML 可以稳定读取真实行列。因此后续自动化流程不能只依赖默认 `max_row/max_column`，需要使用更稳的工作簿解析策略。

---

## 2. 我理解的最终目标

目标不是单纯“翻译字段名”，而是建立一个可复用的模型设计标准化流程：

输入一份模型设计 Excel，以及一份标准库 Excel，必要时再结合 `data-assets` 中的代码、SQL、表结构或已有模型实现，自动产出一份已经套用数据标准的模型设计文档。

最终产物应该是一份标准化后的模型设计 Excel，至少完成以下内容：

- 补全或修正模型表名。
- 根据字段描述、参考字段、参考库表、已有代码和标准库，生成规范字段名。
- 保持原设计文档的结构、sheet、字段顺序、业务说明、参考字段、参考库表等信息。
- 标明字段命名依据、异常点、无法确定项和需要人工确认的项。
- 尽量让文档达到可评审、可开发、可沉淀回标准库的状态。

---

## 3. 输入材料的角色分工

### 3.1 标准库 Excel

标准库是命名与规则的最高依据，建议拆成两类信息使用：

- 规则标准库：规定命名方法，例如字段名格式、枚举字段后缀、大小写、下划线、实体名与属性名组合方式。
- 映射标准库：提供中文业务词到标准词根的映射，例如“日期”对应 `dt`，“创建时间”对应 `create_time`。

后续字段名生成时，应优先从这里取标准词根。标准库没有覆盖时，才进入参考字段、参考库表、代码语义和模型推理。

### 3.2 完结模型设计文档

`模型设计 - 利润核算（快报）.xlsx` 是样例和模板，不只是普通输入。

它可以提供：

- 标准模型设计文档的 sheet 结构。
- 模型目录和依赖数据流的写法。
- 实体设计 sheet 的字段列结构：字段分类、二级分类、字段序号、字段名、字段数据类型、字段描述、参考字段、参考库表、主键标记、业务主键标记、备注。
- 已完结模型中的命名经验，尤其是同类财务域、利润核算主题下字段如何命名。
- 表命名规范、数据域、资产分层、更新方式等附录标准。

### 3.3 待标准化的模型设计文档

后续用户可能给出两种形态：

- 完整但待评审的设计文档：已有字段名，需要检查、修正、标注问题。
- 字段名空着的设计文档：只有字段描述、参考字段、参考库表、字段类型、业务分类等，需要自动生成字段名。

对字段名空着的文档，系统应把“字段描述 + 参考字段 + 参考库表 + 上下文模型主题”作为主要语义输入。

### 3.4 data-assets 代码

`data-assets` 应作为实现证据，而不是覆盖标准库的标准。

建议用途：

- 查找参考库表的真实字段名、字段类型、注释、DDL。
- 查找已有 SQL 中字段的加工逻辑、别名、来源字段和口径。
- 识别同一业务语义在已有代码中的稳定命名。
- 反查模型依赖链，确认表名、分层、更新方式和主题归属。

如果代码命名与标准库冲突，应优先遵循标准库，并在输出中标记“代码现状与标准不一致”。

## 4. 建议流程

### 第一步：输入解析

读取标准库、待处理模型设计 Excel、已完结样例文档和可用代码资产，形成结构化中间数据：

- 标准词根表。
- 命名规则表。
- 表命名规范表。
- 模型目录表。
- 字段设计明细表。
- 依赖表与参考字段清单。
- 代码证据索引。

### 第二步：标准匹配

对每一行字段设计做标准匹配：

1. 用字段描述匹配标准库中文名称。
2. 用参考字段匹配已有字段命名。
3. 用参考库表和代码资产确认字段语义。
4. 用模型主题、字段分类、二级分类补充实体上下文。
5. 用规则标准库判断是否需要枚举后缀、日期后缀、金额/数量/率等指标词根。

### 第三步：字段名生成

根据匹配结果生成字段名，建议每个字段保留以下判定信息：

- 推荐字段名。
- 命名依据：标准库、参考字段、参考表、代码证据、人工规则或推理。
- 置信度：高、中、低。
- 冲突说明：例如标准库与参考字段不一致、多个候选词根冲突。
- 待确认问题：需要业务或数据开发确认的点。

### 第四步：表名生成或校验

表名需要结合文档附录中的表命名规范、模型目录、数据域、分层和更新方式判断。

建议校验项：

- 是否符合分层前缀：如 `ods`、`dwd`、`dws`、`dmt`、`ref`。
- 是否符合业务域或 schema 约定。
- 是否包含合理的实体或业务过程。
- 是否包含更新方式后缀，如 `ilu`、`flu`、`ich`。
- 是否包含周期粒度，如 `dd`、`mm`。
- 是否与模型目录和实体 sheet 标题一致。

### 第五步：输出标准模型设计 Excel

输出应尽量沿用输入模型设计文档的结构，只补全或修正必要区域：

- 模型设计目录：补齐或校验实体表名、分层、状态。
- 模型依赖说明：校验依赖链是否闭合。
- 模型实体设计 sheet：补齐字段名、保留字段描述、参考字段、参考库表。
- 评审辅助列：可新增或隐藏，用于记录命名依据、置信度、冲突和待确认项。
- 评审清单：输出本轮自动检查结果。

## 5. 建议 Skill 设计

建议先做“一个主 Skill + 若干脚本”的结构，等流程稳定后再拆成多个 Skill。

### 5.1 主 Skill：模型设计标准化

职责：

- 接收标准库 Excel、模型设计 Excel、可选样例 Excel、可选 data-assets 路径。
- 调用解析、匹配、生成、评审、导出脚本。
- 输出标准化后的模型设计 Excel 和一份问题清单。

### 5.2 支撑脚本一：Excel 结构解析

职责：

- 稳定读取 xlsx 内部 worksheet XML。
- 识别 sheet、表头、字段明细区域、附录标准区域。
- 输出 JSON 中间文件，供后续步骤使用。

### 5.3 支撑脚本二：标准库索引构建

职责：

- 把规则标准库和映射标准库解析为可检索索引。
- 支持中文名称精确匹配、别名匹配、分词匹配和业务域过滤。
- 对标准词根重复、冲突、缺失进行标记。

### 5.4 支撑脚本三：字段命名与表命名推断

职责：

- 对字段描述、参考字段、参考库表、代码证据进行综合判断。
- 输出推荐字段名、推荐表名、置信度和原因。
- 对低置信度结果保留人工确认标记。

### 5.5 支撑脚本四：Excel 回写与评审清单生成

职责：

- 把结果写回模型设计 Excel。
- 保持原 workbook 样式和 sheet 结构。
- 生成或更新评审清单。
- 输出最终标准模型设计文档。

---

## 6. 关键判定原则

1. 标准库优先：标准库是命名与规则的最高依据。
2. 样例文档优先于自由发挥：完结模型设计文档中的稳定模式应复用。
3. 代码资产提供证据，不直接覆盖标准：代码可以证明现状，但不等于标准。
4. 不确定要显式标注：低置信度字段不应静默生成。
5. 输出要保留可审计链路：每个自动生成字段名最好能追溯到标准词根、参考字段或代码证据。
6. 先自动补全，再人工评审，再沉淀标准：流程应支持把共性问题回流到标准库。

---

## 7. 需要进一步确认的问题

1. 最终 Excel 是否允许新增辅助列，例如“命名依据”“置信度”“待确认问题”。
2. 字段名生成时，标准库缺失词根是否允许 AI 先给候选词根，还是必须留空等待标准库更新。
3. 表名是否也要求自动生成，还是先以字段名标准化为主。
4. `data-assets` 的权威边界：当代码字段名与标准库冲突时，是否统一按“标准库优先，代码现状标记异常”处理。
5. 是否需要把每次模型设计中发现的新词根、新规则自动整理成“待沉淀标准库”sheet。

---

## 8. 当前初步结论

我理解你的目标是：把模型设计从“人工查标准、人工起字段名、人工评审”升级为一个可复用的标准化生产流程。

最合理的第一版不是直接让 AI 改 Excel，而是先建立稳定的结构化管线：

`读取 Excel/代码资产 -> 构建标准索引 -> 字段与表名推断 -> 回写模型设计文档 -> 输出评审清单 -> 沉淀标准库候选项`

这样后续无论你给的是完整设计文档，还是字段名空着的设计文档，都可以按同一套流程产出可审计、可评审、可持续沉淀的标准模型设计文档。
