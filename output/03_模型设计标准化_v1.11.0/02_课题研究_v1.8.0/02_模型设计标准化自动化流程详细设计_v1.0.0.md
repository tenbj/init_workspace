# 模型设计标准化自动化流程详细设计

> 本文把“标准库 + 模型设计 Excel + 可选 data-assets 代码资产 -> 标准模型设计文档”的流程拆到可执行层。  
> 重点回答：Excel 结构解析成什么、标准库索引怎么建、字段名和表名如何推断、怎么回写和评审、哪些适合脚本做、哪些必须由 AI 判断。

---

## 1. 总体结论

这件事不能设计成“AI 直接打开 Excel 然后填字段名”。更稳的做法是把流程拆成两层：

- 脚本层：负责可重复、可校验、可定位的工作，例如解析 Excel、抽取表格、构建索引、生成候选、跑规则校验、回写单元格。
- AI 层：负责语义判断，例如中文字段描述拆解、候选字段名取舍、标准库缺失时的候选词根建议、冲突解释、评审意见归纳。

建议第一版流程如下：

```text
输入文件
  -> Excel 结构解析
  -> 标准库索引构建
  -> 模型设计抽取
  -> 可选代码资产证据索引
  -> 字段/表名候选生成
  -> AI 语义裁决
  -> 规则校验与评审清单
  -> Excel 回写
  -> 标准库待沉淀项
```

核心原则：脚本先把问题变成结构化任务，AI 只处理脚本无法可靠判断的语义问题，最后脚本再负责落回 Excel 和校验。

---

## 2. 输入与输出

### 2.1 输入

| 输入 | 必选 | 作用 |
|---|---:|---|
| 标准库 Excel | 是 | 字段命名规则、标准词根、适用场景、示例 |
| 待处理模型设计 Excel | 是 | 需要补齐或校验的目标文档 |
| 完结样例模型设计 Excel | 建议 | 提供模板结构、已完成模型命名经验、附录标准 |
| data-assets 代码资产 | 可选 | 提供 DDL、SQL、字段加工逻辑、已有命名证据 |
| 人工配置 | 可选 | 指定业务域、数据域、分层、是否允许新增辅助列等 |

当前 `input/` 中没有 `data-assets` 目录，因此第一版可以只基于 Excel 运行；后续出现代码资产时再接入证据索引。

### 2.2 输出

| 输出 | 形式 | 说明 |
|---|---|---|
| 标准化模型设计 Excel | `.xlsx` | 保留原文档结构，回填字段名、表名、评审结果 |
| 评审清单 | Excel sheet 或 Markdown/CSV | 标记阻断项、警告项、待确认项 |
| 字段决策明细 | JSON/CSV | 每个字段的推荐名、依据、置信度、冲突说明 |
| 表名决策明细 | JSON/CSV | 每张模型表的推荐表名、组件拆解、依据 |
| 标准库待沉淀项 | Excel sheet 或 CSV | 标准库缺失词根、命名规则缺口、常见冲突 |
| 运行日志 | JSON/Markdown | 输入文件、解析摘要、异常与统计 |

## 3. Excel 结构解析到底解析成什么

### 3.1 为什么不能只读单元格值

样例文件里，普通 Excel 读取库可能误判每个 sheet 只有 `A1`，但 xlsx 内部 XML 实际包含完整行列。因此解析器不能依赖默认 `max_row/max_column`，应直接读取 worksheet XML，或者使用能读取真实 worksheet 维度的工具。

解析器的目标不是“把 Excel 转成二维数组”这么简单，而是抽出后续可用的数据对象。

### 3.2 工作簿级对象：workbook_manifest

脚本输出：

```json
{
  "file_path": "input/模型设计 - 利润核算（快报）.xlsx",
  "file_hash": "sha256...",
  "sheet_count": 34,
  "sheets": [
    {
      "sheet_id": 4,
      "sheet_name": "1.1 模型设计目录",
      "visible": true,
      "non_empty_rows": 24,
      "max_col_seen": 47,
      "detected_type": "model_catalog"
    },
    {
      "sheet_id": 21,
      "sheet_name": "领星结算报告映射结果",
      "visible": true,
      "non_empty_rows": 105,
      "max_col_seen": 42,
      "detected_type": "entity_design"
    }
  ]
}
```

用途：

- 确认 workbook 是否读完整。
- 判断哪些 sheet 是目录、依赖、实体设计、附录标准、评审清单。
- 给后续回写提供 sheet 定位。

### 3.3 sheet 区域对象：sheet_regions

每个 sheet 需要识别出标题区、表头行、数据区、辅助区。

实体设计 sheet 的例子：

```json
{
  "sheet_name": "管理快报-金额",
  "detected_type": "entity_design",
  "table_name_cell": "A1",
  "version_cell": "J1",
  "header_row": 2,
  "data_start_row": 3,
  "data_end_row": 113,
  "semantic_columns": {
    "field_category": "A",
    "field_sub_category": "B",
    "field_order": "C",
    "field_name": "D",
    "data_type": "E",
    "field_desc": "F",
    "reference_field": "G",
    "reference_table": "H",
    "is_primary_key": "I",
    "is_business_key": "J",
    "remark": "K"
  }
}
```

注意：不能死写列号。比如“领星结算报告映射结果”多了“是否保留”，其列结构为：

```json
{
  "field_category": "A",
  "field_sub_category": "B",
  "field_order": "C",
  "field_name": "D",
  "data_type": "E",
  "field_desc": "F",
  "reference_field": "G",
  "reference_table": "H",
  "is_retained": "I",
  "is_primary_key": "J",
  "is_business_key": "K",
  "remark": "L"
}
```

因此解析器应通过表头文本识别语义列，而不是通过固定位置识别。

### 3.4 模型目录对象：model_catalog

来自 `1.1 模型设计目录`。

- 判断参考表是否在依赖链内。
- 判断模型粒度从明细到汇总是否合理。
- 评审“依赖是否闭环”“目录是否覆盖依赖中的模型”。

## 4. 标准库索引如何构建

标准库索引不是简单的 `中文名称 -> 标准词根` 字典。至少需要四类索引。

### 4.1 规则索引：rule_index

来自 `规则标准库`。

```json
{
  "rules": [
    {
      "rule_id": "R001",
      "target": "字段名",
      "description": "统一使用字段描述为标准翻译，使用小写英文字母，使用下划线分割，命名规则：实体名_属性/指标",
      "example": "emp_name",
      "priority": 100,
      "machine_check": "lower_snake_case"
    },
    {
      "rule_id": "R002",
      "target": "字段名",
      "description": "若为枚举字段，在字段后面增加cd后缀，命名规则：事件场景类型_cd",
      "example": "event_type_cd",
      "priority": 90,
      "machine_check": "enum_suffix_cd"
    }
  ]
}
```

脚本能做：

- 识别小写英文、下划线、非法字符。
- 识别枚举字段是否用了 `_cd`。
- 识别字段名重复、空字段名、字段名过长。

AI 需要做：

- 判断字段描述是不是枚举语义。
- 判断“类型”“状态”“阶段”“场景”等词是否真的应该加 `_cd`。

### 4.2 词根索引：term_index

来自 `映射标准库`。

```json
{
  "by_chinese_name": {
    "日期": [
      {
        "term_id": "T001",
        "business_domain": "技术通用",
        "chinese_name": "日期",
        "standard_root": "dt",
        "definition": "业务分区日期",
        "scene": "分区、业务日期",
        "example": "order_dt"
      }
    ]
  },
  "by_root": {
    "dt": ["T001"]
  },
  "by_domain": {
    "技术通用": ["T001", "T002"]
  }
}
```

脚本能做：

- 精确匹配：字段描述等于标准中文名称。
- 包含匹配：字段描述包含标准中文名称。
- 反向匹配：参考字段已有标准词根。
- 冲突检测：同一个中文名称对应多个词根，或同一个词根对应多个中文名称。

AI 需要做：

- 判断“结算时间，站点时间”应该拆成哪些业务词。
- 判断“业务日期”“统计日期”“分区日期”是否在当前模型里应使用同一个词根。
- 判断中文描述里哪个词是实体，哪个词是属性，哪个词只是修饰。

### 4.3 候选别名索引：alias_index

标准库里不一定直接写所有同义词，因此需要从样例文档和字段描述中派生别名。

```json
{
  "aliases": [
    {
      "alias": "店铺id",
      "canonical_chinese_name": "店铺维表id",
      "standard_root": "shop_id",
      "source": "sample_model",
      "confidence": "medium"
    },
    {
      "alias": "业务时间",
      "canonical_chinese_name": "业务日期",
      "standard_root": "biz_date",
      "source": "sample_model",
      "confidence": "medium"
    }
  ]
}
```

脚本能做：

- 从已完结模型设计中收集 `字段描述 -> 字段名` 对。
- 统计同一字段描述最常见字段名。
- 统计同一参考字段最常见目标字段名。

AI 需要做：

- 判断样例里的命名是否值得复用，还是只是历史遗留。
- 判断同义词是否真的同义。

### 4.4 标准缺口索引：standard_gap_index

当字段描述无法匹配标准库时，不应静默跳过，而要进入待沉淀清单。

```json
{
  "gaps": [
    {
      "field_desc": "站点结算时间",
      "suggested_root": "local_settlement_date",
      "reason": "标准库未覆盖，样例中存在 local_settlement_date/local_posted_date 等相近命名",
      "status": "待人工确认"
    }
  ]
}
```

脚本能做：

- 发现无匹配项。
- 统计缺失词高频出现次数。

AI 需要做：

- 给出候选词根。
- 解释为什么该词根合理。
- 标记必须人工确认。

## 5. 字段命名推断流程

字段命名不是一步完成，而是“生成候选 -> 打分 -> AI 裁决 -> 规则复核”。

### 5.1 字段任务对象：field_task

每一行字段设计生成一个任务。

```json
{
  "task_id": "管理快报-金额!R7",
  "model_context": {
    "sheet_name": "管理快报-金额",
    "table_name": "cbebg.dmt_profit_snapshot_amt_ilu_dd",
    "layer": "DMT",
    "data_domain": "财务域",
    "project": "利润核算"
  },
  "field_context": {
    "field_category": "",
    "field_sub_category": "结算报告",
    "current_field_name": "amt",
    "data_type": "decimal(18,6)",
    "field_desc": "金额",
    "reference_field": "amt",
    "reference_table": "cbebg.dws_fin_settlement_shop_msku_subject_ilu_dd",
    "is_primary_key": false,
    "is_business_key": false,
    "remark": ""
  }
}
```

### 5.2 候选生成

脚本先生成候选，不直接拍板。

| 候选来源 | 适合脚本做什么 | 例子 |
|---|---|---|
| 当前字段名 | 判断是否为空、是否合规、是否可保留 | `amt` 已符合小写下划线 |
| 标准库精确匹配 | 字段描述精确命中标准词根 | “日期” -> `dt` |
| 标准库包含匹配 | 字段描述包含多个标准词 | “店铺维表id” -> `shop` + `id` |
| 样例命名统计 | 同描述/同参考字段历史命名 | “金额”在样例中常见为 `amt` |
| 参考字段 | 从来源字段继承或规范化 | `amazon_order_id` -> `amz_order_id` 需要 AI 判断 |
| 代码证据 | 从 SQL alias、DDL comment、字段 lineage 抽取 | `local_posted_dt` 来源于 `local_posted_date` |
| 规则派生 | 枚举、金额、数量、比例、日期后缀 | “状态”候选 `status_cd` |

候选对象：

```json
{
  "candidate_name": "amt",
  "source": "sample_stat",
  "evidence": "完结模型中字段描述“金额”使用 amt",
  "score": 86,
  "risk": "标准库若没有金额=amt，需要沉淀"
}
```

### 5.3 打分逻辑

建议脚本先做初始分：

| 条件 | 加分/减分 |
|---|---:|
| 标准库精确命中 | +40 |
| 标准库业务域匹配 | +15 |
| 完结样例中同描述高频一致 | +20 |
| 参考字段与候选一致 | +15 |
| 代码 SQL alias 与候选一致 | +20 |
| 字段名非法字符 | -100 |
| 多个候选分差小于 10 | 标记 AI 裁决 |
| 标准库无匹配 | 标记待沉淀 |
| 当前字段名与标准候选冲突 | 标记冲突 |

### 5.4 AI 裁决

AI 只处理以下情况：

- 字段名为空，需要从描述和上下文生成。
- 候选之间冲突，例如标准库候选与参考字段候选不一致。
- 描述是组合语义，例如“结算时间，站点时间”。
- 判断枚举、状态、类型是否应加 `_cd`。
- 判断字段名是否过度缩写或语义丢失。
- 标准库缺失，需要给“待沉淀候选”。

AI 输出不是只给字段名，而是结构化决策：

```json
{
  "task_id": "管理快报-金额!R7",
  "decision": "keep",
  "recommended_field_name": "amt",
  "confidence": "high",
  "basis": [
    "参考字段为 amt",
    "字段描述为金额",
    "样例模型中金额字段使用 amt"
  ],
  "conflicts": [],
  "review_note": "",
  "standard_gap": {
    "need_append": true,
    "chinese_name": "金额",
    "suggested_root": "amt"
  }
}
```

### 5.5 最终字段动作

| 动作 | 含义 | 回写行为 |
|---|---|---|
| `keep` | 当前字段名正确 | 不改字段名单元格，只记录依据 |
| `fill` | 当前字段名为空 | 写入推荐字段名 |
| `replace` | 当前字段名不符合标准 | 写入推荐字段名，并记录原字段名 |
| `confirm` | 无法确定 | 不写或写候选，标黄，进入待确认 |
| `block` | 信息不足或冲突严重 | 不写，进入阻断评审 |

## 6. 表名推断流程

表名比字段名更依赖模型上下文。脚本能做格式校验和组件抽取，AI 负责实体/业务过程英文表达判断。

### 6.1 表名任务对象：table_task

```json
{
  "task_id": "管理快报-金额",
  "sheet_name": "管理快报-金额",
  "current_declared_table": "cbebg.dmt_profit_snapshot_amt_ilu_dd",
  "catalog_table": "cbebg.dmt_profit_snapshot_amt_ilu_dd",
  "model_name": "管理快报-金额",
  "layer": "DMT",
  "data_domain": "财务域",
  "project": "利润核算",
  "dependency_position": "交付结果",
  "update_type": null,
  "update_frequency": null
}
```

### 6.2 表名组件拆解

脚本拆表名：

```json
{
  "schema": "cbebg",
  "layer": "dmt",
  "domain_abbr": "profit",
  "entity_or_process": "snapshot_amt",
  "update_type": "ilu",
  "frequency": "dd"
}
```

然后对照附录标准校验：

- 是否有 schema。
- layer 是否与目录分层一致。
- 更新方式是否在 `ilu/flu/ich/fsn` 等规则内。
- 更新频率是否在 `dd/mm` 等规则内。
- 是否小写下划线。
- sheet A1、目录 K 列、实体 sheet 名称是否一致。

### 6.3 表名候选生成

脚本可生成：

- 如果已有表名且格式合规：候选为保留当前表名。
- 如果缺表名：从分层、数据域简称、模型名称、更新方式、频率拼接候选。
- 如果目录和实体 sheet A1 不一致：生成两个候选并标记冲突。

AI 负责：

- 把模型中文名转成合理实体名或业务过程名。
- 判断模型属于明细、汇总、快照、映射、成本、金额、数量等哪类。
- 判断 `settlement`、`settle`、`snapshot`、`amt`、`qty` 等缩写是否应复用样例。

### 6.4 表名决策输出

```json
{
  "task_id": "管理快报-金额",
  "decision": "keep",
  "recommended_table": "cbebg.dmt_profit_snapshot_amt_ilu_dd",
  "confidence": "high",
  "components": {
    "schema": "cbebg",
    "layer": "dmt",
    "subject": "profit_snapshot_amt",
    "update_type": "ilu",
    "frequency": "dd"
  },
  "basis": [
    "目录表名与实体 sheet A1 一致",
    "符合 DMT 表命名结构",
    "更新方式 ilu 和频率 dd 均在附录规则中"
  ],
  "review_note": ""
}
```

## 7. 代码资产如何参与

当前没有 `input/data-assets`，但流程应预留。

### 7.1 脚本能做的代码证据

如果后续接入代码资产，脚本可以：

- 用 `rg` 搜索参考库表名。
- 解析 SQL 中的 `select ... as field_name`。
- 提取 DDL 中字段名、类型、comment。
- 建立字段 lineage：目标字段来自哪个源字段、经过什么表达式。
- 统计同一字段描述或来源字段在代码中的别名。

证据对象：

```json
{
  "reference_table": "cbebg.dws_fin_settlement_shop_msku_subject_ilu_dd",
  "field": "local_posted_dt",
  "evidence_type": "sql_alias",
  "file": "input/data-assets/xxx.sql",
  "expression": "date(local_posted_date) as local_posted_dt",
  "confidence": "high"
}
```

### 7.2 AI 需要判断的代码问题

AI 负责判断：

- 代码现有字段名是否符合标准，还是历史遗留。
- SQL 表达式是否改变了业务语义。
- 同一个来源字段在不同模型中不同命名时，哪一个更适合当前模型。

### 7.3 权威级别

建议权威顺序：

1. 标准库明确规则和词根。
2. 模型设计文档内置附录标准。
3. 完结样例中的稳定一致模式。
4. data-assets 中的代码证据。
5. AI 语义推断。

代码证据很重要，但不应覆盖标准库。冲突时输出“代码现状与标准不一致”。

## 8. 回写怎么做

回写必须基于解析阶段保存的 `source_cell_map`，不要让 AI 直接决定改哪个单元格。

### 8.1 回写策略

建议复制原始模型设计 Excel，再在副本上回写：

- 保留原 sheet 顺序、格式、合并单元格、公式。
- 只修改目标字段名单元格、表名单元格、可选辅助列。
- 新增评审 sheet 和待沉淀 sheet。
- 对高置信度自动结果正常写入。
- 对低置信度或冲突结果写入候选并标色，或留空并写评审说明。

### 8.2 推荐新增辅助列

如果允许新增辅助列，实体设计 sheet 可追加：

| 辅助列 | 作用 |
|---|---|
| 标准化动作 | keep/fill/replace/confirm/block |
| 推荐字段名 | 自动推荐结果 |
| 原字段名 | 被替换前的字段名 |
| 命名依据 | 标准库、样例、参考字段、代码证据 |
| 置信度 | high/medium/low |
| 冲突说明 | 多候选、标准缺失、代码冲突 |
| 待确认问题 | 给人工评审看的问题 |

如果不允许新增列，则单独创建“标准化评审清单”sheet，通过 sheet 名 + 行号 + 字段序号关联。

### 8.3 回写动作示例

```json
{
  "writebacks": [
    {
      "sheet_name": "某模型实体",
      "cell": "D12",
      "old_value": "",
      "new_value": "shop_id",
      "action": "fill",
      "style": "normal"
    },
    {
      "sheet_name": "某模型实体",
      "cell": "D18",
      "old_value": "type",
      "new_value": "event_type_cd",
      "action": "replace",
      "style": "changed"
    }
  ]
}
```

脚本做：

- 根据 `writebacks` 精确写入。
- 设置颜色、批注或评审列。
- 生成新 workbook。

AI 不做：

- 不直接操作 Excel 单元格坐标。
- 不直接改格式。

## 9. 评审怎么做

评审分两层：规则评审和语义评审。

### 9.1 规则评审，脚本负责

| 检查项 | 说明 | 严重级别 |
|---|---|---|
| 字段名为空 | 必填字段名未生成 | 阻断 |
| 字段名非法 | 非小写、含空格、中文、特殊字符 | 阻断 |
| 字段名重复 | 同一实体内字段名重复 | 阻断 |
| 字段描述为空 | 没有语义来源 | 警告/阻断 |
| 参考表不存在 | 参考库表无法在目录/依赖/代码中找到 | 警告 |
| 主键缺失 | 没有主键或业务主键 | 警告 |
| 枚举字段无 `_cd` | 字段描述疑似类型/状态/枚举 | 警告 |
| 表名不合规 | 不符合附录表命名规范 | 阻断 |
| 目录与实体表名不一致 | 目录表名和 sheet A1 不一致 | 阻断 |
| 依赖链断裂 | 依赖说明中的模型未出现在目录或实体 sheet | 警告/阻断 |

### 9.2 语义评审，AI 负责

AI 重点看：

- 同义不同名：同一业务含义在不同表里命名不一致。
- 同名不同义：同一字段名在不同表里含义不一致。
- 字段名语义过窄或过宽。
- 字段分类与字段描述不一致。
- 模型粒度与业务主键不匹配。
- 参考字段与字段描述表达的含义不一致。
- 表名里的实体/业务过程表达不准确。

### 9.3 评审清单对象

```json
{
  "review_items": [
    {
      "severity": "blocker",
      "scope": "field",
      "sheet_name": "某模型实体",
      "row_number": 18,
      "field_desc": "事件类型",
      "current_value": "type",
      "recommended_value": "event_type_cd",
      "issue": "枚举字段未使用 cd 后缀，且字段名 type 语义过泛",
      "owner": "模型设计者",
      "status": "待确认"
    }
  ]
}
```

## 10. 哪些是脚本能做的，哪些需要 AI

### 10.1 脚本适合做的事

| 模块 | 脚本职责 |
|---|---|
| Excel 解析 | 读取 workbook、sheet、表头、数据区、单元格坐标 |
| 标准库索引 | 构建规则索引、词根索引、冲突索引、别名统计 |
| 候选生成 | 通过标准库、参考字段、样例统计、代码证据生成候选 |
| 规则打分 | 按固定权重计算候选分数 |
| 格式校验 | 字段名、表名、重复、空值、非法字符 |
| 代码搜索 | 搜索表名、字段名、SQL alias、DDL comment |
| 回写 Excel | 按坐标写入结果、标色、生成评审 sheet |
| 运行日志 | 保存输入摘要、统计、异常 |

### 10.2 AI 必须参与的事

| 模块 | AI 职责 |
|---|---|
| 中文语义拆解 | 判断字段描述里哪些是实体、属性、指标、修饰语 |
| 候选取舍 | 标准库、参考字段、样例和代码冲突时做解释性裁决 |
| 枚举判断 | 判断“类型/状态/场景/阶段”等是否真是枚举 |
| 标准缺口建议 | 标准库没有词根时给候选词根和沉淀建议 |
| 表名语义 | 将模型中文名转成合理实体/业务过程英文表达 |
| 语义评审 | 发现同义不同名、同名不同义、粒度不一致等 |
| 人工问题整理 | 把低置信度点组织成可评审问题 |

### 10.3 不应该让 AI 做的事

- 不让 AI 直接猜 Excel 单元格坐标。
- 不让 AI 在没有证据时给高置信度。
- 不让 AI 默默覆盖标准库。
- 不让 AI 直接把代码现状当标准。
- 不让 AI 在输出 Excel 时丢失原表结构和样式。

## 11. 第一版 Skill 应该怎么落

建议第一版只做一个主 Skill，内部有脚本分工。

```text
模型设计标准化 Skill
  SKILL.md
  scripts/
    01_parse_workbooks.py
    02_build_standard_index.py
    03_collect_code_evidence.py
    04_generate_candidates.py
    05_validate_rules.py
    06_writeback_excel.py
  references/
    intermediate_schema.md
    naming_decision_policy.md
  assets/
    review_sheet_template.xlsx
```

### 11.1 主 Skill 的执行顺序

1. 读取用户指定输入文件。
2. 调用脚本解析标准库和模型设计 Excel。
3. 如果存在 data-assets，调用代码证据脚本。
4. 生成字段和表名候选。
5. AI 读取候选任务，输出裁决 JSON。
6. 脚本执行规则校验。
7. AI 读取校验结果，生成语义评审意见。
8. 脚本回写 Excel。
9. 输出最终 Excel、评审清单、待沉淀标准库项。

### 11.2 第一版不要贪多

建议第一版边界：

- 支持字段名为空时自动补齐。
- 支持已有字段名时做合规校验。
- 支持表名校验，暂不强制自动生成复杂表名。
- 支持新增评审 sheet。
- 支持标准库缺失项沉淀。
- 暂不做复杂 SQL lineage，只做表名/字段名/alias 搜索。

## 12. 端到端样例

假设待处理字段行：

| 字段名 | 字段数据类型 | 字段描述 | 参考字段 | 参考库表 |
|---|---|---|---|---|
|  | text | 店铺名 | store_name | cbebg.ods_realtime_db_t_lx_settlement_transactiondetaillist |

## 13. 风险与处理

| 风险 | 处理 |
|---|---|
| Excel 结构不稳定 | 用表头语义识别，不固定列号 |
| 标准库覆盖不全 | 输出待沉淀标准库，不静默编造 |
| 样例命名有历史包袱 | 样例只作证据，不覆盖标准库 |
| 代码与标准冲突 | 标准优先，代码冲突进评审 |
| AI 过度自信 | 强制输出依据、置信度、冲突和待确认项 |
| 回写破坏原格式 | 复制原 workbook，按坐标局部回写 |
| 评审信息太多 | 分 blocker/warning/info，只把 blocker 作为必须处理 |

## 14. 推荐推进路径

### 阶段一：只读分析器

先不回写 Excel，只输出：

- 标准库索引摘要。
- 模型设计结构摘要。
- 字段命名候选。
- 表名校验结果。
- 评审清单。

目的：验证解析和判断是否靠谱。

### 阶段二：字段名补齐

只处理字段名为空的行：

- 高置信度自动填。
- 中低置信度进入评审。
- 不替换已有字段名。

目的：降低风险，先解决最明确的需求。

### 阶段三：字段名修正和表名校验

开始处理已有字段名：

- 不合规字段名给替换建议。
- 表名只做校验和建议，人工确认后再自动改。

### 阶段四：代码证据接入

接入 data-assets：

- SQL alias。
- DDL comment。
- 表字段 lineage。
- 已有模型命名统计。

### 阶段五：标准库回流

把每次模型设计中出现的标准缺口整理成“待沉淀标准库”：

- 新词根。
- 新规则。
- 冲突规则。
- 高频别名。

## 15. 最小可执行版本定义

如果现在立刻做第一版，我建议最小版本只交付以下能力：

1. 稳定读取标准库和模型设计 Excel。
2. 识别模型目录、依赖说明、实体设计 sheet、附录表命名规则。
3. 对每个实体字段生成 `field_task`。
4. 基于标准库和样例文档生成字段名候选。
5. AI 对空字段名和冲突字段名做裁决。
6. 输出评审清单。
7. 复制原 Excel 并回写高置信度字段名。
8. 新增“标准化评审清单”和“标准库待沉淀”sheet。

这个版本已经可以回答最核心的问题：给一份字段名空着的模型设计文档，系统能否根据字段描述、参考字段、参考库表和标准库，产出一份可评审的标准模型设计文档。

## 16. 对当前问题的直接回答

有办法全部梳理清楚，关键是不要把它想成一个“AI 填 Excel”的黑盒，而要把它拆成：

- Excel 结构解析：把文档拆成目录、依赖、实体字段、附录标准和可回写坐标。
- 标准库索引：把规则、词根、别名、冲突和缺口做成可检索结构。
- 字段/表名推断：脚本生成候选和证据，AI 做语义裁决。
- 回写：脚本按坐标改 Excel，AI 不直接操作单元格。
- 评审：脚本抓硬规则，AI 抓语义问题，最终形成 blocker/warning/info 清单。

只要这个结构成立，后续做成一个或多个 Skill 就比较自然：先做一个主 Skill 跑通端到端，再按复杂度拆出“Excel 解析”“标准索引”“命名推断”“回写评审”等子能力。
