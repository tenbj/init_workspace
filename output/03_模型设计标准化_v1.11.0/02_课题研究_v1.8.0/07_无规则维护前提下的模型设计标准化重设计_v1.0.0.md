# 无规则维护前提下的模型设计标准化重设计

> 本文根据用户明确反馈重新评估方案：不维护候选集合、不维护弱证据规则、不维护 token 抽取规则、不维护判定策略。  
> 结论：需要重设计。脚本不再承担任何语义预筛职责，流程改为 AI-first。

---

## 1. 用户前提

用户明确说明：

- 没有候选集合。
- 没有弱证据规则。
- 没有 token 抽取规则。
- 没有判定策略。
- 目前也不打算维护，因为维护成本高、容易遗漏。

这个前提会使上一版“脚本发现规则不收敛”的设计不再成立。

上一版成立的条件是：

```text
脚本有候选集合 + 弱证据表 + token 规则 + 判定策略。
```

现在这些都没有，所以必须重新设计。

---

## 2. 重新评估：旧方案哪里失效

### 2.1 脚本无法发现“不确定”

如果没有候选集合，脚本不知道“商品”可能对应 product、sku、msku、asin。

如果没有弱证据规则，脚本不知道 `id` 是弱证据。

如果没有 token 抽取规则，脚本不会把 `msku_id` 拆成 `msku + id`。

如果没有判定策略，脚本不知道多候选、弱证据、冲突证据该如何处理。

因此脚本不能发现：

```text
确定
不确定
候选冲突
证据不足
```

它最多能发现非常客观的结构事实：

```text
字段名为空
字段描述为空
模板列缺失
Excel 行列读取失败
```

### 2.2 标准库索引的角色也要降级

如果不维护业务规则和候选关系，标准库索引不能作为脚本判定依据。

它只能是：

```text
给 AI 看的资料包
```

而不是：

```text
脚本可执行的规则库
```

### 2.3 “脚本预筛 AI 任务”不成立

旧方案假设脚本能先筛出哪些字段需要 AI。

现在不成立，因为脚本不知道什么字段需要 AI。

新的原则应是：

```text
凡是涉及字段命名、表名语义、字段描述理解、参考字段继承的任务，默认都交给 AI。
```

脚本不做语义筛选，只做任务打包。

---

## 3. 新方案：AI-first，脚本只做基础设施

重设计后的流程：

```text
脚本解析 Excel
  -> 脚本固定模板检查
  -> 脚本把每个实体 sheet 打包成 AI 工作包
  -> AI 全量评审字段和表名
  -> AI 输出结构化决策
  -> 脚本做客观后验校验
  -> 脚本回写 Excel
  -> 用户评审
```

这里的核心变化是：

```text
脚本不再判断哪些字段可疑。
AI 对目标范围内的字段进行全量语义评审。
```

---

## 4. 脚本的新职责

脚本只做不需要业务理解的工作。

### 4.1 Excel 解析

脚本负责：

- 读取 workbook。
- 识别 sheet。
- 读取固定模板列。
- 抽取模型目录。
- 抽取依赖说明原始行。
- 抽取实体设计字段行。
- 保存单元格坐标。

输出：

```text
workbook_manifest.json
template_check.json
model_catalog.json
entity_sheets.jsonl
entity_fields.jsonl
```

### 4.2 模板检查

脚本可以检查固定模板是否完整：

- 是否存在固定列。
- 列名是否一致。
- 表头是否缺失。
- 字段序号是否为空。
- 字段描述是否为空。
- 字段名是否为空。

这不是语义判断，是结构检查。

### 4.3 AI 工作包打包

脚本按模型或 sheet 生成 AI 工作包。

不再生成“可疑语义任务”，而是生成：

```text
ai_field_review_batches.jsonl
```

一行一个模型实体 sheet：

```json
{
  "batch_id": "entity:管理快报-金额",
  "model_context": {
    "sheet_name": "管理快报-金额",
    "declared_table": "cbebg.dmt_profit_snapshot_amt_ilu_dd",
    "model_catalog_row": {},
    "dependency_rows": []
  },
  "standard_library": {
    "rules_sheet_rows": [],
    "mapping_sheet_rows": []
  },
  "fields": [
    {
      "row_number": 4,
      "field_name": "",
      "data_type": "bigint",
      "field_desc": "商品",
      "reference_field": "id",
      "reference_table": "xxx",
      "is_primary_key": "",
      "is_business_key": ""
    }
  ]
}
```

脚本不判断这行是否可疑，直接交给 AI。

### 4.4 客观后验校验

AI 输出字段名后，脚本可以检查：

- 字段名是否为空。
- 字段名是否小写下划线。
- 同一实体内字段名是否重复。
- 字段名是否含中文或空格。
- AI 是否给了必填字段：推荐字段名、置信度、依据、是否需人工确认。
- 回写计划是否指向合法单元格。

脚本仍然不能判断字段名语义对不对。

### 4.5 Excel 回写

脚本按 AI 决策回写：

- 高置信度且不需确认：可回写字段名。
- 中低置信度或 AI 标记需确认：写入候选/评审清单，不直接覆盖。
- AI 明确无法判断：写入评审清单。

这里的“高置信度”来自 AI，不来自脚本。

---

## 5. AI 的新职责

在无规则维护前提下，AI 承担语义主流程。

AI 需要做：

1. 读标准库原始内容。
2. 读模型上下文。
3. 读字段列表。
4. 自己判断字段描述、参考字段、参考表之间的关系。
5. 自己生成候选字段名。
6. 自己判断证据是否足够。
7. 自己标记是否需要人工确认。
8. 输出结构化决策。

AI 输出示例：

```json
{
  "sheet_name": "管理快报-金额",
  "row_number": 4,
  "current_field_name": "",
  "recommended_field_name": null,
  "decision": "need_human_confirm",
  "confidence": "low",
  "reason": "字段描述为“商品”，参考字段仅为 id，缺少参考表、业务主键或标准库关系，无法判断商品具体粒度。",
  "human_question": "请确认该字段表示 product、sku、msku、asin 还是 listing。",
  "writeback_allowed": false
}
```

如果上下文足够：

```json
{
  "sheet_name": "管理快报-金额",
  "row_number": 4,
  "current_field_name": "",
  "recommended_field_name": "msku_id",
  "decision": "suggest_with_review",
  "confidence": "medium",
  "reason": "字段描述为商品，但参考表和模型粒度均指向店铺MSKU粒度；商品在该上下文中更可能指 MSKU。",
  "human_question": "建议确认字段描述是否应改为 MSKU维表ID。",
  "writeback_allowed": false
}
```

注意：AI 可以建议，但中等置信度不直接回写。

## 6. 标准库在新方案中的角色

标准库不再被脚本解析成可执行语义规则，而是作为 AI 的权威参考材料。

### 6.1 标准库可以直接给 AI

如果标准库规模不大，例如当前映射标准库约 130 行，可以直接把完整标准库作为上下文给 AI。

这样不需要维护候选集合。

### 6.2 标准库变大时怎么办

如果未来标准库很大，有两种低维护方案：

1. 全文检索：只按字段描述和参考字段做简单字符串检索。
2. 向量检索：自动生成 embedding 检索相近标准。

这两者都不是人工维护候选规则，而是技术检索。

但需要明确：

```text
检索结果只是给 AI 的参考，不作为脚本结论。
```

### 6.3 待沉淀不等于规则维护

用户不想维护复杂规则，这是合理的。

待沉淀标准可以只作为评审结果沉淀，不强迫转成脚本规则。

也就是说：

```text
标准库主要给 AI 看，不主要给脚本执行。
```

## 7. “没有规则”时如何控制风险

如果语义都交给 AI，风险会转移到 AI 判断质量。需要用流程控制风险。

### 7.1 不直接全自动回写

第一版不建议直接覆盖字段名。

建议分三类：

| AI 决策 | 回写行为 |
|---|---|
| `fill_safe` | 高置信度，可写入字段名 |
| `suggest_with_review` | 写入候选和评审清单，不覆盖或标色 |
| `need_human_confirm` | 不写字段名，只进评审清单 |
| `cannot_decide` | 阻断项，要求补充信息 |

### 7.2 AI 必须输出理由

每个推荐字段名必须有：

- 推荐字段名。
- 依据。
- 置信度。
- 是否允许自动回写。
- 给人的确认问题。

没有理由的建议不得回写。

### 7.3 脚本只做安全阀

脚本后验检查：

- AI 输出字段名非法 -> 拒绝回写。
- AI 输出为空但标记可回写 -> 拒绝回写。
- AI 输出重复字段名 -> 拒绝回写。
- AI 未给理由 -> 拒绝回写。

这仍然不需要业务规则。

### 7.4 人工评审是流程的一部分

无规则维护意味着不能追求高自动化率。

目标应改为：

```text
AI 生成可评审的标准化建议，而不是一次性自动完成所有字段。
```

## 8. 新旧方案对比

| 维度 | 旧方案 | 新方案 |
|---|---|---|
| 脚本角色 | 解析 + 语义预筛 + 候选打分 | 解析 + 任务打包 + 客观校验 + 回写 |
| 是否需要维护规则 | 需要 | 不需要复杂业务规则 |
| 字段是否全量给 AI | 否，脚本预筛 | 是，按实体 sheet 批量给 AI |
| 标准库用途 | 脚本索引 + AI 参考 | 主要给 AI 参考 |
| 自动化率 | 可能更高 | 初期较低 |
| 维护成本 | 高 | 低 |
| 漏判风险 | 脚本可能漏掉需要 AI 的字段 | 低，因为全量给 AI |
| AI 成本 | 较低 | 较高 |
| 可解释性 | 高，但规则维护重 | 依赖 AI 理由和审计输出 |

## 9. 是否需要重新设计

结论：需要重新设计。

但不是推翻全部，而是调整重心：

保留：

- Excel 固定模板解析。
- 解析结果持久化。
- 依赖图作为上下文。
- 输出评审清单。
- Excel 回写。
- 待沉淀标准。

废弃或降级：

- 脚本语义预筛。
- 手工维护候选集合。
- 手工维护弱证据规则。
- 手工维护 token 抽取规则。
- 脚本候选打分。
- 脚本判断规则是否收敛。

新增：

- AI 全量字段评审。
- AI 工作包设计。
- AI 输出结构化决策 schema。
- 脚本后验安全校验。
- 人工评审优先的回写策略。

## 10. 新的最小可执行版本

第一版建议这样做：

### 10.1 只读阶段

脚本输出：

```text
workbook_manifest.json
template_check.json
model_catalog.json
entity_fields.jsonl
ai_field_review_batches.jsonl
```

AI 输出：

```text
ai_field_review_decisions.jsonl
review_summary.md
```

不回写 Excel。

### 10.2 半自动阶段

在 Excel 中新增：

```text
AI字段建议
待人工确认
待沉淀标准
```

不覆盖原字段名，先让人评审。

### 10.3 自动回写阶段

只有当 AI 连续多轮表现稳定，并且用户认可某些类型字段可自动处理后，再开放高置信度回写。

## 11. 对“商品 + id”的新方案处理

输入：

```text
字段描述：商品
参考字段：id
```

脚本做：

```text
不判断。
只把这行和所在模型上下文打包给 AI。
```

AI 做：

```text
判断证据不足，无法确定商品粒度。
输出 need_human_confirm。
```

脚本后验：

```text
看到 writeback_allowed=false，不回写字段名。
把问题写入评审清单。
```

用户看到：

```text
请确认“商品”具体指 product、sku、msku、asin 还是 listing。
```

这个流程不需要维护候选集合，也不需要脚本识别 `id` 是弱证据。因为 AI 会读到 `id` 并判断它无法提供足够语义。

## 12. 最终结论

在用户不打算维护候选集合、弱证据规则、token 规则和判定策略的前提下，原来的脚本辅助语义判断方案不合理，需要重设计。

新的合理方案是：

```text
脚本不做语义判断，也不做语义预筛。
脚本只做 Excel 解析、上下文打包、持久化、客观校验、Excel 回写。
AI 对字段进行全量语义评审，输出结构化建议和置信度。
用户通过评审清单和待沉淀标准进行确认。
```

这会牺牲一些自动化率和成本，但显著降低规则维护成本和漏判风险，更符合当前阶段。
