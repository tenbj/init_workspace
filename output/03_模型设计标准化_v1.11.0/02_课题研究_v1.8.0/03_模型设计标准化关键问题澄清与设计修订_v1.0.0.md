> 本文针对 2026-05-11 用户提出的 6 个关键问题，对上一版“自动化流程详细设计”做修订。  
> 本文优先级高于前一版文档中与之冲突的表述。

## 1. 关于“是否保留”：修订为固定模板字段，默认是

用户反馈：

> “是否保留”是给人用的，用于人最后的评审，对于你来说默认是就好了。Excel 模板的字段应该是固定的。不固定的就是问题，需要我来确认的。

这个反馈是对的。上一版把“是否保留”当成一种不稳定列来兼容，是不准确的。修订如下：

### 1.1 模板字段应固定

模型实体设计 sheet 的标准字段应固定为一套模板，不应该因为某些 sheet 多一列或少一列就默默兼容。

建议固定字段如下：

| 序号 | 字段 | 用途 | AI/脚本处理 |
|---:|---|---|---|
| 1 | 字段分类 | 人工组织字段来源或主题 | 可读取，不强推断 |
| 2 | 二级分类 | 人工组织字段来源或主题 | 可读取，不强推断 |
| 3 | 字段序号 | 字段顺序 | 脚本校验连续性 |
| 4 | 字段名 | 核心输出 | AI 生成/校验，脚本回写 |
| 5 | 字段数据类型 | 开发约束 | 脚本校验空值，AI 可提示不合理 |
| 6 | 字段描述 | 核心语义输入 | AI 重点理解 |
| 7 | 参考字段 | 来源证据 | 脚本检索，AI 判断是否继承 |
| 8 | 参考库表 | 来源证据 | 脚本检索，图谱关联 |
| 9 | 是否主键字段 | 建模约束 | 脚本校验，AI 可评审 |
| 10 | 是否业务主键 | 粒度约束 | 脚本校验，AI 可评审 |
| 11 | 是否保留 | 人工评审字段 | 默认“是”，AI 不用它判断是否处理 |
| 12 | 备注 | 人工补充 | AI 可读取为辅助上下文 |

如果当前已有模板里“是否保留”位置不同，需要先确定一个正式模板版本。正式模板确定后，脚本只接受该模板，不再宽松兼容。

### 1.2 不固定就是问题

Excel 结构解析不再以“尽量识别各种列结构”为目标，而是以“识别是否符合模板”为目标。

如果出现以下情况，应进入结构问题清单：

- 缺少固定字段列。
- 固定字段列改名。
- 固定字段列顺序变化。
- 出现未登记的额外列。
- 表头行不在预期位置。
- “是否保留”缺失或不是固定列。

这类问题不应该由 AI 自行猜测处理，而应该交给用户确认模板版本。

### 1.3 “是否保留”的处理规则

“是否保留”只作为人工评审字段：

- 空值时默认视为“是”。
- 为“否”时，字段仍然可以被解析，但默认不参与最终字段输出。
- AI 不基于“是否保留”决定命名标准。
- 脚本可以在评审清单中提示“存在是否保留=否的字段”，供人工确认。

## 2. Excel 结构解析结果必须存文件，而不是只放上下文

用户问题：

> Excel 结构解析，输出的内容载体是文件吗？还是一次性的使用上下文就结束了？换个会话就没了？

修订结论：必须存文件。不能只依赖本轮会话上下文。

原因：

- 模型设计标准化是可审计流程，不是一次性聊天。
- 换会话后应能继续使用同一批解析结果。
- 字段名决策需要回溯证据。
- 用户要能查看“AI 到底根据什么改了 Excel”。
- 后续可以复跑、对比、回滚。

### 2.1 运行产物目录

每次执行模型设计标准化，都创建一个 run 目录：

```text
output/01_模型设计标准化_v{project_version}/03_代码程序_v{code_version}/runs/{run_id}/
```

`run_id` 建议：

```text
YYYYMMDD_HHMMSS_{任务短名}
```

示例：

```text
output/01_模型设计标准化_v1.3.0/03_代码程序_v1.0.0/runs/20260511_161500_利润核算快报/
```

如果还没有进入真正开发阶段，设计文档先放在 `02_课题研究`；一旦开始跑实际 Excel 标准化，解析 JSON、回写结果、日志、最终 Excel 都放到 `03_代码程序/.../runs/`。

### 2.2 解析产物文件类型

建议文件组织：

| 文件 | 类型 | 用途 |
|---|---|---|
| `00_run_manifest.json` | JSON | 本次运行总入口，记录输入文件、hash、时间、参数 |
| `01_workbook_manifest.json` | JSON | 工作簿、sheet 列表、sheet 类型、可见性、行列统计 |
| `02_template_check.json` | JSON | 模板检查结果，缺列、多列、顺序异常等 |
| `03_sheet_regions.json` | JSON | 每个 sheet 的标题区、表头行、数据区、固定列坐标 |
| `04_model_catalog.json` | JSON | 模型目录结构化结果 |
| `05_dependency_graph.json` | JSON | 依赖数据流图 |
| `06_entity_fields.jsonl` | JSONL | 每一行字段一个对象，适合流式处理 |
| `07_standard_library_index.json` | JSON | 标准库解析与索引结果 |
| `08_field_candidates.jsonl` | JSONL | 每个字段的候选字段名和证据 |
| `09_ai_decisions.jsonl` | JSONL | AI 对字段/表名的裁决结果 |
| `10_review_items.jsonl` | JSONL | 评审问题清单 |
| `11_standard_gaps.jsonl` | JSONL | 待沉淀标准项 |
| `12_writeback_plan.json` | JSON | 准备写回 Excel 的单元格级计划 |
| `run_summary.md` | Markdown | 给人看的运行摘要 |

### 2.3 为什么有 JSON 也有 JSONL

JSON 适合整体对象，例如工作簿清单、依赖图。

JSONL 适合一行一个任务，例如字段候选、AI 决策、评审项。好处：

- 可以逐行处理，不怕字段很多。
- 某一行失败不影响整体。
- 后续可追加、过滤、对比。
- 更适合给 AI 分批处理。

### 2.4 工作簿清单示例

用户举的 `workbook_manifest` 应保存为：

```text
01_workbook_manifest.json
```

示例：

```json
{
  "file_path": "input/模型设计 - 利润核算（快报）.xlsx",
  "file_hash": "sha256...",
  "sheet_count": 34,
  "sheets": [
    {
      "sheet_id": 4,
      "sheet_name": "1.1 模型设计目录",
      "visible": true,
      "non_empty_rows": 24,
      "max_col_seen": 47,
      "detected_type": "model_catalog"
    }
  ]
}
```

这个文件不是临时上下文，而是长期运行证据。下一轮会话可以从 `00_run_manifest.json` 找回全部中间产物。

## 3. 依赖数据流对象应重新设计为图

用户反馈：

> 依赖数据流对象应该是个图，因为人不会画图，才用 Excel，表达方式并不好，需要有一个更好的方式。

这个判断非常重要。Excel 中的“模型依赖说明（数据流）”只是人工可维护的二维表达，不适合作为内部计算结构。内部应转换为图。

### 3.1 为什么必须是图

模型依赖天然不是表格，而是有向图：

- 一个源表可以进入多个模型。
- 一个模型可以依赖多个上游。
- 一个 DMT 结果可能汇聚多个 DWS/DWD。
- 依赖链会分叉、汇合、跨层。
- 需要检查断点、孤点、环路、缺失节点。

二维 Excel 适合人填，但不适合做这些计算。

### 3.2 图的基本结构

建议文件：

```text
05_dependency_graph.json
```

结构：

```json
{
  "nodes": [
    {
      "node_id": "source:realtime_db.t_lx_settlement_transactiondetaillist",
      "node_type": "source_table",
      "display_name": "结算报告",
      "system": "领星",
      "database": "realtime_db",
      "table": "t_lx_settlement_transactiondetaillist"
    },
    {
      "node_id": "model:领星结算报告映射结果",
      "node_type": "model",
      "layer": "DWD",
      "model_name": "领星结算报告映射结果",
      "table_name": "cbebg.dwd_fin_settle_map_result_ilu_dd"
    }
  ],
  "edges": [
    {
      "edge_id": "e001",
      "from": "source:realtime_db.t_lx_settlement_transactiondetaillist",
      "to": "model:领星结算报告映射结果",
      "edge_type": "feeds",
      "source_excel_row": 4,
      "evidence": "1.2 模型依赖说明（数据流）!R4"
    }
  ]
}
```

### 3.3 节点类型

| 节点类型 | 含义 |
|---|---|
| `external_file` | 共享盘 Excel、人工上传文件 |
| `source_table` | ODS/采集库/业务库源表 |
| `model` | REF/DWD/DWS/DMT 等模型 |
| `metric_output` | OneData 指标或报表交付结果 |
| `unknown` | Excel 中出现但无法识别的节点 |

### 3.4 边类型

| 边类型 | 含义 |
|---|---|
| `feeds` | 上游输入下游 |
| `transforms_to` | 经过加工生成 |
| `aggregates_to` | 明细汇总为汇总 |
| `maps_to` | 映射表参与标准化或分类 |
| `manual_upload_to` | 人工文件导入模型 |
| `unknown_relation` | 关系不明确，需要确认 |

### 3.5 图的输出不止 JSON

为了让人看懂，图应输出三种形式：

| 文件 | 用途 |
|---|---|
| `05_dependency_graph.json` | 机器计算 |
| `05_dependency_graph.mmd` | Mermaid 图，可视化 |
| `05_dependency_graph.md` | 人类说明，列出图谱问题 |

Mermaid 示例：

```mermaid
flowchart LR
  A[领星结算报告] --> B[DWD 领星结算报告映射结果]
  B --> C[DWS 店铺MSKU科目汇总]
  C --> D[DMT 管理快报-金额]
```

### 3.6 图能做哪些校验

脚本能做：

- 依赖节点是否都存在于模型目录。
- 实体设计 sheet 是否覆盖所有模型节点。
- 是否有孤立模型。
- 是否有跨层异常，例如 DMT 直接依赖 ODS 但未说明原因。
- 是否有环。
- 同一节点是否名称不一致。

AI 能做：

- 判断某条边的业务含义。
- 判断某个模型是否应该拆成多个节点。
- 判断“管理快报-金额”和“管理快报-数量”是否应共享上游。
- 解释图上的异常是否真是设计问题。

## 4. 重新评估标准库索引的意义、边界和可行性

用户质疑：

> 关于标准库索引，感觉你仿佛用脚本就像完全实现，但这里需要有语义理解的部分，比如说商品和 msku 应该是一回事，但你能通过索引检索到吗？规则索引也不知道你要如何使用？所以我有些不理解标准库建立索引的意义。

这个质疑成立。上一版写法容易让人误解成“索引一建，脚本就能理解业务”。这不现实。

### 4.1 先纠正一个关键点：索引不是理解

标准库索引的意义不是替代 AI 的语义理解，而是提供证据、约束和可追溯候选。

可以这样理解：

- 索引负责“找到可能相关的标准”。
- AI 负责“判断这些标准和当前字段是否真的相关”。
- 脚本负责“记录证据、打分、回写、校验格式”。

索引是检索系统，不是业务理解系统。

### 4.2 商品和 MSKU 的例子

“商品”和“MSKU”这个例子非常典型。

脚本索引能做到：

- 如果标准库里有“商品 -> product/prd”和“MSKU -> msku”，脚本能检索到两个候选。
- 如果样例文档中“msku_id”的字段描述多次出现“商品”“MSKU维表id”，脚本能统计出它们经常共现。
- 如果代码里 `product_id` 和 `msku_id` 经常 join，脚本能发现关联证据。

脚本做不到：

- 直接断定“商品”和“MSKU”就是一回事。
- 判断当前字段粒度到底是 SPU、SKU、MSKU、ASIN 还是平台商品。
- 判断在利润核算里应该统一叫 `msku_id` 还是 `product_id`。

AI 需要做：

- 结合上下文判断“商品”在当前模型里指什么。
- 如果模型粒度是店铺 + MSKU + 日期，字段描述写“商品”但参考字段是 `msku_id`，AI 应提示“字段描述应改成 MSKU 或店铺商品口径”。
- 如果标准库没有“MSKU”和“商品”的关系，AI 应把它列入待沉淀。

所以，“商品”和“MSKU”不是索引能自动解决的问题，而是索引提供候选和证据，AI 给出语义判断，最终人确认标准。

### 4.3 标准库索引到底有什么用

它的价值有 6 个：

1. 缩小 AI 判断范围  
   不让 AI 从无限词汇里自由发挥，而是先给它标准库候选。

2. 提供可追溯依据  
   最终字段名能说明来自哪条标准、哪个样例、哪个参考字段。

3. 发现标准库缺口  
   如果所有候选都匹配不上，就进入待沉淀，不静默生成。

4. 发现冲突  
   同一个中文词有多个词根、同一个词根有多个中文含义，都能被脚本发现。

5. 支撑一致性检查  
   同一个字段描述在多个模型里不一致，脚本能统计，AI 再判断。

6. 降低换会话损耗  
   标准库解析结果持久化后，后续会话不用重新理解全部 Excel。

### 4.4 规则索引怎么用

规则分两类：机器可执行规则和语义解释规则。

#### 机器可执行规则

脚本可以直接执行：

- 字段名必须小写。
- 字段名只能包含字母、数字、下划线。
- 字段名不能重复。
- 字段名不能为空。
- 表名必须符合 `{schema}.{layer}_..._{update_type}_{frequency}`。
- 更新方式必须在标准枚举里。

#### 语义解释规则

脚本不能直接执行，只能转成 AI 任务：

- “字段名统一使用字段描述为标准翻译。”
- “实体名_属性/指标。”
- “枚举字段加 cd 后缀。”

例如“枚举字段加 cd 后缀”，脚本只能初筛字段描述里是否有“类型、状态、阶段、场景、标识”等词，但不能断定它一定是枚举。AI 需要结合字段描述、参考字段、数据类型、备注判断。

### 4.5 标准库索引的可行边界

| 能力 | 脚本可行性 | AI 可行性 | 说明 |
|---|---|---|---|
| 精确匹配标准词 | 高 | 不需要 | “日期”匹配 `dt` |
| 包含匹配 | 中 | 需要复核 | “站点结算时间”包含“结算”“时间” |
| 同义词识别 | 低 | 中高 | 商品/MSKU 要 AI 判断 |
| 业务粒度判断 | 低 | 中 | 需要依赖图、主键、参考表 |
| 规则格式校验 | 高 | 不需要 | 小写下划线等 |
| 枚举语义判断 | 低 | 中高 | 类型/状态不一定都是枚举 |
| 词根缺口建议 | 低 | 中 | AI 可建议，人最终确认 |
| 标准冲突仲裁 | 中 | 中高 | 脚本发现，AI 解释，人确认 |

结论：标准库索引有意义，但它不是“自动理解标准”。它是让 AI 的判断更受约束、更可审计、更能沉淀。

## 5. 待沉淀清单的形式与交互

用户问题：

> 待沉淀清单是什么形式？json？md？怎么和我交互？

结论：应该同时有机器文件和人类评审表，但用户主要交互对象应是 Excel。

### 5.1 三种载体

| 载体 | 文件 | 给谁用 |
|---|---|---|
| 机器明细 | `11_standard_gaps.jsonl` | 脚本和 AI |
| 人类评审表 | 最终 Excel 中的 `待沉淀标准` sheet | 用户 |
| 摘要说明 | `standard_gaps_summary.md` | 用户快速阅读 |

### 5.2 为什么用户主要用 Excel

你的输入和评审习惯都在 Excel 中，标准库本身也是 Excel。因此“待沉淀清单”最终也应该回到 Excel，而不是要求你读 JSON。

JSONL 是底层证据，Excel sheet 是交互界面。

### 5.3 待沉淀标准 sheet 字段

建议列：

| 列 | 说明 |
|---|---|
| 状态 | 待确认/接受/拒绝/合并到已有标准/需要补充 |
| 缺口类型 | 新词根/同义词/规则缺口/冲突/口径不清 |
| 来源模型 | 哪个模型 sheet |
| 来源行号 | Excel 行号 |
| 字段描述 | 原始字段描述 |
| 参考字段 | 原始参考字段 |
| 参考库表 | 原始参考库表 |
| 当前字段名 | 原字段名 |
| 推荐字段名 | AI 推荐 |
| 推荐标准词根 | 建议沉淀的词根 |
| 关联已有标准 | 可能相关的标准库条目 |
| AI 理由 | 为什么建议沉淀 |
| 用户意见 | 用户填写 |
| 最终处理 | 本轮是否写入标准库 |

### 5.4 示例

| 状态 | 缺口类型 | 字段描述 | 推荐字段名 | 推荐标准词根 | AI 理由 | 用户意见 |
|---|---|---|---|---|---|---|
| 待确认 | 同义词 | 商品维表id | msku_id | msku_id | 参考字段为 msku_id，模型粒度为店铺+MSKU，但字段描述写商品，需确认商品是否等同 MSKU |  |
| 待确认 | 新词根 | 站点结算时间 | local_settlement_date | local_settlement_date | 标准库未覆盖，样例存在 local_posted_date/local_settlement_date 近似表达 |  |

### 5.5 交互方式

第一轮：

- AI 输出标准化 Excel。
- Excel 内新增 `待沉淀标准` sheet。
- 所有状态默认为“待确认”。

用户评审：

- 在 `状态` 列选择：接受、拒绝、合并到已有标准、需要补充。
- 在 `用户意见` 列写原因或指定标准词根。

第二轮：

- AI 读取用户改过的 `待沉淀标准` sheet。
- 对“接受”的条目生成标准库更新建议。
- 对“合并到已有标准”的条目更新别名索引。
- 对“拒绝”的条目加入黑名单或本项目例外。

这样，待沉淀清单不是一次性报告，而是标准库治理入口。

## 6. 整体架构：先一个主 Skill，不急着拆多个

用户问题：

> 整体的架构是一个 skill 就结束了？还是说拆多个 skill 更好？你的设计原则和评估标准是什么？

结论：第一阶段做一个主 Skill 更好，但内部必须模块化。等边界稳定后，再拆多个 Skill。

### 6.1 为什么第一阶段不拆多个 Skill

现在最大的不确定性不是代码复杂度，而是流程边界：

- 标准库到底怎么治理。
- 模板字段最终如何固定。
- 哪些异常必须人工确认。
- AI 裁决结果用户是否接受。
- 待沉淀标准如何回流。

这些还没稳定时，如果拆成多个 Skill，会带来额外复杂度：

- 用户不知道该调用哪个 Skill。
- 中间产物跨 Skill 传递更麻烦。
- 每个 Skill 都要重复解释上下文。
- 版本管理会更乱。

所以第一阶段应做一个主 Skill：

```text
模型设计标准化
```

内部拆脚本、配置和阶段，但用户只感知一个入口。

### 6.2 主 Skill 内部模块

```text
模型设计标准化 Skill
  1. 模板检查
  2. Excel 解析
  3. 依赖图构建
  4. 标准库证据检索
  5. 候选生成
  6. AI 裁决
  7. 规则评审
  8. Excel 回写
  9. 待沉淀标准输出
```

用户调用仍然是一句话：

```text
用模型设计标准化处理 input/xxx.xlsx，标准库用 input/标准库.xlsx
```

### 6.3 什么时候拆成多个 Skill

满足以下任意条件，可以拆：

| 拆分条件 | 说明 |
|---|---|
| 能独立复用 | 例如“标准库治理”不只服务模型设计，也服务 DWD SQL 生成 |
| 输入输出稳定 | 模块 JSON schema 稳定，不再频繁变 |
| 用户会单独调用 | 用户经常只想做标准库体检，不想跑完整模型设计 |
| 执行周期不同 | 有的模块很重，例如代码资产全量索引，需要单独跑 |
| 权限和风险不同 | 回写 Excel 风险高，解析只读风险低 |
| 维护人员不同 | 标准库治理和模型设计评审可能由不同人负责 |

### 6.4 可能的未来 Skill 拆分

稳定后可以拆成：

1. `模型设计标准化`
   - 主入口，负责端到端处理。

2. `标准库治理`
   - 负责标准库体检、冲突检测、待沉淀项合并。

3. `模型设计解析`
   - 负责 Excel 模板检查、结构解析、依赖图构建。

4. `模型命名评审`
   - 负责字段名、表名、语义一致性评审。

5. `模型设计回写`
   - 负责把决策结果写回 Excel。

但这应该是第二阶段甚至第三阶段的拆分，不是现在。

### 6.5 评估标准

判断架构好不好，看 7 个标准：

1. 用户入口是否简单。
2. 中间产物是否可追溯。
3. 换会话是否能恢复。
4. 脚本和 AI 边界是否清楚。
5. 人工确认点是否明确。
6. 标准库能否持续沉淀。
7. 最终 Excel 是否可直接评审和开发使用。

如果拆分让这些变差，就不要拆。如果拆分让复用和治理变清楚，再拆。

## 8. 当前最重要的设计修正

本次修订后，最重要的变化有 6 条：

1. Excel 模板字段固定，不再把字段不一致当成可兼容情况。
2. “是否保留”默认是人工评审字段，AI 默认按“是”处理。
3. Excel 解析结果必须持久化为 run 目录下的 JSON/JSONL/Markdown 文件。
4. 依赖说明必须转换成图，Excel 只是输入视图，不是内部结构。
5. 标准库索引不是语义理解，只是证据检索和约束系统；语义仍由 AI 判断，人最终确认。
6. 待沉淀清单必须同时有机器 JSONL 和用户可编辑 Excel sheet，其中 Excel sheet 是主要交互方式。

## 9. 对用户 6 个问题的直接回答

### 9.1 “是否保留”怎么处理？

默认是。它是人最后评审用的字段，AI 不用它决定是否命名。模板字段固定，不固定就是问题清单项。

### 9.2 Excel 结构解析结果存不存文件？

存文件。存到本次运行目录，核心格式是 JSON 和 JSONL。不能只放上下文，否则换会话就丢失，不可审计。

### 9.3 依赖数据流对象怎么设计？

重新设计成图。Excel 只是人工输入方式，内部要变成 `nodes + edges` 的有向图，并输出 JSON、Mermaid 和人类说明。

### 9.4 标准库索引有什么意义？

索引不是理解，而是检索候选、提供证据、发现冲突和缺口。像“商品”和“MSKU”这种语义关系，索引只能提供证据，AI 必须判断，人最终确认。

### 9.5 待沉淀清单是什么？

底层是 `11_standard_gaps.jsonl`，用户交互是最终 Excel 里的 `待沉淀标准` sheet。你在 sheet 里改状态和意见，下一轮 AI 读取后生成标准库更新建议。

### 9.6 一个 Skill 还是多个 Skill？

第一阶段一个主 Skill，内部模块化。等模板、标准库、待沉淀、回写流程稳定后，再按复用性、输入输出稳定性、用户是否单独调用等标准拆成多个 Skill。

## 10. 下一步建议

下一步不建议继续写概念文档，而建议做一个“只读原型”：

1. 不回写 Excel。
2. 只解析标准库和模型设计文档。
3. 输出 run 目录。
4. 生成 `workbook_manifest.json`、`template_check.json`、`entity_fields.jsonl`、`dependency_graph.json`、`standard_gaps.jsonl`。
5. 输出一个 `run_summary.md` 给人看。

只读原型跑通后，再决定字段名自动生成和 Excel 回写。
