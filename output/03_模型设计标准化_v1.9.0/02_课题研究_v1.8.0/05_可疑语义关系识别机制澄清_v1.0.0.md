# 可疑语义关系识别机制澄清

> 本文修正上一版“脚本发现可疑关系”的表述。  
> 准确说法：脚本不发现语义关系，脚本只发现“需要 AI 语义判断的触发条件”。

---

## 1. 先回答用户的问题

用户问：

> 脚本不理解语义，怎么识别可疑关系？参考字段只含 `id`，字段描述“商品”，脚本又如何识别？

答案是：脚本不能识别“商品和 MSKU 有关系”。如果参考字段只有 `id`，字段描述只有“商品”，且没有其他上下文证据，脚本不能推出 MSKU。

脚本最多能做两件事：

1. 识别“商品”是一个需要标准化的业务术语。
2. 识别当前字段证据不足，例如字段描述是宽泛词，参考字段只是 `id`，无法确定粒度。

因此它生成的不是“商品/MSKU关系任务”，而是：

```text
字段描述“商品”语义未消歧，参考字段 id 无法提供有效粒度证据，需要 AI 结合上下文判断。
```

如果上下文仍然不足，AI 也不应该猜成 `msku_id`，而应输出“无法确定，需要人工确认”。

---

## 2. 脚本到底发现什么

脚本发现的不是语义关系，而是三类触发条件：

1. 词典触发：字段描述命中标准库或业务术语表中的敏感词。
2. 结构触发：字段行、模型粒度、表名、依赖图中出现可能相关的结构证据。
3. 证据缺口触发：字段描述太宽、参考字段太泛、缺少参考表或上下文，无法自动命名。

这三类触发条件只说明“需要进一步判断”，不说明结论是什么。

---

## 3. 词典触发：脚本只做字面命中

脚本可以维护一个“需要消歧的业务术语表”。来源包括：

- 标准库中的中文名称。
- 语义关系标准库中的术语。
- 历史待沉淀清单中频繁出现的词。
- 人工维护的高风险词，如商品、产品、SKU、MSKU、ASIN、店铺、账号、订单、费用、成本。

示例：

```json
{
  "ambiguous_terms": [
    {
      "term": "商品",
      "possible_meanings": ["product", "sku", "msku", "asin", "listing"],
      "reason": "商品是宽泛业务口语，必须结合模型粒度判断"
    },
    {
      "term": "产品",
      "possible_meanings": ["product", "spu", "sku", "msku"],
      "reason": "产品在不同系统中可能表示不同粒度"
    }
  ]
}
```

当字段描述为“商品”时，脚本只会命中：

```json
{
  "trigger_type": "dictionary",
  "term": "商品",
  "message": "字段描述命中高风险宽泛术语，需要消歧"
}
```

这不是语义理解，只是字面匹配。

---

## 4. 结构触发：脚本收集周边证据

脚本可以看字段周边是否出现更具体的粒度证据。

### 4.1 参考字段证据

| 参考字段 | 脚本能判断什么 |
|---|---|
| `msku_id` | 命中 msku 词根 |
| `product_id` | 命中 product 词根 |
| `asin` | 命中 asin 词根 |
| `id` | 过于泛化，没有粒度证据 |

所以，如果参考字段只有 `id`：

```json
{
  "reference_field_signal": "weak",
  "reason": "reference_field=id 只表示标识符，不提供商品粒度信息"
}
```

脚本不能从 `id` 推出 `msku_id`。

### 4.2 参考表证据

如果参考表是：

```text
cbebg.dws_fin_settlement_shop_msku_subject_ilu_dd
```

脚本可以字面识别表名包含 `msku`：

```json
{
  "reference_table_signal": "msku",
  "reason": "reference_table contains token msku"
}
```

如果参考表为空或只是未知表，脚本也不能推出 MSKU。

### 4.3 业务主键证据

如果同一个实体 sheet 中，业务主键字段包括：

```text
shop_id + msku_id + biz_date
```

脚本可以识别当前模型粒度含 `msku_id`：

```json
{
  "grain_signal": "msku",
  "reason": "business key contains msku_id"
}
```

如果业务主键没有填，或者只有 `id`，则没有粒度证据。

### 4.4 表名和 sheet 名证据

如果表名、sheet 名、模型名中出现：

```text
shop_msku_subject
店铺MSKU科目汇总
```

脚本能做字面命中。

如果模型名只是“商品汇总”，脚本仍然不能知道商品是什么粒度。

## 5. 证据缺口触发：这是用户例子的关键

用户举例：

```text
字段描述：商品
参考字段：id
```

这种情况脚本应触发“证据缺口”，而不是触发“商品/MSKU关系”。

输出应类似：

```json
{
  "task_id": "semantic:某模型:R10",
  "trigger_type": "evidence_gap",
  "field_desc": "商品",
  "reference_field": "id",
  "issue": "字段描述为宽泛业务术语，参考字段 id 无法提供具体粒度证据",
  "known_candidates": ["product", "sku", "msku", "asin", "listing"],
  "script_conclusion": "cannot_decide",
  "ai_question": "请结合模型名称、参考表、业务主键、依赖图判断这里的商品具体指什么；若证据不足，请标记人工确认。"
}
```

这说明脚本的责任是“发现不够确定”，不是“发现正确答案”。

---

## 6. 可疑关系任务应该如何分级

脚本生成语义任务时，应有分级，避免把所有字段都丢给 AI。

### 6.1 强证据冲突

例子：

```text
字段描述：商品ID
参考字段：msku_id
参考表：shop_msku_subject
业务主键：shop_id + msku_id + biz_date
```

脚本判断：

```text
商品是宽泛词，多个结构证据指向 MSKU。
```

任务类型：

```text
semantic_disambiguation_with_strong_context
```

AI 可以较高置信度建议 `msku_id`，但仍不能沉淀全局等价。

### 6.2 弱证据缺口

例子：

```text
字段描述：商品
参考字段：id
参考表：空
业务主键：空
```

脚本判断：

```text
只有宽泛词，没有粒度证据。
```

任务类型：

```text
semantic_disambiguation_with_insufficient_context
```

AI 应输出低置信度或人工确认，不应自动填 `msku_id`。

### 6.3 标准冲突

例子：

```text
字段描述：商品ID
参考字段：product_id
参考表：xxx_msku_xxx
业务主键：msku_id
```

脚本判断：

```text
参考字段指向 product，表名和主键指向 msku。
```

任务类型：

```text
semantic_conflict
```

AI 应解释冲突，并优先进入人工确认。

## 7. 脚本的触发逻辑示例

脚本可以使用规则打标签，但每个标签都只是证据。

```python
def detect_semantic_triggers(field):
    triggers = []

    desc_terms = match_ambiguous_terms(field.field_desc)
    if desc_terms:
        triggers.append({
            "type": "dictionary",
            "terms": desc_terms,
            "message": "字段描述命中宽泛业务术语"
        })

    ref_tokens = tokenize_field_name(field.reference_field)
    if field.reference_field in ["id", "code", "name", "type"]:
        triggers.append({
            "type": "weak_reference_field",
            "message": "参考字段过于泛化，无法提供粒度证据"
        })
    elif ref_tokens:
        triggers.append({
            "type": "reference_token",
            "tokens": ref_tokens
        })

    table_tokens = tokenize_table_name(field.reference_table)
    if table_tokens:
        triggers.append({
            "type": "reference_table_token",
            "tokens": table_tokens
        })

    grain_tokens = extract_grain_tokens(field.entity_context.business_keys)
    if grain_tokens:
        triggers.append({
            "type": "grain_token",
            "tokens": grain_tokens
        })

    return triggers
```

这段逻辑没有语义理解，只有：

- 字面匹配。
- token 提取。
- 泛化字段识别。
- 证据打包。

## 8. AI 在不同证据条件下怎么处理

### 8.1 证据强时

输入：

```json
{
  "field_desc": "商品ID",
  "reference_field": "msku_id",
  "reference_table_tokens": ["shop", "msku", "subject"],
  "grain_tokens": ["shop_id", "msku_id", "biz_date"]
}
```

AI 合理输出：

```text
当前上下文中“商品ID”大概率指 MSKU 粒度，推荐字段名 msku_id；
但商品是宽泛词，建议字段描述改为“MSKU维表ID”，并进入待沉淀标准。
```

### 8.2 证据弱时

输入：

```json
{
  "field_desc": "商品",
  "reference_field": "id",
  "reference_table": "",
  "grain_tokens": []
}
```

AI 合理输出：

```text
无法判断商品具体指 product、sku、msku、asin 还是 listing。
不建议自动生成字段名。
请补充参考库表、业务主键或明确字段描述。
```

### 8.3 证据冲突时

输入：

```json
{
  "field_desc": "商品ID",
  "reference_field": "product_id",
  "reference_table_tokens": ["msku"],
  "grain_tokens": ["msku_id"]
}
```

AI 合理输出：

```text
存在 product 与 msku 冲突。若该字段表示主数据产品，应使用 product_id；
若该字段表示利润核算粒度，应使用 msku_id 并修正字段描述。
本字段需人工确认。
```

## 9. 重新定义“脚本发现可疑关系”

上一版表述：

```text
脚本发现字段描述和参考字段存在词根冲突。
```

更准确的表述应为：

```text
脚本基于字面词典、字段名 token、表名 token、业务主键、依赖图和证据缺口，发现当前字段存在语义不确定性或多候选冲突，从而生成 AI 语义判断任务。
```

也就是说：

- 脚本发现“不确定”。
- AI 判断“可能是什么”。
- 用户确认“标准是什么”。

## 10. 对“参考字段只有 id”的最终处理规则

当字段描述为“商品”，参考字段只有 `id`：

### 10.1 如果没有其他上下文

处理：

- 不自动生成 `msku_id`。
- 输出 blocker 或 warning。
- 要求补充字段描述或参考表。

评审提示：

```text
字段描述“商品”过宽，参考字段 id 无法提供粒度信息。请确认该字段表示 product、sku、msku、asin、listing 还是其他实体。
```

### 10.2 如果有强上下文

例如同 sheet 已经有业务主键 `shop_id + msku_id + biz_date`，参考表或表名也包含 `msku`。

处理：

- AI 可以推荐 `msku_id`。
- 置信度最多是 medium/high，不是 absolute。
- 必须建议字段描述改为更准确的“MSKU维表ID”。
- 进入待沉淀标准或评审清单。

### 10.3 如果上下文冲突

处理：

- 不自动回写。
- 进入 blocker。
- 要求人确认。

## 11. 关键边界一句话

脚本不是语义裁判，它是证据秘书。

它负责说：

```text
这里出现了宽泛词、弱参考字段、多候选或上下文冲突。
```

AI 负责说：

```text
基于这些证据，我认为当前上下文更可能是什么，但哪里仍需要确认。
```

用户和标准库负责说：

```text
这个关系是否成为企业标准。
```

如果只有“字段描述=商品，参考字段=id”，脚本和 AI 都不应该把它自动变成 MSKU。
