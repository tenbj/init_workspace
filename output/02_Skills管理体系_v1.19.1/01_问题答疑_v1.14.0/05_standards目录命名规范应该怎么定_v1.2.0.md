# `.system/standards/` 目录的命名规范应该怎么定？

> 版本：v1.2.0
> 日期：2026-05-09（v1.1.0 补充版本号分析；v1.2.0 更新最终推荐为淘汰法）

---

## 问题起源

`03_Skills管理标准_v1.0.0.md` 迁入 `.system/standards/` 后命名不一致，但在讨论"该改成什么"之前，需要先回答一个更根本的问题：**`.system/standards/` 目录下的文件，到底应该遵循什么命名规范？**

现有规则只说了两件事：
1. 文件名固定（《工作区命名规范.md》第 114 行）
2. 不按语义版本改 live 文件名（第 116 行）

但没有定义**新增标准文件时的命名模式**。现有三个文件的命名是"历史形成的"，而非"规范驱动的"。

---

## 现状分析：现有文件的命名隐含了什么模式？

| 文件名 | 主题 | 内容类型 | 语言 |
|--------|------|---------|------|
| `workspace-spec.json` | workspace（工作区） | spec（规格） | 英文 |
| `工作区骨架规格.md` | 工作区 | 骨架规格 | 中文 |
| `工作区命名规范.md` | 工作区 | 命名规范 | 中文 |

观察到的隐含模式：

1. **JSON 用英文，MD 用中文**——这个有道理：JSON 是机器读的，MD 是人读的
2. **MD 文件的结构是 `{主题}{文档类型}.md`**——"工作区"是主题，"骨架规格"/"命名规范"是文档类型
3. **现有 MD 文件的主题恰好都是"工作区"**——但这只是因为目前只有工作区级别的标准
4. **无编号、无版本号**——已确认的规则

---

## 需要回答的两个前置问题

### 前置问题 1：`.system/standards/` 的收录范围是什么？

这个目录应该放什么？有三种理解：

| 理解 | 说明 | 当前实际 | 未来预期 |
|------|------|---------|---------|
| **窄义**：只放工作区基础设施标准 | 骨架、命名、spec 这类定义工作区本身结构的文件 | ✅ 完全匹配 | Skills 标准不该放这里 |
| **中义**：放所有达到 SSOT 地位的标准 | 凡是需要被多处引用、作为唯一事实源的标准 | ✅ 匹配 | Skills 标准可以放这里 |
| **广义**：放所有治理标准 | 包括流程规范、操作手册等 | ❌ 过宽 | 会膨胀失控 |

**我的判断**：应该取**中义**。理由：

- Skills 管理标准确实是 SSOT——它定义了 Skill 的域分类、编号、命名、生命周期规则，多个 Skill 的 YAML frontmatter 和脚本都需要引用它
- 如果只取窄义，Skills 标准放回 `output/` 子项目里，会导致"标准散落在子项目中"的问题，跟 `workspace-spec.json` 放在子项目里一样不合理
- 但必须有收录门槛——不是所有文档都能进 `.system/standards/`

**建议的收录门槛**：
- 被多个 Skill/Rule/脚本引用的规范性文件
- 定义了"怎么做"的唯一权威来源
- 内容稳定，不会频繁变更（草案阶段不放）

### 前置问题 2：文件数量的增长预期？

当前 3 个文件。未来可能新增的标准：

| 潜在标准 | 当前状态 | 是否属于 SSOT |
|---------|---------|-------------|
| Skills 管理标准 | 已有草案 | ✅ 是 |
| 记忆管理标准 | 规则散落在 memory-rules.md 中 | 可能 |
| 版本控制标准 | 规则散落在 version-control-rules.md 中 | 可能 |

预计中期（6~12 个月）文件数量：**4~7 个**。不会爆炸式增长，因为标准本身就应该少而精。

## 四个命名方案对比

### 方案 A：沿用现有模式——`{主题}{文档类型}.md`

```text
workspace-spec.json          ← 不变
工作区骨架规格.md             ← 不变
工作区命名规范.md             ← 不变
Skills管理标准.md             ← 新增
```

规则定义：
- JSON 文件用英文小写加连字符（`workspace-spec.json`）
- MD 文件用中文，格式 `{主题}{文档类型}.md`
- 特定英文术语保留原文（如 Skills、DWD）
- 无编号、无版本号

**优点**：
- 最小改动，不动现有文件
- 简单直观，4~7 个文件完全够用
- 与 `.system` "核心骨架、名称固定"的定位一致

**缺点**：
- 没有排序机制，文件按字典序排列（中英混排，顺序可能不直观）
- 主题边界靠"自然语言"区分，不够机械化

---

### 方案 B：带领域前缀——`{领域}-{文档类型}.md`

```text
workspace-spec.json          ← 不变
workspace-骨架规格.md         ← 改名
workspace-命名规范.md         ← 改名
skills-管理标准.md            ← 新增
```

规则定义：
- 统一用 `{英文领域小写}-{中文文档类型}.md`
- 同领域文件自动按字典序聚拢

**优点**：
- 领域分组明确，文件系统里天然排在一起
- 命名机械化，新增文件不需要纠结

**缺点**：
- **需要改现有两个文件名**，牵连 workspace-spec.json 内部引用、Rules 引用、体检脚本等
- 英文-中文拼接风格不统一（`workspace-骨架规格.md` 读起来别扭）
- 改动成本高，收益不够大

---

### 方案 C：编号排序——`{两位编号}_{主题}.md`

```text
workspace-spec.json          ← 不变（机器文件不编号）
01_工作区骨架规格.md          ← 改名
02_工作区命名规范.md          ← 改名
03_Skills管理标准.md          ← 新增
```

规则定义：
- JSON 机器文件不编号
- MD 人读标准按加入顺序编号，`{两位编号}_{主题}.md`
- 无版本号

**优点**：
- 有明确排序
- 编号给了稳定性（按加入顺序，不重排）

**缺点**：
- **需要改现有两个文件名**，同上改动成本
- 与现有标准 "`.system` 名称固定" 矛盾——现有规则明确列出了不带编号的文件名
- 编号暗示"可增长的集合"，但 `.system/standards/` 应该是精简且稳定的
- 编号在 4~7 个文件时收益微小（肉眼就能扫完）

---

### 方案 D：维持现有文件不动 + 新增文件遵循自然命名

```text
workspace-spec.json          ← 不变
工作区骨架规格.md             ← 不变
工作区命名规范.md             ← 不变
Skills管理标准.md             ← 新增（去编号、去版本号）
```

规则定义：
- 现有文件名为"历史确认名"，不改
- 新增文件遵循：中文为主 + 特定术语保留英文 + 无编号 + 无版本号
- 版本信息写在文件头部元数据中
- 文件名应当自描述：读文件名就知道这个标准管什么

**本质上方案 D = 方案 A**。区别是方案 A 试图从现有文件中"提取"一个通用模式并声明为规则，而方案 D 承认"现有命名就是现有命名"，只约束新增文件。

---

## 对比总结

| 维度 | A（自然命名） | B（领域前缀） | C（编号排序） | D（不动+约束新增） |
|------|:---:|:---:|:---:|:---:|
| 改动成本 | 无 | 高（改2个+全引用链） | 高（同B） | 无 |
| 排序能力 | 无 | 领域聚拢 | 数字排序 | 无 |
| 可读性 | 好 | 中（英中拼接） | 好 | 好 |
| 与现有规则兼容 | ✅ | ❌ 需改规则 | ❌ 与"名称固定"矛盾 | ✅ |
| 未来扩展性 | 4~7个够用 | 好 | 好 | 4~7个够用 |
| 实施复杂度 | 低 | 高 | 高 | 低 |

## 为什么四个方案都不带版本号？（v1.1.0 补充）

用户追问：所有方案好像都没考虑文件名带版本号，为什么？

### 不带版本号的原因

有一条已定义的规则和一个实操代价：

**规则依据**：

> `.system` 不按语义版本改 live 文件名，不在当前区堆 `_v*` 文件。
> ——《工作区命名规范.md》第 116 行

**实操代价——引用链地狱**：

如果标准文件名带版本号，比如 `Skills管理标准_v1.0.0.md`，那么每次 bump 版本时，必须同步更新：

| 需要更新的位置 | 具体引用 |
|--------------|---------|
| `workspace-spec.json` → `overwriteLayer.standards` | 文件名字符串 |
| `workspace-spec.json` → `systemCore.files` | 文件路径 |
| `工作区骨架规格.md` | 文件列表 |
| `工作区命名规范.md` | `.system` 章节文件列表 |
| `framework-check.ps1` | 体检脚本中的文件名检查 |
| 任何引用该标准的 Rule/Skill | 路径或文件名引用 |

**这跟 Skill 文件夹带版本号导致的问题完全一样**——你之前在 [skillRegistry 讨论](./03_skillRegistry是什么_v1.0.0.md)中就遇到了：文件夹每次 bump 版本号，所有引用该路径的脚本和配置都要跟着改。

不带版本号时，这些引用全部保持稳定，永远不需要更新。

### 那版本信息放哪里？

现有标准文件已经在用的做法：

| 文件 | 版本信息位置 |
|------|------------|
| `workspace-spec.json` | 文件内部 `"version": "1.3.0"` |
| `工作区骨架规格.md` | 文件头 `> 版本：1.2.0` |
| `工作区命名规范.md` | 文件头 `> 版本：1.2.0` |

三个文件都把版本写在**文件内部**，不在文件名中。历史版本由 FOLDER 备份机制保留（整个 `standards/` 文件夹快照到 `.history/.system/standards_{时间戳}/`）。

### 但如果就是想带版本号呢？

如果你认为标准文件的版本可见性很重要（一打开文件夹就知道每个标准是哪个版本），也不是不行。需要承担的代价：

1. **每次 bump 都改文件名**——操作本身不难（备份脚本可以扩展）
2. **每次 bump 都更新引用链**——这是真正的代价，至少 5~6 处联动更新
3. **需要修改现有规则**——把"`.system` 不按语义版本改 live 文件名"这条规则取消或加例外
4. **与其他 `.system` 文件的风格不一致**——其他两个 MD 文件和 JSON 文件都不带版本号

### 收益有多大？

坦率地说，**不大**。因为：

- 标准文件数量少（4~7个），不像 `output/` 有几十个子项目需要靠版本号区分快照
- 标准更新频率低，不像子项目文件每天改好几次
- 打开文件看头两行就知道版本号，不需要靠文件名
- 备份机制已经负责历史追溯

### 结论

不带版本号不是"忘了考虑"，而是**有意为之**——引用链稳定性 > 文件名可见性。在 `.system/standards/` 这个特定场景下，代价大于收益。

但这个决定最终取决于你对"引用链稳定"和"版本一眼可见"这两个价值哪个更重要。

## 最终推荐：方案 A（v1.2.0 更新）

### 一句话理由

**B 和 C 要改现有文件，代价大于收益；A 和 D 本质相同，不需要改。** 在 4~7 个文件的规模下，选最简单的就是最好的。

### 淘汰法

| 方案 | 淘汰理由 |
|------|---------|
| **B（领域前缀）** | 需要改 2 个现有文件名 → 触发引用链更新（workspace-spec.json 2 处、骨架规格、命名规范、体检脚本）。英中拼接（`workspace-骨架规格.md`）读起来别扭。改动成本 >> 领域分组的收益。 |
| **C（编号排序）** | 同上改动成本。且编号暗示"可增长的集合"，与 `.system` "核心骨架、名称固定"的定位矛盾。4~7 个文件肉眼就能扫完，不需要编号辅助。 |
| **D（不动+约束新增）** | 不淘汰，但它 = A。D 只是 A 的保守版表述。 |

**存活者：A。**

### 方案 A 的具体规则

```
.system/standards/ 文件命名规范：
├── JSON 机器文件：英文小写 + 连字符（如 workspace-spec.json）
├── MD 人读标准：{主题描述}.md
│   ├── 中文为主，特定英文术语保留原文（Skills、DWD 等）
│   ├── 文件名应自描述——读文件名就知道标准管什么
│   ├── 无编号
│   └── 无版本号（版本写在文件头 > 版本：x.y.z）
└── 收录门槛：达到 SSOT 地位、被多处引用、内容稳定
```

### 最终目录预览

```text
.system/standards/
├── workspace-spec.json      ← 机器可读 SSOT（不变）
├── 工作区骨架规格.md         ← 骨架人读标准（不变）
├── 工作区命名规范.md         ← 命名人读标准（不变）
└── Skills管理标准.md         ← 新增（去掉编号和版本号）
```

### 为什么不怕"没排序"？

`.system/standards/` 的定位是**少而精的 SSOT 集合**，不是 `output/` 那样的开放式增长集合。标准文件增加到 7 个以上的可能性很低——如果真到了那一步，说明标准本身需要合并而非继续分拆。

如果未来确实超过 10 个（几乎不可能），再引入领域前缀也不迟——到那时只影响新增文件，不需要改已有文件。
