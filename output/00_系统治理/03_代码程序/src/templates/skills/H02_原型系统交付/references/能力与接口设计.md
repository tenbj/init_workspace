# 能力与接口设计

H02 的目标是把原型背后的业务能力做成系统能力，再让用户和 AI 都能调用。

## 能力分层

推荐分成四层：

| 层 | 作用 | 示例 |
|---|---|---|
| 页面 | 给人使用的交互界面 | 列表、详情、提交表单、状态筛选 |
| 后端 API | 系统稳定能力边界 | 创建批次、登记对象、提交结果、查询活动 |
| 数据库 | 状态与证据持久化 | 当前状态、事件流水、幂等请求、审计记录 |
| MCP | 给 AI 使用的工具目录 | list、get、create、submit、verify |

MCP 通常调用后端 API，不直接绕过系统写库。这样页面、人、AI 使用同一套业务规则。

## API 粒度

不要按“一个任务一个 API”设计。先找稳定业务对象和操作：

- 资源：用户、批次、模型、订单、指标、证据、任务、文件等。
- 操作：查询列表、读取详情、创建、更新状态、提交结果、上传证据、查看活动。
- 约束：幂等、版本、权限、状态机、范围校验。

同一操作可以服务很多 AI 任务。例如 `submit_result` 可以提交人工结果、AI 结果或外部系统结果，只要参数和证据满足合同。

## 数据库设计

最小可用结构：

- 当前状态表：面向页面和查询。
- 事件流水表：记录谁在何时做了什么。
- 幂等请求表或字段：保存 `request_id` 和指纹，支持网络重试。
- 证据引用：保存路径、标签和来源，不把大文件强行塞进状态字段。

公开包只放合成数据。真实数据库连接只能通过环境变量或用户授权的本地配置注入进程。

## MCP 工具设计

工具名应该贴近系统操作，而不是贴近一次性任务描述。

推荐工具类型：

- `get_system_status`
- `list_*`
- `get_*`
- `create_*`
- `register_*`
- `submit_*`
- `list_activity`

每个工具必须说明：

- 何时使用
- 输入字段
- 返回字段
- 是否有副作用
- 前置步骤
- 409、422、503 等异常处理

提交类工具必须支持：

- `request_id` 幂等
- `expected_version` 或等价并发控制
- 证据必填规则
- 失败不声称成功

## 复用现有架构

如果输入项目已有框架、数据库访问层、路由规范或测试方式，优先沿用。只有在现有结构无法承载页面、API、数据库和 MCP 时，再说明原因并引入新框架。

## 边界

- MCP 暴露的是调用系统能力，不是绕过系统的脚本后门。
- API 可以供页面、Python 示例、AI 和其他系统共用。
- 数据库 env、token、cookie、登录态不得写入示例、文档或 ZIP。
