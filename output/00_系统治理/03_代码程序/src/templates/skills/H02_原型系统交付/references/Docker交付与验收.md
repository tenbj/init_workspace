# Docker交付与验收

## 范围与默认行为

首次系统交付和已有系统迭代默认交付、维护并真实验证Docker部署。用户明确仅交原型、明确排除Docker时遵守范围，在合同docker.exclusion记录原话与原因；引擎不可用、拉取失败、时间不足或项目以前没有Docker不属于已完成或自动豁免。先完成可做的实现，报告具体阻塞并保持draft。

本分册规定验收结果，不固定语言、目录、端口、数据库品牌或容器数量。复用现有架构：内置HTTP MCP随应用，已有独立MCP按运行边界拆分；stdio兼容入口不能靠暴露端口变成HTTP服务。网页、API、MCP复用业务规则。双图作为已验收HTML随镜像提供，保留既有路由，避免覆盖框架的/docs；公开接入指南、OAuth路由、工具清单和Skill下载如有也须入镜像。

## 开始前

1. 读取项目真实启动入口、依赖锁、配置加载、路由、数据库初始化/迁移、可写目录、认证代理和当前部署。已有项目增量维护，保留用户改动；不重新初始化覆盖合同。
2. 运行`python <H02>/scripts/docker_preflight.py --report <本轮证据目录>/docker-preflight.json`。该工具只读CLI、引擎和Compose。预检成功不代表构建/部署成功。
3. 记录目标OS/架构、CPU/内存/磁盘需求、镜像来源和可达性。拉取、安装依赖或构建失败时先区分DNS、代理、镜像站、版本不可用与代码错误；不全局改Docker镜像源、context或关闭TLS来绕过问题。
4. 为每次演练创建唯一Compose项目名（例如h02test-加随机后缀）、独立卷/网络、仅绑定127.0.0.1的空闲或动态端口。先记录已有容器，确认测试数据库与真实库隔离。测试env使用独立临时凭据；不读取生产秘密填入夹具。
5. 启动、构建与拉取均设置合理时限并记录失败输出。Windows的Docker CLI可能派生Compose子进程；超时只终止本次命令树，再核对本项目资源，不能全局结束docker进程或将超时后遗留的启动任务当成功。首次镜像展开与数据库初始化耗时应与健康等待区分。
6. 隔离演练同样要核算资源。同一宿主机默认串行执行多项目Docker验收，一次仅保留一套活跃测试环境；只有资源预算已确认充足且任务明确需要时才并行。测试覆盖文件为应用和数据库分别设置合理CPU、内存与连接上限，所有测试阶段（含仅应用、旧版本、恢复阶段）均保留这些覆盖。可在同一测试实例的新库验证逻辑恢复，报告明确同实例/跨实例边界；不能照搬测试参数到生产，也不能停止无关服务换取通过。延长超时不能替代资源与故障诊断。
7. 测试容器显式使用restart: "no"，不得继承正式Compose的自动重启策略。成功、失败、超时和取消（含KeyboardInterrupt/SystemExit）均经finally尝试清理本次精确项目；超时或取消须先终止自有命令子进程树并有界回收，再执行资源清理，保留原取消异常，finally不得用return吞掉异常。日志收集、代理退出和Compose清理各自处理异常，任何一步失败不能跳过其他清理或掩盖最初错误；down之后仍须按本次精确Compose项目标签分别回读容器、卷、网络，无法确认清零或清理失败不得记为通过。默认不保留运行中的失败环境；需要诊断时先保存私有日志。引擎不可用导致清理失败，登记精确项目、容器和私有配置路径，恢复后先核对归属再清理，不能叠加新测试环境。
8. 开始和结束核对已有生产服务及本次资源归属；停止测试不代表删除生产数据。用户要求停用无用测试时，优先停止或移除已核实的测试容器；卷和诊断材料按明确归属及任务清理策略处理。禁止全局prune、按模糊名称批量删除或把所有test前缀都当作本次资源。

## 实现交付

- 提供Dockerfile、.dockerignore、Compose配置、无秘密环境变量模板、中文部署/升级/恢复说明。已有MySQL等外部服务继续可用，新环境一体部署按需提供独立Compose覆盖文件，实际支持的每种组合都要验收。Compose插值文件与容器env_file有不同作用，文档明确命令和配置优先级。
- 基础镜像与依赖锁定可复核的版本/摘要；按目标平台安装，不复制宿主机node_modules或venv。非root运行及卷写权限必须实测，含既有卷升级后的UID/GID。构建只COPY运行必需文件，排除.env、密钥、runtime、真实数据、.git和私有备份；不能将这些文件先COPY再删除，旧层仍会保留。
- 数据库驱动必须支持目标服务的认证机制，不能为兼容旧驱动降低服务端认证；镜像层扫描须识别压缩层，不能只匹配导出包的压缩字节。
- 只固定顶层包不等于依赖锁定。保留完整依赖锁并执行依赖一致性检查、应用导入/编译检查；MCP SDK和数据校验库等关键组合要真实启动验证。构建安装成功不证明运行兼容，不能把临时解决版本冲突的无约束升级当最终方案。
- 容器前台运行真实服务，使用exec形式启动以传递停止信号；不要运行创建后台进程后退出的本机管理脚本。应用监听容器网卡，宿主机端口公开范围另行决定。日志至stdout/stderr并轮转。
- 明确数据归属：业务库、附件、用户保存配置等可变数据持久化；凭据用运行时环境、私有文件只读挂载或项目支持的secret机制。Windows绝对路径、CA文件路径和localhost含义必须重新适配。镜像更新不覆盖业务数据；持久卷不等于备份。
- 静态应用文件、双图和首次建库脚本优先随镜像交付，减少依赖宿主机工作目录。必须使用bind mount时，先实测目标宿主机路径共享、权限和文件可达性；出现创建容器挂起先用最小挂载探针诊断，不反复重启整个Docker环境。
- 健康检查区分进程存活、依赖就绪和业务可用；设置启动宽限、有界重试及失败信息。依赖健康条件不代替应用重连，unhealthy标记不自动触发Docker重启。配置合适的重启策略，确认引擎/宿主机重启边界；不得宣称因此获得高可用。
- 数据库首次初始化可能明显慢于重启；健康探针总窗口必须覆盖建库、授权、初始化脚本和正式监听。MySQL等具有临时初始化服务时，按应用实际TCP入口验证，不能只检查socket或进程。Compose整体等待与探针重试窗口要一致，保留初始化失败和慢启动的区别。
- 初始化、迁移和服务启动分开。数据库健康但未初始化时不能判成功；新库检查、应用身份、权限、迁移版本须明确。不得每次启动重跑演示seed或清理脚本。已有系统迁移按I02备份、停写、校验；Docker化本身不授权变更真实数据库。
- 代理入口如有须覆盖页面、API、MCP、OAuth发现/授权、文档与下载；配置准确的公开URL、Host/Origin、可信代理、Cookie和流式响应。默认保持同源路径；不把容器内部主机名给外部AI客户端。
- 首次先验证一个应用实例；多副本、共享文件、MCP会话和数据库并发另按实际需求验收。不为了模板引入Redis或强拆服务。

## 实机验收矩阵

在项目内提供可重复执行的验收脚本或命令清单，真实运行以下步骤。可按技术栈用SDK、浏览器和数据库工具，不用假MCP或HTTP 200代替协议验证。生产只读验收与隔离写入演练分开。

| 报告check名称 | 必须取得的观测 |
|---|---|
| compose_config | 实际选择的Compose组合解析成功；只在内存检查解析结果，避免输出已插值秘密 |
| build | 从交付构建上下文构建成功；记录基础镜像来源与实际应用镜像ID；首次至少一次无业务缓存的干净构建 |
| startup | 冷启动所有必需依赖，初始化完成且在期限内就绪；记录服务和健康状态 |
| api | 核心业务只读及隔离写入回读，业务校验/幂等/版本冲突按项目测试；不只health |
| mcp | 真实SDK握手、工具发现、认证工具调用及结果；固定SDK与AI自主任务分开 |
| auth | 无/错误凭据被拒绝；有效只读凭据成功，适用时验证越权与OAuth链路 |
| diagrams | 从容器原路由取得两个实际HTML，内容指纹与本轮产物一致；双图浏览器交互仍按D04/G02独立验收 |
| recreate | 写入合成记录/用户配置后重建应用及可重建存储容器，记录与配置仍一致 |
| upgrade | 从已知旧版本切换目标版本，确认镜像/业务版本及记录不丢；迁移先在隔离库演练 |
| rollback | 故意失败或已知兼容场景回退到明确旧镜像并验证业务；有不兼容迁移时演练兼容恢复或前向修复，不盲目回滚库 |
| backup_restore | 创建一致性备份，在独立卷/库恢复并比对合成记录；禁止覆盖生产来做演示 |
| failure_recovery | 至少注入依赖延迟/中断或错误配置，验证检测、非成功结果及恢复；不能仅重试直到绿而丢失失败阶段 |
| secrets | 检查构建上下文、镜像配置/history/文件层及公开产物；不输出秘密，删除后的旧层也要覆盖 |
| cleanup | 仅清理本次归属的测试容器/网络/卷，核对既有服务未变；禁止全局prune或不带项目名的down |

无持久状态应用仅允许recreate/backup_restore标not_applicable并写依据，其余必要阶段不能略过。不同部署组合分别保留报告；公开HTTPS或外部依赖无法验证时明确该部署模式未验证，不把本机报告推广到它。

系统浏览器验收必须包含实际Docker入口的主页面、核心静态资源、登录态与关键数据读写；不能只验证原本机进程。已有browser检查可复用同一份真实浏览器证据并在Docker的startup/api观测中引用。双图仍按D04/G02完成语义和交互检查。纯API合成回归没有业务前端，其报告不能代替此项。

## 证据合同与验收工具

`scripts/docker_contract.py`由validate_project调用，只核对文件和证据，不启动或删除容器，不替执行者生成成功结论。参考`assets/docker-report.example.json`字段，真实执行后填写。至少记录：

- 合同docker：required、mcp_mode（embedded/separate/stdio）、stateful、compose_files、dockerfiles、ignore_files、guide、inputs、services、evidence。
- inputs显式覆盖实际应用源码、依赖锁、Docker构建文件、Compose覆盖文件、双图及所有发布资源；不得只登记Dockerfile。使用snapshot(project_root, inputs)生成排序的文件SHA256清单。避免把报告自身或runtime作为输入。
- 报告：passed、environment=isolated、delivery_id、唯一run_id、带时区的started_at/finished_at、compose_project、mcp_mode、inputs、实际运行服务images（service/id），各阶段checks（name/status/非空observations）。敏感原始日志只在私有处保存，公开观测用摘要和非敏感标识。
- 项目checks增加docker并引用同一报告；缺文件、失败步骤、镜像ID缺失、来源变化、旧delivery_id均阻止ready。证据只能在实际执行成功后填写。测试夹具的报告不能复制为业务系统通过。
- 多组合验收：docker登记主要交付组合，docker.variants可登记额外组合，每项是完整docker配置且required=true、evidence独立，不允许嵌套；验证器逐个执行同一门槛。切换数据库/认证/拓扑属于不同组合，需要单独证据。

首次原型骨架仍为draft。用户明确排除Docker时，docker={required:false, exclusion:{basis:"user_instruction", instruction:"用户原话", reason:"本次范围"}}；不能由AI用环境失败自造豁免。旧项目首次采用新版H02补合同和实测，不因旧合同ready跳过。

## 更新与恢复

构建前锁定本轮输入，使用可回退的版本标签和实际镜像ID；不要把latest当作回滚依据。修改代码、依赖、Docker配置或图示后重跑受影响运行验收并更新快照。例行小改不需要改容器拓扑，但仍需验证当前镜像能启动与关键能力连通；不能复用前一轮报告冒充新证据。

发现失败先保留测试报告，修复后新建run_id重验；结果未知时先核查容器/版本/数据状态，不无条件重跑迁移。正式系统更新走I02，停止错误范围之外的服务、删卷、恢复旧备份覆盖新数据均不属于默认动作。首次无生产目标可完成隔离Docker交付，并明确未线上部署。

交给I02时明确目标服务管理器、机器/环境、Compose项目名与覆盖文件、已验证镜像ID、卷与数据源、公开入口、迁移版本和回退目标。原有服务由NSSM等托管时，新增Docker交付物不自动等于已切换生产；本次确需切换时沿用已有授权，先识别并停止冲突写入者、验证数据与端口，再切换流量。Docker目标使用其Compose部署方式，不照搬Windows本机启动命令，也不能让新旧实例未经设计同时写同一份文件数据。

## Skill自身回归

`scripts/test_docker_contract.py`验证缺失/失败/过期证据不能误过。`scripts/test_docker_runtime.py --output-dir <新的隔离输出目录>`进行真实Docker演练，只使用合成夹具、随机凭据与新建资源。该演练用于验证本Skill工具链，不代替生成系统自己的业务、双图语义或生产验收。演练默认允许900秒首次建库等待，可用--startup-timeout在60至1800秒内调整；报告保留上限，不无限重试。修复后的重复演练可显式用--reuse-build-cache，报告如实登记，不能冒称干净构建。镜像探针支持未压缩/gzip层；发现zstd层拒绝通过，须先补受验证的解码器。

本地Docker曾通过只代表已测版本和场景。后续每个系统均须现场执行上述流程，不能承诺所有未知环境永不失败；可靠性来自提前发现问题、保留数据并验证恢复。
