# 发布流程

## 默认顺序

1. 更新 00 初始化程序：
   - 定位当前 `output/00_系统治理/03_代码程序/src`
   - 运行 `scripts/update_init_program.ps1`
   - 以当前 live 工作区为权威源，全量刷新 `src/templates` 下的入口文件、Rules、Skills 和 Standards
   - 不做人工文件/目录结构比对，不零散复制；目标模板目录按脚本规则替换成最新
   - 按发布目标同步 `SKELETON_VERSION`、`build.ps1` 的 `$Version` 和 `SSO_SPEC_VERSION`
   - 记录 `.b09_update_manifest.json`

2. 重封装 exe：
   - 确认第 1 步脚本成功并生成 `.b09_update_manifest.json`
   - 运行 `scripts/build_init_exe.ps1`
   - 该脚本默认检查更新清单；缺少清单或版本不一致时停止构建
   - 脚本调用对应 `src/build.ps1` 重新封装 `dist/初始化工作区_v*.exe`
   - 记录 exe 文件名、大小、SHA256 和构建结果
   - `*.exe` 只作为 GitHub Release 附件，不作为普通 Git 文件提交

3. 识别发布目标：
   - GitHub 仓库，例如 `owner/repo`
   - 公开版本号，例如 `v2.8.0`
   - 主交付物，例如 `初始化工作区_v2.8.0.exe`
   - 是否需要创建 Release、上传附件、推送 tag

4. 读取本地状态：
   - `git status --short`
   - `git remote -v`
   - `git branch --show-current`
   - `git tag --list`
   - 最新 `output/*/版本记录.md`

5. 维护发布说明：
   - 更新 `CHANGELOG.md`
   - 如项目使用 notes 文件，同步 `.github/release-notes/vX.Y.Z.md`
   - 保证 README 当前版本、tag、Release 标题、资产文件名一致

6. 构建与校验：
   - 确认第 1 步更新清单存在
   - 确认第 2 步已完成主要交付物构建
   - 复算 SHA256 并与第 2 步记录一致
   - 执行 B01
   - 执行敏感信息与忽略规则检查

7. Git 操作：
   - 暂存应提交文件
   - 创建发布准备提交
   - 创建 tag
   - 推送分支与 tag

8. GitHub Release：
   - 使用 `gh release create`
   - 上传 Release 附件
   - 写入 Release Notes
   - 记录 Release URL 与资产校验信息

9. 收尾：
   - 复查 `gh release view`
   - 写入 B03 记忆
   - 如本轮是长任务，关闭 B08 任务进度

## 授权规则

- 优先使用 GitHub CLI 浏览器授权：`gh auth login`。
- 不要求用户把 token 粘贴到聊天窗口。
- 如用户未登录，停止在“可执行命令清单”阶段，不代替用户输入凭据。

## 异常边界

| 情况 | 处理 |
|------|------|
| 工作区有用户未说明的改动 | 不覆盖、不重置，先区分本轮相关与无关 |
| tag 已存在 | 不强删 tag；先报告对应 commit 和 Release 状态 |
| Release 已存在 | 优先查看并询问是否更新 Release，而不是直接重建 |
| 敏感扫描失败 | 停止发布，先修复或从暂存区移除风险文件 |
| 远端落后或冲突 | 不强推；先获取状态并说明需要人工决策 |

## 发布后必须记录

- 仓库 URL
- commit SHA
- tag
- Release URL
- 附件名和大小
- SHA256
- B01/构建/敏感扫描结果
