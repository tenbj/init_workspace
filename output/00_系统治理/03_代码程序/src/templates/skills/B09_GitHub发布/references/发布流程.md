# 发布流程

## 1. 确认范围并建立本次发布分支

“发布”的完整默认语义见SKILL.md；用户已明确限定时只执行对应阶段。

- 用B11识别真实仓库、远端、最新目标基线、当前分支、脏改动和标签；多系统分别建任务清单，不能共用版本、提交列表或证据。
- 本次新发布任务建新工作分支；续做同一次发布沿用已记录分支。这里的发布工作分支不是受保护的长期release基线。
- 从确认的基线组织正式变更，保留原始分支与未提交内容的恢复点，不将隔离旧开发自动带入。已有未公开提交如需净化，在独立分支保留事项边界；不能直接改写公开历史或用reset/clean丢弃改动。
- 开始即记录仓库、基线SHA、工作分支、正式范围、排除范围、拟提交事项、版本和交付物。版本按仓库已有策略及真实变更确定；版本冲突先查远端，不覆盖既有Tag/Release。

## 2. 按项目类型构建和验证

### 核心骨架项目

仅发布核心骨架项目时执行：

1. 定位初始化程序源码，运行`scripts/update_init_program.ps1`。以live工作区为权威源，按注册表刷新模板、同步版本并记录`.b09_update_manifest.json`；不手工零散复制。
2. 确认更新成功后运行`scripts/build_init_exe.ps1`，记录`.b09_build_manifest.json`、exe路径、大小和SHA256；exe仅作为Release附件。

### 普通应用/系统

执行该仓库真实支持的构建、测试与交付流程。**不运行上面的初始化程序更新或exe重封装，也不要求对应清单。** 不能仅凭项目在核心骨架工作区下就归为核心骨架项目。

H02交付的系统按H02核对有效测试、当前源码、双图、合同、隔离Docker证据和发布包；脚本治理规则归H02维护。运行/迁移工具与测试区分，私有资料不入包。只改文档等低影响事项按实际改动验证，不机械执行无关系统重建。

## 3. 分类提交后统一推送

1. 更新CHANGELOG和Release Notes，描述用户可见正式迭代；内部记忆、备份日志不代替用户发布说明。
2. 按Git标准的独立事项拆分中文提交；同一功能实现、迁移、测试、说明保持完整，不逐文件拆分。提交保护与暂存边界按B11执行。
3. 完成本次所有事项和必要发布准备提交，记录每条SHA及验证；检查所有待公开提交/blob和资产，不只扫描最终工作树。
4. 统一推送工作分支，创建PR，描述最终改动与验证。创建PR后按宿主能力附加到当前任务。CI失败先在同分支修复并增量推送，不绕过检查。

## 4. PR合并、Tag、Release

1. 回读最新目标基线和PR检查；用merge commit保留分类提交，按标准写中文合并说明。远端策略不支持时报告具体冲突，不自行squash或直推主分支。
2. 获取合并结果，按B11的`verify_pr_merge.py`逐条核验本次分类提交归属。通过后在确切合并SHA创建并推送Tag。
3. 创建GitHub Release，填写中文Release Notes并上传适用资产与校验文件。没有二进制交付物的项目不凭空制造附件。
4. 回读远端Tag解析后的提交、Release状态与Tag、资产名和大小；附件下载回读计算SHA256并对比本地产物。Tag存在不等于Release完成。

## 异常与授权

- 用户“发布”的明确指令在对象可确定时已覆盖完整链路，不在提交、push、merge、Tag、Release每步重复索取批准。只问流程或仅修改Skill不构成发布某仓库的授权。
- 未登录时通过现有授权入口解决，不索要聊天中的token或打印凭据；不能完成认证就记录已完成阶段和实际阻塞。
- 不自动覆盖远端URL、身份、Tag或Release；已存在对象先回读，属于本次已成功阶段则核验后复用，属于其他发布则报告冲突。
- 合并前失败在工作分支修复；合并后发Tag/Release失败记录真实状态并从失败阶段恢复，不重做已成功合并。
- 已公开提交不能自动amend/rebase/强推。普通远端更新先fetch，能按既定事项安全解决的继续验证，存在语义冲突才询问。
- 发布不默认部署生产、删除分支或清理旧开发；这些动作按另外已给授权执行。

## 完成回执

每个仓库分别记录：工作分支、目标基线、分类提交SHA、PR URL与MERGED状态、合并SHA及核验结果、Tag及解析SHA、Release URL、资产名/大小/SHA256、构建与本轮测试结果、仍保留的隔离内容。只有必要阶段都有实际证据才称完整发布成功；仅本地提交、仅push或仅合并都要准确标明。
