# 发布流程

## 输入与执行边界

先定位调用方已确认的正式交付 SQL；路径、库/域/分层和中文模型名应来自当前用户要求、模型设计或仓库规范，不能将历史示例当作此次目标。缺少中文名时先查交付说明；无法唯一确定才问用户。表名标准复用 C18 的命名依据，不能在发布时擅自重命名模型。

发布仓库、远端、目标基线、工作分支和提交标题必须按B11从目标仓库及本任务输入确定。来源master和DWD中文分支示例仅为实例。只读计划脚本输出目录和命名建议，不复制、不执行 Git 写入、不联网。输入示例含占位内容，使用前必须替换。

## 1. 更新主线

1. 检查 `git status --porcelain=v1`、当前分支、仓库根、远端地址及仓库适用规则；远端展示要去除 URL 内嵌凭证。确认是预期 GitLab 项目。
2. 正常路径：干净工作区 `git switch master`，然后 `git pull --ff-only <已确认远端> <已确认基线>`，记录更新后的基础提交。
3. 有用户未提交内容时，不默认 stash/reset/clean；可以在任务目录建立独立 worktree，在那里快进更新 master。若 master 已被原工作区占用，从已 fetch 的 `origin/master` 建立隔离发布 worktree；记录这是保护用户改动的替代路径，不能声称原工作区 master 已更新。
4. 本地主线分叉、不明冲突或拉取失败，停止后续提交；先解释可核实的分叉，不把本地提交悄悄推入此次 MR。
5. 复跑先读取发布回执和远端状态。已经完成的提交/MR不重做；用户已合并的 MR 不再发送“帮合并代码”。

## 2. 落位、分支和提交

目标：`{仓库根}/{业务库}/{数据域}/{分层小写}/{规范表名}/{规范表名}.sql`。

例：`cbebg/ads/dwd/dwd_ads_sqp_brand_view_ilu_dd/dwd_ads_sqp_brand_view_ilu_dd.sql`。仅复制这一个加工文件并保留所属目录；排除 `create_*.sql`、`add_*.sql`、`full_load.sql`、说明、Excel、参数样例、验证和历史文件。需要额外文件时以用户明确范围为准，不能按整份交付目录递归复制。

从更新后的主线复制正式 SQL，再创建本次分支；也可先建分支再复制，提交前必须已处于本次工作分支。既有同名文件应检查实际差异，不能默认为新增。

| 项目 | 格式 |
|---|---|
| 分支 | 按目标仓库规范指定；无约定时使用`codex/`前缀 |
| 新增提交消息 | 按目标仓库规范指定；无约定时使用`codex/`前缀 |
| 修改提交消息 | 按目标仓库规范指定；默认中文类型化提交消息 |
| MR 标题 | 与当前发布内容及提交标题一致 |

来源项目曾使用分支 `DWD-SQP品牌视图`（非当前默认）；目录仍为 `dwd`。先 `git check-ref-format --branch <分支>`。遇到已有分支，检查该分支、工作树、对应 MR 和作者归属后恢复或调整；Windows 大小写碰撞不得 `-M` 强制覆盖。只有确认是同一分支的大小写修正时才通过唯一临时名中转。

只 `git add -- <目标相对路径>`；检查暂存区路径集合恰好等于此次授权集合，运行 `git diff --cached --check`。逐字核对正式源与暂存对象，允许 Git 正常 CRLF/LF 转换，不能忽略其他内容变化。核对提交 `HEAD` 对象中的内容与文件集合；工作文件一致不代表实际提交一致。

没有差异时不制造空提交：检查是否已在主线或已存在未合并 MR，再决定记录 no_change 或恢复通知。Git 身份缺失时不擅改全局姓名邮箱。

## 3. 推送与 MR

实际 GitLab 已验证支持 SSH push options，可优先使用：

```text
git push -u <已确认远端> <分支名> -o merge_request.create -o merge_request.target=<已确认基线> -o merge_request.title=<标题>
```

参数通过工具参数或子进程参数数组传递，中文标题作为一个参数；不要用字符串拼 shell。代码更改时 MR 描述说明触发问题、最终行为、变更与验证，不复述会话。需多行描述时用工具结构化参数，CLI 支持文件时使用 UTF-8 正文文件，避免引号和换行错乱。

推送前查询已有开放 MR，避免重复创建。未安装 GitLab CLI 不是理由去安装一串新依赖：优先已有 SSH push options。也可用已配置 glab/官方 API，或已登录 GitLab 浏览器的 DOM 操作；**这一浏览器权限仅用于 GitLab，不可用于钉钉通知**。不从无关文件搜集密钥、不在命令 URL 中写令牌。

必须回读：服务器返回的真实 MR URL/编号、源分支、本次提交 SHA、目标分支、opened/merged/closed 状态，以及远端分支 SHA。MR 已合并按已合并记录，不发送合并请求通知；已关闭而未合并需核对原因。若仅有 push 输出链接而未验证 MR 内容，记录 `mr_unverified`，不得宣称完成并通知。

无法联网时保留本地提交，不强推、不伪造 MR 链接。推送已成功而 MR 创建失败，只补 MR；MR 已创建而通知失败，只补通知。

## 4. 调用 F05 作为最后一步

调用方提供：

```json
{
  "recipient_name": "<本任务已授权收件人>",
  "content": "帮合并代码：<已核对真实MR链接>（codex自动发送）",
  "request_id": "gitlab:<项目标识>:mr:<真实编号>:head:<本次提交SHA>:merge-request",
  "receipt": "<本次任务目录>/通知回执.json"
}
```

正式和测试收件人均由本任务明确指定，无默认人员。只有发起者已授权发布通知或明确调用本发布技能的完整流程才调用 F05；准备草稿/预检本身不授权发送。不要同时通知两个对象。

F05 负责凭证复用、联系人消歧、幂等发送、回执和异常路由。C19 不重复实现这些逻辑，禁止用截图、Codex 视觉、浏览器钉钉、桌面自动化、坐标点击、模拟按键或剪贴板代替 CLI。

成功条件是 F05 返回 `sendStatus=SUCCESS`，pending 仅为待查询。CLI 缺失、登录失效、组织权限、EOF/代理故障时记录 `notification_pending/failed/unknown`，保留 MR 不回滚代码，不重复发布。环境配置归 F05 的条件分支，不能每次发布都安装、重新扫码或改 Clash。
