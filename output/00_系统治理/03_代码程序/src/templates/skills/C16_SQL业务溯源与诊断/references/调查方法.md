# 调查方法

## 先建立业务判断，再读处理步骤

从当前要求和已确认的上下文中形成一份简短工作判断：

- 用户要恢复或保证的业务结果是什么？例如“每个门店的库存不能重复”，不止“这列怎么来的”。
- 一行代表谁、哪个时间和哪些维度？是否同时有实体标识、代表对象、汇总对象？
- 哪些规则已经由用户确认，哪些只是现有代码行为，哪些仍是推断？
- 本轮是解释一个局部、诊断异常、实施修复，还是验收部署？

这些是调查时的工作信息，不要求每次先向用户提交四项表格。用户新消息通常是推进原问题，沿用已确认的口径；用户明确收窄或切换目标时更新范围。

已有信息能确定的关联问题，直接查证。例如输出按门店区分，而候选选取只按商品分组，应核对是否会跨门店取值。不必先让用户指出缺少哪个分组键。

“代表对象应取周期末快照还是周期累计最高”“无销量应保留还是排除”可能是不同的合理规则。先说明当前行为及影响，列为业务选择，不凭字段名猜定。能独立完成的事实调查继续进行。

## 以一条稳定业务记录贯穿

优先用用户的筛选条件和异常行。记录足以唯一识别业务对象的时间、站点/组织、类别、链接/订单及款式/状态等维度；字段含义依实际模型判断。

需要区分三类标识：原始实体ID、分组ID、展示代表ID。代表ID可能因修复重新选择，回验用稳定业务键，并列出前后代表ID；不能只因旧ID不见了就声称记录被删或问题解决。

## 倒查来源，再正向检查必要链路

先画出或记录实际依赖：目标字段来自哪个表达式/别名，别名来自哪张表或子查询，实际关联用了什么键。别名、字段名和业务对象不能混用。

发现一个断点后，继续检查与目标直接相关的路径：

| 环节 | 需要回答的问题 |
|---|---|
| 源记录 | 同样的时间、业务键和有效条件下，有没有记录？字段有没有值？ |
| 关联 | 左右实际键是否一致？时间口径、父子实体、组织维度是否混用？右表是否一对多？ |
| 候选与选行 | 分组是否覆盖目标业务粒度？所选记录是否属于目标对象？同分是否稳定？全空指标是否仍产生名次？ |
| 聚合 | 聚合对象和去重键是否正确？JOIN是否扩大了行数、数量或金额？过滤发生在分子、分母和排名之前还是之后？ |
| 周期与历史 | 最后记录日、最后有效日、最新非空日是否被混用？有效性的依据与业务要求是否一致？ |
| 展示 | 下游是否仍输出旧字段？展示身份和属性是否按明确规则对应？源层变化是否真正传到报表？ |

不是要求每次检查所有项。选择能够改变当前结论或修复完整性的环节；明确无关的模型不扩展。身份改变时注意关联属性，但不假定所有指标必须来自同一条物理明细：指标可以按业务粒度汇总，代表对象可以按另一个已确认规则选取，两者须可解释且口径一致。

## 根因与修复范围

区分：源无记录、源字段空、关联未命中、候选被错误选走、分组或汇总粒度不一致、规则本身待确认。允许一个结果存在多个连续原因，不强行归为单一问题。

确定修复时，按因果依赖列出必须一起修改的点。例如细化候选分组时同步核对回关联键；新增最终指标时同步核对依赖它的历史比较。最小修改指能解决目标的最小完整修改，不是只改最先看到的一行。

用户只要求诊断时给出具体改法而不执行。授权修复后完成本地实现与适当检查；生产部署和数据回算按本次授权处理。部分原因需要业务决定时，明确当前可完成项和剩余决定，不把推断写成规则。

## 何时收敛

- 原案例的异常能够由可复查的代码和证据解释。
- 所提修复所经过的相关上游、选行和下游输出已核对，不存在已发现却未说明的必要依赖。
- 修改任务已验证原案例、受影响的关键边界和合理范围内的整体影响；验收范围与数据时间明确。
- 尚未完成的事项已说明证据缺口或业务选择，不宣称“一次查完所有问题”。

证据不足时交付已确认部分和最小补证查询。不要用无休止全表扫描、扩大历史范围或重复查询来替代判断。
