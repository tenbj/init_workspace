# 单案例取证与解释

## 写查询时

查询数据库使用 C02，复用其连接与只读能力。每条关键结论保留实际执行SQL、参数/筛选范围、执行时间、错误状态、行数及结果位置；不要写入凭证。

先保留能解释案例的必要明细，展示源候选与实际选中行。不要一开始用DISTINCT、MIN/MAX、LIMIT 1或只取第一名隐藏一对多和同分问题；展示完整必要候选不等于扫描整库。

若要解释ROW_NUMBER或排名，先在完整业务分区计算，再筛用户案例。先按单ASIN过滤再排序得到的第一名不能作为原榜单证据。若客户端截断，标注未完整，缩小到正确业务分区或分段取数后再定论。

NULL、空串、零值、缺记录分别核对，不把NULL擅自补0。LEFT JOIN后过滤右表可能改变保留行范围；汇总不一致时同时检查候选倍增和业务键唯一性。

当前代码、线上物化表和历史结果是不同证据。用户说已重跑时，检查批次或更新时间，并读取当前表回验；不能用之前的只读模拟结果充当重跑结果。无数据库访问时可做代码分析或本地模拟，说明其限度。

## 解释时

先回答用户这一轮的判断，用一个可复查的案例说明。句子围绕“哪一行的什么字段，经过哪条条件，变成什么值”。不要要求用户先理解全部CTE和别名。

例如：

> 源里有这条记录，未命中发生在组织键。左侧是门店S2，右侧候选属于S1，当前ON要求门店相同，因此结果为空。

随后放相关ON条件及实际值即可。需要说明一连串问题时，按同一案例的依赖顺序一次说明，并标出哪些修改必须同时进行；详细查询和全量统计可以放到证据文件。

| 用户此刻关心的内容 | 优先给出的内容 |
|---|---|
| 字段来自哪里 | 实际SELECT表达式、别名对应表、后续是否覆盖 |
| 源没有还是关联不到 | 按实际过滤条件的源记录，以及ON左右实际值 |
| 为什么选这条 | 同一分区必要候选、排序条件、选中行 |
| 为什么修后还不对 | 原业务键的前后结果，以及后续哪个环节改变了结果 |
| 应该怎么改 | 需要一起修改的具体位置、理由及同案例验证 |

范围、定性、证据、验证边界都需要清楚，但不强制每次用固定四项开头或长报告模板。简单问题可以几句话回答；复杂根因链再用表格或列表。默认讲清一个案例，用户希望多个案例或仅要结论时按其要求调整。

## 验证时

先核对原案例，再按实际改动选择边界：错误关联看键匹配及增行；新增分组看分区唯一和跨组取值；选行看同分、NULL、缺分类；周期指标看跨期、有效天数和断期。无需为单纯字段来源解释新写测试。

修复只读计算一致、生产表已更新、业务要求已满足分别说明。例如代码已执行但没有有效销量仍产生代表行，应说明部署成功与业务边界残余，而不是把非空比例作为唯一验收标准。
