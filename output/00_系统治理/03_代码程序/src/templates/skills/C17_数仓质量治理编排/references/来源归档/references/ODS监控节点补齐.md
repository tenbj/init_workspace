# ODS监控节点补齐

2026-09-30用户带教并验证。适用于已授权补齐ODS同步统计监控的工作流；区分配置上线、工作流运行及指标运行，不将其中一项成功当作整套质量治理通过。

## 定位和保护

**ODS默认执行范围（用户最终确认）**：按原规范完成节点及指标配置、恢复工作流与原定时上线，然后仅运行质量指标、查询新结果并截图。默认不额外启动DATAX/工作流来验证新增监控节点，不把下方完整工作流验证作为交付前置条件。只有用户明确要求验证新增节点或运行工作流时才走该分支。本规则仅限ODS，不改变非ODS流程；“默认不验证监控”在此指不额外触发工作流验证，仍须运行质量指标并查询结果截图。

1. 常规配置默认Doris，只有用户明确指定修复某个CK时进入该CK。人工导入模型先判断是否适配，不因ODS前缀强套同步规则。
2. 模型列表按完整技术表及连接/中文名锁定唯一目标：右侧更多→关联ETL→核对下方面板目标身份及最近调度→悬停确认「跳转工作流」→点击进入新页面。最近历史成功不是本轮运行证据。
3. 新页核对完整工作流名、项目、工作流标识。按唯一任务编号计数，主画布和缩略图可能重复展示。对标案例为 `ods_realtime_db_t_crawler_ss_product_target_category` 的DATAX→HTTP「DPX-统计同步数据」。已有等效监控时先核对，不重复新建。
4. 保存脱敏修改前定义，记录原任务编号、版本、参数指纹、依赖、工作流及定时状态。禁止删除工作流或任何任务节点；不导出凭据、DATAX连接密码或带登录凭据的中间跳转URL。

## 进入编辑并补节点

1. 跳转页通常处于上线只读状态。复制左上角完整工作流名→左侧工作流定义→右上角搜索精确定位→悬停确认「下线」并操作→编辑。每次使用最新页面和提示，不沿用历史元素编号。
2. 下线工作流可能同时下线定时，记录两者状态。保留原DATAX，只添加HTTP「DPX-统计同步数据」，前置任务选择当前目标DATAX，形成DATAX→HTTP依赖。
3. **业务参数来自当前目标DATAX的localParams**：原样复制table、sql、columns、db、preSql、postSql、StartTime、EndTime，保留空值、完整SQL及变量模板。不可用表名推测SQL，不复制对标的表名、SQL或日期过滤；缺项/差异先核查实际配置。
4. 从当前有效对标监控节点获取modelStatCountUrl及HTTP设置。已验证案例为 `http://${modelStatCountUrl}`、GET、默认响应码200、连接和Socket超时600000ms。地址是环境配置，每次现场读取，不把案例IP当所有环境默认值。
5. 六个请求参数均为PARAMETER，保留运行时模板：

| 名称 | 值 |
|---|---|
| projectCode | ${system.project.code} |
| flowCode | ${system.workflow.definition.code} |
| statTaskCode | ${system.task.definition.code} |
| processInstanceId | ${system.workflow.instance.id} |
| startTime | ${StartTime} |
| endTime | ${EndTime} |

`statTaskCode`保留当前HTTP任务模板，不填写原DATAX编号。已验证案例9项自定义参数为目标原8项加监控地址，方向IN、类型VARCHAR。全量复制是对标配置结构，不能据此断言接口消费全部字段或执行preSql。

## 保存、回读与重新上线

1. 节点「确定」只更新草稿，随后还须工作流「保存」→基本信息核对原名称等→确定。无需改名、重建工作流或重建定时。
2. 保存后重新读取持久化定义：原DATAX身份、版本、完整参数指纹保持一致；新HTTP配置和自定义参数逐项一致；依赖正确，无节点丢失。只用实际观察到的只读接口或UI回读，不猜写接口绕过UI。
3. 回工作流定义唯一目标行，执行「上线」并确认。若弹出配置定时提示，已有定时时取消该提示并使用原定时，不创建新计划。
4. **分别恢复工作流和原定时**。工作流上线不代表定时上线；对原本已上线的定时执行「定时上线」并确认，最终列表两列均为上线。若原定时本来下线则保持原状，除非用户另有明确要求。
5. 保存最终状态及版本证据。未手动运行时明确记录“配置上线完成，运行未验证”；不自动触发整个DATAX来证明保存成功。

## 平台同步行数质量指标（2026-09-30已验证）

工作流及定时恢复后，用户要求继续创建质量指标时，回模型列表，从目标行右侧「质量指标」进入。先按同一对标模型查看现有指标的编辑信息、监控策略和周期，再为当前模型查重创建。常规C15的非ODS目录、Doris查询连接及自定义SQL模板不直接适用于本分支。

1. 对标的监控目录为「同步行数校验检查→跨境电商→市场域→ODS」，名称取当前目标模型中文名以区分对标；说明「同步行数校验检查」，归属角色/人员继承当前模型，启用。该案例对标通知为「钉钉-工作通知」，订阅人员和报表链接为空；按用户要求对标时沿用，不新增收件人。
2. 先按目标模型查重，再清空模型过滤、按完整新监控名全局查重。新增后尚未绑定模型，继承的隐藏模型筛选可能使列表继续显示0条；刷新页面后重新按名称查询，再进入唯一目标。不得再次新增来解决不可见问题。
3. 「配置监控」内数据连接选择 **业务-数据平台**，数据模型从树选择当前「跨境电商→业务域→ODS→目标模型」，确认其技术表身份。策略连接用于读取平台同步日志，目标模型仍是Doris；不要因Doris默认规则而把策略连接错改为跨境电商。
4. 策略类型选 **规则策略**，规则选 **同步行数校验检查**，异常条件为 **quality_value 大于 0**；`${data_set_id}` 由平台自动填入当前目标模型编号，不能抄对标编号。规则预览读取平台 `dap_application.dap_mart_dataset_etl_log`，取当前模型按id倒序最近1条的source_count、target_count，用NULL安全相等比较。保留规则模板，不另造SQL。
5. 本案例对标 `cronList=[]`、周期页为空，按「一样的」授权保持相同，不套用非ODS的更新周期加5分钟算法。其他对标应现场读取周期再决定，空周期本身不证明触发机制。
6. 保存后重开策略、周期和编辑监控：核对当前模型编号、规则ID/名称、查询连接、quality_value阈值、规则SQL全文、目录、负责人、启用和通知。保存证据；没有手动运行就记未运行，不用对标历史正常替代目标结果。
7. C15通用验收器当前硬编码「跨境电商＋自定义策略」，不适用此ODS规则分支。按上述现场值逐项回读核验并记录SQL全文比较结果，不能伪造字段使通用脚本通过。缺少同步日志时该SQL可能返回0，不据此宣称同步成功或覆盖无日志/双NULL情况。

已验证案例：对标监控261/模型2712，目标监控406/模型2562，规则18；这些编号仅为证据，不在下次任务中硬编码。下拉框输入文字不等于选中；展开后等待可见选项、点击并回读完整标签。写操作仍走UI，网络证据只取必要响应字段，禁止将请求头或登录请求写入产物。

## 工作流运行入口与完整验证（用户2026-09-30补充）

**可选验证分支，ODS默认不执行。** 新增节点后，只有用户要求验证时才使用。当前案例属于用户明确要求验证的实测，不能推广为C17后续ODS任务的默认动作。

需要手动运行工作流时，**回数据平台模型列表→目标Doris模型→右侧更多→关联ETL→在该模型ETL面板点击「运行任务」→确认一次→等待→点击运行任务右边第四个按钮「刷新」**。悬停核对刷新提示和所属面板，防止点到主列表刷新或再次点击运行。不要默认从DolphinScheduler工作流列表启动。用户明确要求运行时执行；仅条件式说明入口时不据此重跑生产同步。

1. 提交提示“运行成功”仅表示启动请求成功，必须等待列表出现本次新实例；核对实例名、开始时间、版本及状态，不能读到历史成功便结束。页面短暂空白或仍运行中，只刷新同次实例，不再次提交。
2. 关联ETL面板可能只显示DATAX任务。本次验证因此同时核对DolphinScheduler同一实例内DATAX与后置HTTP状态；DATAX成功不代替HTTP成功。需要补查时只查看实例，不从该处再次启动。
3. 成功后回目标质量指标，先刷新记录识别是否已有新结果。用户明确要求重新运行时，仅勾选目标一条→手动运行→确认一次→查询/监控记录。以新的记录ID、监控时间、实际SQL中的模型ID和结果值确认本次执行，保留真实列表截图。
4. 2026-09-30实测：实例587579（工作流v7）11:20:17开始、11:21:35成功；DATAX 11:21:31成功，新增HTTP 11:21:34成功，其响应code=200、msg=操作成功。工作流完成后指标仍为10:59:29旧记录；手动重跑406产生45303，11:23:53正常、值0。该观察窗口未见自动新增指标记录，不据此推断所有场景的自动触发机制。编号只作案例证据。

运行工作流和运行质量指标是两个动作：前者执行同步及后置统计，后者执行日志检查SQL。需要验证新增统计节点时，应按授权先从关联ETL运行，核对新的工作流实例、DATAX及HTTP节点结果、对应本次实例和日期范围的统计日志，最后核对该模型质量结果。不能用历史DATAX成功或单独手动指标返回0证明新HTTP已跑通。

## 原理与证据边界

- DATAX负责按其实际源查询和目标写入配置同步数据，源目标及日期口径应以当前任务配置为依据。
- 后置HTTP通过项目、工作流、当前统计任务、实例编号及起止日期调用统计服务。配置设计体现“同步后统计”的依赖；当前案例8项本地业务参数原样来自DATAX，避免统计口径偏离同步口径。HTTP显式请求只传6项上下文参数，不能说把SQL、table直接作为HTTP查询参数发送了。
- 质量规则从平台ETL日志读取该模型最近一条source_count、target_count比较，所以规则查询连接是业务-数据平台，治理模型仍为Doris。
- 按已读SQL，源目标不等时返回1；相等返回0，双NULL和无日志也会返回0。需同时检查统计日志是否属于本次运行、计数是否已生成，才能完成新节点链路验证。
- 统计服务如何读取本地参数、如何写入计数、是否自动触发质量指标，需要服务实现或对应的运行证据；未获得时作为待验证机制，不从空周期或HTTP名称直接断言。本案例已验证DATAX及HTTP成功、HTTP业务响应成功、随后手动指标正常；尚未直接回读同次平台ETL日志的计数和时间，不能把这些响应当成日志行已核对的证据。
- 表行数一致性不证明每个字段值一致，也不替代业务主键、完整性等检查。

## 恢复与中断

用户暂停立即停止平台变更，记录草稿是否保存、工作流/定时状态及下一步。用户明确继续后先回读现场再接续，避免重复节点或重复运行。完成案例与前后脱敏证据见 `output/07_数仓质量治理/01_问题答疑/68_ODS质量治理带教记录.md`。
