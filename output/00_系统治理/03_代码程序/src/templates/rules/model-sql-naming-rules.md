# 模型命名确认与改名流程规范

适用于模型开发、交付、代码发布及平台接入。版本：1.0.0。原始业务命名依据仍以 input 中的表规范、字段标准和领域定义为准；本文约束核名、确认与变更流程。C18、C19 引用同一份流程，不各自维护另一套规则。

## 开发阶段：先核名，再固定交付名称

1. 表名必须独立于字段审核，拆解库、层、域、可选子域、业务过程/实体、可选来源标签、更新方式、频率；记录中文含义及逐段依据。不能把 ODS 去掉前缀后直接当作已确认 DWD 名，也不能把源库、账套编号、采集时间串自动解释为数据子域。
2. 优先标准词根和已有同业务名称；新增词根、仓库惯例、技术标签例外分别注明，不能把惯例说成标准已登记。源库技术标签确有业务必要时，说明区分的对象及用户确认依据，不一刀切禁止数字。
3. 更新方式由实际目标删写范围确定。频率来自实际调度或用户明确确认；“dd每日已确认”不代表具体执行时刻已配置，也不能根据粒度、源名称或无日期参数猜频率。ODS存量完整性与DWD全量覆盖语义分别验证。
4. 在进入正式交付和发布前，向用户展示完整库表名、中文名、逐段解释及未决项，取得明确确认。会话已有清晰确认时直接复用；表名仅出现在AI产物或用户泛泛认可代码，不算名称已明确确认。未确认时可开发、取证和给建议，不能静默发布该名称。
5. 开发材料保存 `表名确认.json`：status、table、model_name、database、layer、domain、update_mode、frequency、standard_source或naming_basis、name_confirmation、confirmed_date；有来源标签、业务名称及例外时补充依据。正式说明摘要引用，保持正式五件交付精简。

## 发布阶段：消费确认记录，不重新猜名

1. 读取本模型确认记录，核对记录、正式SQL实际INSERT目标、交付目录/文件名、发布元数据和仓库相对路径完全一致。记录缺失、未确认、字段不一致时停止复制/提交/推送，指出具体缺口；已确认信息不重复询问。
2. 确认发布仓库身份并保护未知修改。采用隔离worktree时，记录唯一实际提交工作区；不要为了满足路径展示而在原master额外制造未跟踪副本。需要迁回确认仓库时先核对文件哈希和工作区状态，再用Git正常切换和清理本任务副本。
3. 已有提交或MR时先核对发布回执与远端提交并复用；查询失败不视为“没有MR”。按C19核对服务器真实MR链接、分支与MR head的一致性并记录创建目标参数后进入通知；不把合并状态查询或网页登录作为提交MR后的通知门。

## 名称变化：全部当前产物一起迁移

1. 同步DDL及加工目标、目录和文件名、SQL镜像、字段文档及工作簿模型信息、说明与索引、质量SQL和配置、确认记录、生成器、发布输入/回执、仓库路径和现有MR内容。平台已建对象另行核实迁移影响，改本地名不代表生产表已重命名。
2. 历史查询回执、原始输入、旧提交和旧名称记录保留原貌并标注历史；不可批量替换源ODS名称、伪造旧回执的新哈希或新执行日期。当前运行入口不得继续产出旧目标，旧入口仅作跳转或归档。
3. 已推送时在原分支追加改名提交并更新现有MR，核对对主线的完整差异只保留正确当前路径；不强推、不重复新建MR、不自动合并。
4. 验收覆盖：新名称各处一致；原始源名不变；只改目标名时业务查询等价；最终文件哈希和验证范围可信；两份工作簿可读；仓库状态及MR提交可核对。生产落表、真实调度时刻、通知和合并状态分别记录。
