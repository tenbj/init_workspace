## 根因

1. 把“允许发布合并”误扩展成“允许改变既定合并策略”。
2. 发布检查发现中间提交含真实联系人及截图后，选用了 main squash 来避免公开这些 blob；正确做法应是净化工作分支并保留事项边界，然后走 PR。
3. 没有先核对仓库已有 PR 记录；仓库此前已有正常 PR 合并流程。
4. 只核验了最终文件和发布资产，未把 PR 状态、合并双亲和分类提交可达性作为发布条件。
5. 收尾汇报没有明确突出“未创建 PR、分类提交被压缩”，导致用户需要追问才能确认偏差。

## 防复发措施与验收

| 措施 | 落点 | 验收 |
|---|---|---|
| 用户已确定分类提交时保持事项边界 | B11 入口及验收与合并流程 | PR 页面逐条可见，禁止本任务 squash/rebase |
| 发布以已合并 PR 为前提 | B09 入口、发布流程、发布前检查 | 合并后才创建/调整 tag |
| PR 合并证据核对 | B11 `scripts/verify_pr_merge.py` | 旧单亲发布被拒绝；新双亲 PR 合并通过 |
| 检查覆盖即将推送的整个新历史 | B11 验收与合并流程 | 原敏感提交及其不合格 blob 不被引入 |
| 已授权历史修复使用精确租约 | B11 验收与合并流程 | 远端变化则拒绝覆盖 |
| 交付明确 PR、分类提交与发布目标 | 本次 PR/Release 说明 | 用户可直接核对独立防复发提交 |

脚本是只读核验工具，不是服务器保护，也不能保证任意绕过流程的操作被技术性阻止；执行者必须按 B09/B11 调用并保留结果。今后如发现隐私问题或工具限制，应在既定分支流程内解决，不能自行以直接推送 main 代替。
