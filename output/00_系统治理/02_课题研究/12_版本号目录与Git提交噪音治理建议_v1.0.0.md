# 版本号目录与 Git 提交噪音治理建议

## 一、目标

解决当前工作区中“少量内容修改导致 Git 状态出现大量删除、新增或重命名”的问题，同时保留语义版本管理、历史追踪和可恢复能力。

本建议不主张取消版本管理，而是把版本号从高频变化的 live 路径中移出来，放到更适合承载版本语义的位置：元数据、版本记录、历史快照和 Git tag。

## 二、问题背景

当前规则把版本号写进多个 live 路径：子项目文件夹、分类文件夹、部分内容文件名。每次新增一篇文档或做一次小修改，都可能触发父级目录版本 bump。对人来说，这表达了“当前状态已升级”；对 Git 来说，这意味着一整棵目录树换了路径。

本轮新增一篇治理建议时，B02 已经把 `output/00_系统治理_v1.25.0` 升级为 `output/00_系统治理`。这类 rename 会让 Git 看到大量路径删除和新增。`.history/**` 已经在 `.gitignore` 中被忽略，所以主要噪音并不是历史快照进入 Git，而是 live 目录名变化。

## 三、依据

| 事实源 | 当前口径 | 对本问题的影响 |
|---|---|---|
| `.system/standards/workspace-spec.json` | 子项目、分类目录、01/02 内容文件都带版本号 | live 路径随版本变化，天然容易触发大面积 Git rename |
| `B02` | PROJECT 模式备份后会 bump output 子项目文件夹版本 | 修改任意 output 子项目内容都可能改动整棵子项目路径 |
| `B04` | 新增 01/02 内容时要求分类目录版本同步 bump | 新增一个文件也会带动分类目录路径变化 |
| `.gitignore` | `.history/**` 已忽略，仅保留占位结构 | 历史快照不是当前 Git 噪音主因 |
| Git 机制 | Git 以内容和路径呈现变更，目录名变化会表现为 rename/delete/add | 把版本号放在 live 路径中，会把语义版本变化放大成路径变化 |

## 四、最终判断

版本号不应放在高频变化的 live 文件夹名中。live 路径应该表达稳定身份，例如“系统治理”“课题研究”“代码程序”；版本号应该表达某个状态的编号，放在 `版本记录.md`、manifest、文件头元数据、`.history` 快照名或 Git tag 中。

适合带版本号的对象，是不可变或低频发布对象：发布包、EXE、压缩包、归档快照、Release tag。活动工作区目录不适合带版本号，尤其不适合每次内容变更都重命名。

## 五、最小整改清单

| 优先级 | 意图指向 | 具体落点 | 要做什么 | 验收标准 |
|---|---|---|---|---|
| P0 | 稳定 live 身份 | `.system/standards/workspace-spec.json` 与命名标准 | 将 output live 子项目路径从 `{编号}_{主题}_v{x.y.z}` 调整为 `{编号}_{主题}`，版本写入元数据 | 小改不再导致整个子项目目录 rename |
| P0 | B02：保留版本但不改 live 路径 | `B02` 备份脚本与说明 | PROJECT 模式只创建版本化 `.history` 快照并更新 `版本记录.md`，不重命名 live 子项目 | 修改 output 后，Git 只显示真实改动文件 |
| P0 | B04：分类目录稳定 | `B04` 子项目管理规则 | 分类目录改为 `01_问题答疑`、`02_课题研究`、`03_代码程序`，分类版本进入目录元数据或 `目录.md` | 新增内容不再导致分类目录 rename |
| P1 | 内容文件稳定命名 | 01/02 内容文件规则 | 内容文件可保留编号和标题，版本写入文件头或 `目录.md`，例如 `12_版本号目录与Git提交噪音治理建议.md` | 修改正文不再要求文件名升版 |
| P1 | 发布边界使用版本号 | B09 发布流程 | Release、tag、EXE、导出包继续带版本号 | 对外交付仍能明确版本 |
| P1 | Git 提交流程降噪 | 发布与提交规则 | 一次任务形成一个提交；细碎修改先留在工作区或 squash；`.history` 继续不纳入 Git | 常规提交文件数接近真实改动范围 |

## 六、不做事项

- 不取消语义版本；只取消 live 路径承载语义版本。
- 不把 `.history` 快照重新纳入 Git；Git 自己已经是远端历史，`.history` 更适合作为本地可恢复保险。
- 不继续让“路径名、文件头、目录、版本记录”多处同时表达同一个版本事实。
- 不把 PATCH 级小改扩大成整棵目录重命名。

## 七、执行顺序

1. 先确认新标准：live 路径稳定，版本进入元数据和历史快照。
2. 修改前执行 B02，对相关标准、Skill 和输出子项目做备份。
3. 更新 `workspace-spec.json` 与人类可读命名标准，明确 live 路径和历史路径的分工。
4. 更新 B02：PROJECT 模式不再 rename live 子项目，只更新版本记录并生成历史快照。
5. 更新 B04：新建子项目和分类目录时不再把版本号写入 live 目录名。
6. 编写一次性迁移脚本，把现有 output live 目录稳定化，并同步修复目录链接和对话记录文件名。
7. 更新 B01/B06 检查口径，防止新旧规则混用。
8. 运行 B01 与规范化检查，再看 `git status --short` 是否只剩真实改动。

## 八、验收口径

- 新增一篇文档时，Git 只出现文档、`目录.md`、`版本记录.md`、必要记忆文件的改动，不出现整棵子项目删除和新增。
- 修改一处文案时，Git 不出现父级目录 rename。
- `.history/**` 仍保持 Git 忽略状态。
- `版本记录.md`、manifest 或文件头能查到当前版本。
- 对外发布物仍可通过 Git tag、Release 名称、EXE 文件名或归档包名识别版本。
- B01 体检能识别 live 路径是否误带版本号，B06 规范化能给出修复建议。

## 九、结论

建议采用“稳定 live 路径 + 元数据版本 + 不可变历史快照 + Git tag/Release”的组合。这样既不会丢掉版本管理，又能让 Git 提交回到真实变更本身。

短期止血可以先做到三点：继续忽略 `.history`，小改不要立刻提交，任务完成后 squash 成一个提交。长期方案则应改标准和脚本，让版本号退出 live 文件夹名。这一刀下去，提交噪音会明显安静下来。
