# 项目更新日志设计方案

## 目标

为整个项目建立一套可提交 GitHub、可直接用于 GitHub Release 的更新日志体系。它要同时满足三件事：

1. 开发时能从提交、版本记录和变更文件中追溯改动。
2. 发布时能给用户一份清楚、克制、可读的 Release Notes。
3. 不破坏当前工作区已有的 `output/版本记录.md`、`B02` 备份、`B01` 体检和 `.memory` 记忆体系。

本方案只设计“公开发布用更新日志”的结构和流程，不重写现有工作区版本控制制度。

## 问题背景

当前项目已经有多层历史信息：Git 提交记录、各 `output/` 子项目的 `版本记录.md`、`.history/` 快照、`.memory/` 记忆，以及 `docs/GitHub发布授权与Release流程.md` 中的发布命令。这些信息都能解释项目发生过什么，但不适合直接作为 GitHub Release 的正文。

原因是它们面向不同读者：`版本记录.md` 面向工作区内部治理，`.history/` 面向回滚，`.memory/` 面向对话恢复，Git 提交面向开发协作。GitHub Release 面向安装和升级的人，它需要的是“这个版本对我有什么影响、我是否需要升级、怎么升级、下载哪个资产”。

因此需要新增一层公开发布口径：`CHANGELOG.md` 作为发布更新日志主文档；GitHub Release 的正文从对应版本段落复制或生成。GitHub 自动生成 Release Notes 可以作为辅助材料，但不作为最终事实源。

## 依据

| 来源 | 类型 | 本方案采用方式 |
|------|------|---------------|
| `.system/standards/workspace-spec.json` | 工作区机器事实源 | 确认 `output/`、`.memory/`、`.history/` 的职责边界 |
| `.system/standards/工作区骨架规格.md` | 人类可读标准 | 确认 `目录.md`、`版本记录.md`、三分类子目录和历史快照规则 |
| `.agents/skills/B02_版本控制备份_v1.0.0` | 执行入口 | 修改发布文档或版本记录前先做备份 |
| `docs/GitHub发布授权与Release流程.md` | 过程文档 | 复用现有 `gh release create` 发布方式 |
| GitHub Releases 文档 | 外部平台规则 | GitHub Release 以 tag 为核心，可使用自动生成说明与比较链接 |
| Keep a Changelog | 外部格式约定 | 采用面向人的分组格式，而不是原始提交堆叠 |
| Semantic Versioning | 外部版本约定 | 使用 `MAJOR.MINOR.PATCH` 判断发布级别 |
| Conventional Commits | 外部提交约定 | 用提交类型帮助归类 changelog |

## 最终判断

项目应采用“四层更新日志”：

| 层级 | 文件或来源 | 读者 | 用途 |
|------|------------|------|------|
| 提交层 | Git commit | 开发者 | 记录原子改动，支持追溯和自动归类 |
| 内部版本层 | `output/*/版本记录.md` | 工作区维护者 | 记录子项目、Skill、规则、脚本和文档的内部演进 |
| 公开日志层 | `CHANGELOG.md` | GitHub 用户 | 记录每个发布版本的用户可见变化 |
| 发布层 | GitHub Release | 下载者 | 展示本次版本说明、资产、校验值和升级提示 |

其中 `CHANGELOG.md` 是公开发布更新日志的 SSOT。GitHub Release 正文应来自 `CHANGELOG.md` 的对应版本段落；`版本记录.md` 只作为整理 changelog 时的输入材料。

整个项目的公开版本号应跟“用户下载和使用的交付物”一致。对当前项目而言，优先跟初始化工具版本一致，例如 `v2.7.0`，而不是跟 `00_系统治理_v1.12.0` 或其他 `output/` 子项目版本一致。

## 最小整改清单

| 优先级 | 意图指向 | 具体落点 | 要做什么 | 验收标准 |
|--------|----------|----------|----------|----------|
| P0 | 建立公开更新日志 SSOT | `CHANGELOG.md` | 新增根目录公开更新日志，按版本倒序维护 | GitHub 用户不看 `output/` 也能理解每次发布变化 |
| P0 | 统一 Release 正文来源 | `.github/release-notes/vX.Y.Z.md` 或 `CHANGELOG.md` 对应段落 | Release 正文从 changelog 版本段落生成或复制 | GitHub Release 与 `CHANGELOG.md` 内容一致 |
| P0 | 明确项目公开版本号 | README、发布流程、Release tag | 公开版本号跟初始化工具或主要交付物版本一致 | tag、Release 标题、exe 文件名、README 当前版本一致 |
| P1 | 规范提交信息 | Git commit message | 使用 Conventional Commits 的类型和 scope | `git log` 能看出 feat/fix/docs/chore/security 等类别 |
| P1 | 增加 GitHub 自动归类辅助 | `.github/release.yml` | 配置 GitHub 自动生成 Release Notes 的分类 | 自动生成结果能作为 changelog 初稿参考 |
| P1 | 固化发布流程 | `docs/GitHub发布授权与Release流程.md` | 加入 changelog 更新、版本校验、hash 校验步骤 | 发布前检查清单包含 changelog 和 Release Notes |
| P2 | 自动生成辅助脚本 | `scripts/release_notes.*` | 从 Git tag、版本记录、Git log 汇总草稿 | 人工只需编辑用户可见措辞，不手工翻历史 |

## 推荐文件结构

```text
CHANGELOG.md
docs/
  GitHub发布授权与Release流程.md
.github/
  release.yml
  release-notes/
    v2.7.0.md
```

说明：

- `CHANGELOG.md` 是长期维护的公开日志。
- `.github/release-notes/vX.Y.Z.md` 是可选的发布临时稿，适合 `gh release create --notes-file` 直接引用。
- `.github/release.yml` 只用于 GitHub 自动生成 Release Notes 的辅助归类，不替代人工整理。
- `output/*/版本记录.md` 继续服务内部工作区，不直接暴露给普通下载者。

## `CHANGELOG.md` 模板

```markdown
# Changelog

All notable changes to this project are documented here.

## [Unreleased]

### Added

### Changed

### Fixed

### Security

## [v2.8.0] - 2026-05-11

### Highlights

- 一句话说明本次发布最重要的价值。

### Added

- 新增了什么用户可见能力。

### Changed

- 调整了什么行为、结构或默认策略。

### Fixed

- 修复了什么会影响使用的问题。

### Security

- 移除了什么敏感信息风险，或修复了什么安全问题。

### Upgrade Notes

- 升级旧工作区时需要注意什么。

### Assets

- `初始化工作区_v2.8.0.exe`
- SHA256: `<发布前填入>`

### Full Diff

- `v2.7.0...v2.8.0`
```

分类建议保持固定：

| 分类 | 放什么 |
|------|--------|
| `Highlights` | 本次版本最值得用户知道的 1 到 3 条 |
| `Added` | 新功能、新 Skill、新命令、新文档入口 |
| `Changed` | 行为变化、目录结构变化、标准口径变化 |
| `Fixed` | bug、路径错误、构建问题、检查误报 |
| `Security` | 脱敏、密钥移除、权限和发布安全修复 |
| `Removed` | 删除或迁移的用户可见能力 |
| `Deprecated` | 仍可用但未来会移除的能力 |
| `Upgrade Notes` | 旧版本升级注意事项、兼容性说明 |
| `Assets` | Release 附件、hash、平台说明 |

## Release 正文模板

GitHub Release 不应贴内部长历史，建议使用以下结构：

```markdown
## init_workspace v2.8.0

### Highlights

- ...

### Changes

- Added: ...
- Changed: ...
- Fixed: ...
- Security: ...

### Upgrade Notes

- ...

### Assets

- `初始化工作区_v2.8.0.exe`
- SHA256: `...`

### Verification

- B01 framework check: PASS
- Build: PASS
- Sensitive file check: PASS

### Full Changelog

https://github.com/tenbj/init_workspace/compare/v2.7.0...v2.8.0
```

Release 正文比 `CHANGELOG.md` 可以更短，但不能多出与 changelog 冲突的信息。

## 版本号规则

公开版本号使用 `vMAJOR.MINOR.PATCH`：

| 版本级别 | 当前项目中的触发条件 | 示例 |
|----------|----------------------|------|
| MAJOR | 旧工作区无法无感升级、入口规则或目录骨架出现不兼容变化 | 重构 `.system/standards` 的根结构 |
| MINOR | 新增兼容能力、新 Skill、新检查、新发布流程、新文档入口 | 新增 B08 任务进度管理 |
| PATCH | 修 bug、安全脱敏、目录链接修正、构建修复、文档小修 | 移除硬编码连接信息 |

判断口径：

- 面向用户的下载物版本优先，例如 `初始化工作区_v2.7.0.exe`。
- `output/00_系统治理_v1.12.0` 是内部治理子项目版本，不等于 GitHub Release 版本。
- `workspace-spec.json`、README、exe 文件名、Git tag、Release 标题应保持同一个公开版本号。

## Commit 信息设计

提交信息建议使用 Conventional Commits：

```text
feat(skill): add B08 task progress management
fix(security): remove hardcoded Doris connection defaults
docs(release): add changelog and release notes process
chore(release): prepare v2.8.0
```

推荐类型：

| 类型 | 进入 changelog 的位置 |
|------|-----------------------|
| `feat` | `Added` |
| `fix` | `Fixed` |
| `docs` | `Changed` 或不进入公开日志，视用户影响决定 |
| `refactor` | 通常不进公开日志，除非改变行为 |
| `chore` | 通常不进公开日志，`chore(release)` 只用于发布提交 |
| `security` 或 `fix(security)` | `Security` |
| `BREAKING CHANGE` | `Breaking Changes`，并触发 MAJOR |

scope 建议使用项目内稳定概念：

```text
skill
rules
standards
memory
release
build
docs
security
```

## GitHub 自动生成 Release Notes 辅助配置

如果后续通过 Pull Request 合并，建议增加 `.github/release.yml`：

```yaml
changelog:
  exclude:
    labels:
      - ignore-for-release
  categories:
    - title: Breaking Changes
      labels:
        - breaking-change
        - semver-major
    - title: Added
      labels:
        - feature
        - enhancement
    - title: Fixed
      labels:
        - bug
    - title: Security
      labels:
        - security
    - title: Documentation
      labels:
        - documentation
    - title: Other Changes
      labels:
        - "*"
```

自动生成内容用于“起草”，最终仍要人工删掉内部噪声，补上升级说明、资产、hash 和验证结果。

## 发布流程

建议每次发布按以下顺序执行：

1. 确认发布版本号，例如 `v2.8.0`。
2. 整理 `git log v2.7.0..HEAD`、`output/*/版本记录.md`、构建产物变化，形成 changelog 初稿。
3. 更新 `CHANGELOG.md`：把 `Unreleased` 内容移动到 `v2.8.0 - YYYY-MM-DD`。
4. 构建 exe，并计算 SHA256。
5. 运行 `B01` 体检、必要测试和敏感信息扫描。
6. 更新 README 当前版本、下载文件名、构建路径。
7. 提交发布准备：

```powershell
git add CHANGELOG.md README.md docs/GitHub发布授权与Release流程.md
git commit -m "chore(release): prepare v2.8.0"
git tag v2.8.0
git push origin main
git push origin v2.8.0
```

8. 创建 GitHub Release：

```powershell
gh release create v2.8.0 `
  "output\00_系统治理_vX.Y.Z\03_代码程序_v2.8.0\dist\初始化工作区_v2.8.0.exe" `
  --title "init_workspace v2.8.0" `
  --notes-file ".github\release-notes\v2.8.0.md"
```

## 不做事项

- 不把 `.history/` 当公开 changelog。它是备份区，不是发布说明。
- 不把 `.memory/` 写入 Release Notes。它是对话和知识恢复区，噪声太高。
- 不把所有 `output/*/版本记录.md` 原样拼接到 GitHub Release。内部治理细节会淹没用户真正关心的变化。
- 不把 `*.exe` 直接提交到 Git。exe 只作为 GitHub Release 附件上传。
- 不让 GitHub 自动生成 Release Notes 成为唯一事实源。它缺少升级提示、hash 和人工判断。

## 验收口径

一次合格的发布更新日志应满足：

1. `CHANGELOG.md` 存在，且最新版本在文件顶部。
2. Git tag、README 当前版本、Release 标题、exe 文件名一致。
3. Release 正文能回答：本次更新了什么、为什么升级、怎么升级、下载哪个文件。
4. Release 正文包含资产名称和 SHA256。
5. 内部 `版本记录.md` 与公开 `CHANGELOG.md` 不冲突，但公开日志只保留用户可见信息。
6. 发布前 `B01` 体检无 FAIL。
7. 敏感信息检查通过，`.Claude.json`、`input/`、`.history/`、`.temp/` 不误入公开提交。

## 结论

这个项目应该把 `CHANGELOG.md` 作为“对外发布更新日志”的主文档，把 `output/*/版本记录.md` 作为内部整理素材，把 GitHub Release 当作对应版本的发布页面。这样既保留工作区现有的细粒度治理能力，又能给 GitHub 用户一份简洁、可信、能指导升级的 Release Notes。
