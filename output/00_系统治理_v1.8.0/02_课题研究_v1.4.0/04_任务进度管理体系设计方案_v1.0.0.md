# 任务进度管理体系设计方案

> 版本：v1.0.0  
> 日期：2026-05-11  
> 状态：方案初稿  
> 归属：系统治理 / AI 执行恢复机制

---

## 1. 目标

本体系要解决的问题不是“记录最终发生了什么”，而是“AI 执行到一半中断时，下一次在上下文缺失的情况下仍能继续”。

核心目标：

1. 让每个正在执行的任务都有一个本地、可读、可恢复的进度状态。
2. 让上下文压缩、工具中断、会话断开、模型切换后，都能通过固定入口恢复。
3. 让 AI 知道当前任务的目标、已完成事项、下一步、风险、涉及文件和最近一次安全检查点。
4. 让最终记忆与临时进度分层，避免把大量过程噪声塞进 `.memory/对话记录` 或 `.memory/系统记录`。
5. 与现有 `B01/B02/B03/B04` 强制门兼容，不破坏当前版本备份、子项目、知识提炼体系。

---

## 2. 现有体系的缺口

当前工作区已经有三类强记录：

1. `output/`：面向成果，记录完整方案、研究、代码产物。
2. `.memory/对话记录`：面向会话摘要，记录用户问题、AI 做了什么、产出文件。
3. `.memory/系统记录` 和 `.memory/知识提炼`：面向长期治理和可复用知识。

这些记录适合“事后归档”，但不完全适合“执行中断恢复”。缺口主要有四个：

1. 缺少任务级 live 状态：下一步做什么、为什么停在这里、哪些文件已经备份、哪些还不能动。
2. 缺少恢复入口：新会话不知道先读哪个文件才能接上。
3. 缺少操作事件链：只知道最终产物，不知道中间执行到哪一步、哪个命令刚跑完、哪个假设还没验证。
4. 缺少中断前写入机制：如果还没到最终回复，B03 可能尚未写入，导致最关键的半成品状态丢失。

因此需要新增一层“任务进度管理”，定位为短中期运行态记忆，而不是替代现有长期记忆。

---

## 3. 总体设计

建议新增一个独立的任务进度层：

```text
.memory/
  任务进度/
    索引.md
    进行中/
      T20260511-1656-任务进度管理体系.md
    已完成/
      T20260511-1656-任务进度管理体系.md
    已取消/
```

设计原则：

1. `.memory/任务进度` 只记录任务运行态，不承载最终知识结论。
2. `索引.md` 是恢复入口，列出当前所有 `ACTIVE / PAUSED / BLOCKED` 任务。
3. 每个任务一个独立进度文件，文件顶部固定放“恢复卡片”。
4. 任务完成后从 `进行中/` 移到 `已完成/`，并把最终摘要写入 B03 对话记录或系统记录。
5. B01 体检应检查任务进度区结构和索引一致性，但不自动修改。
6. B03 负责最终沉淀；任务进度层负责执行中可恢复。

## 5. 写入时机

任务进度文件要在执行过程中持续更新，触发点应比 B03 更频繁。

必须写入的时机：

1. 任务开始后，完成初步理解和归属判断时。
2. 执行 B02 备份后，记录最近安全点和新的 live 路径。
3. 修改文件前，记录计划修改的文件和原因。
4. 修改文件后，记录实际变更、涉及文件、下一步验证动作。
5. 执行关键命令后，记录命令目的、结果摘要和是否阻塞。
6. 遇到阻塞、等待用户确认、需要暂停时，立刻把状态改为 `PAUSED` 或 `BLOCKED`。
7. 进入最终回复前，记录完成状态、产出文件和后续建议。
8. 任务完成后，迁移到 `已完成/` 并更新 `索引.md`。

可选写入的时机：

1. 长任务每 10 到 15 分钟追加一次 checkpoint。
2. 启动子代理或并行工作时，记录分工和回收条件。
3. 发现用户工作区已有未归属变更时，记录“不可覆盖”风险。

## 6. 状态机

任务状态建议固定为七种：

| 状态 | 含义 | 下一步 |
|------|------|--------|
| ACTIVE | 正在执行 | 正常继续 |
| PAUSED | 主动暂停或等待用户确认 | 读恢复卡片后询问或继续 |
| BLOCKED | 遇到外部阻塞 | 先处理阻塞项 |
| REVIEW | 已完成主要修改，待验证或审阅 | 跑验证或让用户确认 |
| DONE | 已完成并归档 | 不再默认恢复 |
| CANCELED | 用户取消 | 不再继续 |
| STALE | 长期未更新，需重新判断 | 先询问用户是否继续 |

`索引.md` 中只需要重点展示 `ACTIVE / PAUSED / BLOCKED / REVIEW`。`DONE / CANCELED` 可进入历史区。

## 7. 与现有强制门的关系

### B01：框架体检

新增检查项：

1. `.memory/任务进度/` 是否存在。
2. `索引.md` 是否存在。
3. `索引.md` 中的 active 文件是否真实存在。
4. `进行中/` 中是否有未被索引的任务。
5. 是否存在更新时间过久的 `ACTIVE` 任务。

B01 只报告，不修复。

### B02：版本控制备份

B02 不负责备份任务进度文件。任务进度是运行态追加记录，类似 `.memory/对话记录`，应保持轻量追加。

但 B02 完成后，必须把以下信息写入任务进度：

1. 原始路径。
2. 历史快照路径。
3. 新 live 路径。
4. 版本变化。
5. 本轮后续允许编辑的位置。

### B03：记忆管理

B03 不替代任务进度。两者分工如下：

| 层级 | 作用 | 写入频率 |
|------|------|----------|
| 任务进度 | 执行中恢复 | 高频，关键步骤后写 |
| 对话记录 | 会话摘要 | 每轮最终回复前写 |
| 系统记录 | 规则、Skill、治理变更 | 有系统治理信息增量时写 |
| 知识提炼 | 可复用结论 | output 有实质内容变更时写 |

任务完成时，任务进度文件中的最终摘要应压缩进入 B03，而不是原样复制。

### B04：子项目管理

B04 负责知识产出的归属，任务进度负责执行过程的归属。一个任务进度文件可以引用一个或多个 output 子项目，但不能替代 B04。

## 8. 建议新增 Skill：B07_任务进度管理

建议新增 `B07_任务进度管理_v1.0.0`，避免把进度写入规则散落到 AGENTS、B03 和各 Skill 中。

职责：

1. 创建任务进度文件。
2. 更新恢复卡片。
3. 追加事件日志。
4. 更新 `索引.md`。
5. 关闭并归档任务。
6. 提供恢复读取流程。

建议脚本：

```text
.agents/skills/B07_任务进度管理_v1.0.0/
  SKILL.md
  scripts/
    task_progress.ps1
```

脚本动作：

```powershell
task_progress.ps1 -Action Start -Title "任务进度管理体系" -Goal "..."
task_progress.ps1 -Action Checkpoint -TaskId "T20260511-1656-任务进度管理体系" -Message "B02 已完成..."
task_progress.ps1 -Action UpdateNext -TaskId "..." -Next "..."
task_progress.ps1 -Action Pause -TaskId "..." -Reason "等待用户确认"
task_progress.ps1 -Action Close -TaskId "..." -Result "已完成方案初稿"
task_progress.ps1 -Action Resume
```

这样 AI 不需要手写索引和时间戳，降低格式漂移风险。

## 9. 需要修改的标准与规则

若进入实现，建议按以下顺序修改：

1. `workspace-spec.json`
   - 新增 `.memory/任务进度`、`.memory/任务进度/进行中`、`.memory/任务进度/已完成`、`.memory/任务进度/已取消`。
   - 新增 `.memory/任务进度/索引.md` 必备文件。
   - 更新 `memoryCleanRules.allowedDirs`。
   - 注册 `B07_任务进度管理_v1.0.0`。

2. `工作区骨架规格.md`
   - 增加任务进度层说明。
   - 增加任务进度与 B01/B03 的边界。

3. `工作区命名规范.md`
   - 增加 task-id 命名规则：`T{yyyyMMdd-HHmm}-{中文短题}`。
   - 增加任务文件移动规则：进行中到已完成或已取消。

4. `AGENTS.md`
   - 新增强制门：进入任务后创建或恢复任务进度；关键步骤后 checkpoint；最终回复前关闭或暂停任务。
   - 保持入口文件薄，只索引制度，不展开细则。

5. `.agents/rules/memory-rules.md`
   - 定义任务进度不属于 B03 长期记忆。
   - 定义完成后如何把摘要沉淀到 B03。

6. `B01_框架体检`
   - 增加任务进度结构和索引一致性检查。

7. 新增 `B07_任务进度管理`
   - 写 Skill 文档和脚本。
   - 注册到 `workspace-spec.json` 和 `.claude/commands/`。

## 10. 推荐执行节奏

建议分三步实施，而不是一次性把所有规则改完。

### 第一阶段：最小可用

目标：先能恢复任务。

范围：

1. 增加 `.memory/任务进度` 结构。
2. 新增 `B07` Skill 和一个统一脚本。
3. 修改 `AGENTS.md`，要求任务开始、关键步骤、最终回复前写进度。
4. 修改 B01，能检查结构和索引。

验收标准：

1. 新任务开始后能生成进度文件。
2. 中断后读取 `索引.md` 能找到恢复入口。
3. 任务完成后能归档。

### 第二阶段：和现有治理闭环

目标：让进度层和 B03、B02、B04 配合顺滑。

范围：

1. B02 完成后自动提示写 checkpoint。
2. B03 收尾时读取任务进度最终摘要。
3. B04 新建或定位子项目时，把归属结果写入任务进度。

验收标准：

1. 版本备份、产出路径和恢复卡片保持一致。
2. 最终对话记录能引用任务产出，不丢关键结论。

### 第三阶段：自动恢复增强

目标：新会话或上下文缺失时自动提醒。

范围：

1. B01 检查到 `ACTIVE / PAUSED / BLOCKED` 时输出恢复提示。
2. `B07 -Action Resume` 可汇总最近活动任务。
3. 长时间未更新的任务自动标记建议为 `STALE`。

验收标准：

1. 新 AI 进入工作区后能立即看到未完成任务。
2. 用户说“继续上次任务”时不依赖聊天上下文。

## 11. 关键取舍

### 为什么放在 `.memory/任务进度`

任务进度是执行状态，不是最终成果；放在 `output/` 会污染成果区，放在 `.history/` 又不适合实时更新。`.memory` 是最接近的语义位置，但必须同步修改 clean rules，否则 B01 会误报。

### 为什么不直接扩展 `.memory/对话记录`

对话记录是摘要，不适合承载高频 checkpoint。把所有操作日志塞进去，会让长期记忆变得嘈杂，后续检索成本升高。

### 为什么需要 B07

仅靠文字规则容易格式漂移。B07 用脚本统一创建、更新、归档，可以把 AI 的负担降到最低，也能减少中断恢复时的解析成本。

### 为什么不要求每一步都写

过度记录会拖慢执行。更合理的是“关键状态转移必写，普通探索可少写”。判断标准是：如果现在中断，下次是否会因为没有这条记录而重复劳动或误操作。

---

## 12. 初版结论

建议采用“任务进度层 + B07 Skill + B01 检查 + B03 收尾沉淀”的设计。

这套体系的最小核心只有三个东西：

1. 一个固定恢复入口：`.memory/任务进度/索引.md`。
2. 一个任务级恢复文件：顶部固定“恢复卡片”。
3. 一个写入工具：`B07_任务进度管理`，负责 start/checkpoint/pause/close/resume。

它不替代现有 output 和 memory，而是在任务执行期间补上“活的上下文”。这样即使 AI 中断、上下文压缩或下次换模型，只要本地文件还在，就能先读恢复卡片，再从下一步继续。
