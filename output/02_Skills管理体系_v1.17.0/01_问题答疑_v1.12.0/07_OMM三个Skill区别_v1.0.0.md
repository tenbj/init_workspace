# OMM 三个 Skill 区别

> 回答问题：D01、D02、D03 这三个 oh-my-mermaid skill 分别是什么，有什么区别？

---

## 一句话总览

这三个 skill 是同一条 OMM 架构文档链路的三个阶段：

| Skill | 阶段 | 核心动作 | 是否改文件 | 是否联网/云端 |
|------|------|----------|------------|--------------|
| D01_OMM架构扫描 | 生产文档 | 扫描代码，生成或更新 `.omm/` 架构图谱 | 会修改 `.omm/` | 不一定 |
| D02_OMM架构查看 | 本地查看 | 启动本地 Web 查看器看 `.omm/` 图谱 | 不修改 | 不需要云端 |
| D03_OMM云端推送 | 发布分享 | 登录、关联项目、推送 `.omm/` 到 OMM 云端 | 不改图谱内容，但会上传 | 需要 |

---

## D01：OMM 架构扫描

**它是什么**：  
D01 对应原始 `omm-scan`，负责“把代码仓库变成架构文档”。它会阅读项目入口、依赖、目录边界、路由、服务层、数据流等信息，然后用 `omm write` 把内容写入 `.omm/`。

**它做什么**：

- 生成总览架构图，例如 `overall-architecture`
- 按项目实际情况选择视角，例如请求生命周期、数据流、依赖图、路由页面图、命令面等
- 对图中的每个元素继续递归分析，能拆内部结构就继续生成子图，不能拆就作为叶子节点
- 为节点补充描述、上下文、约束、风险、待办、备注等字段

**什么时候用**：

- 用户说 `omm scan`
- 用户要求“扫描架构”“生成架构图”“刷新架构图”
- 代码结构有明显变化，需要更新 `.omm/` 架构文档

**主要风险/边界**：

- 这是重流程，不能在普通问答里自动触发
- 会写入或更新 `.omm/` 文件
- 依赖 `omm` CLI；CLI 不可用时需要安装 `oh-my-mermaid`

---

## D02：OMM 架构查看

**它是什么**：  
D02 对应原始 `omm-view`，负责“把已有 `.omm/` 架构文档打开给人看”。它不负责生成架构文档，只负责本地预览。

**它做什么**：

- 先运行 `omm list`，确认项目里已有 `.omm/` 内容
- 有内容时运行 `omm view`
- 用户指定端口时透传 `--port`
- 返回本地查看地址，默认是 `http://localhost:3000`

**什么时候用**：

- 用户说 `omm view`
- 用户要求“打开架构查看器”“查看架构图”“看 .omm 图谱”
- D01 已经生成过 `.omm/`，现在只是想浏览

**主要风险/边界**：

- 如果没有 `.omm/`，不应该启动空查看器，而是提示先执行 D01
- 它是只读查看，不修改 `.omm/`
- 需要本地端口可用

---

## D03：OMM 云端推送

**它是什么**：  
D03 对应原始 `omm-push`，负责“把本地 `.omm/` 架构文档发布到 oh-my-mermaid 云端”。它处理登录、项目关联、推送和错误提示。

**它做什么**：

- 先用 `omm share` 检查登录状态和项目关联状态
- 没登录时引导 `omm login`
- 没有关联项目时运行 `omm link`
- 状态完成后运行 `omm push`
- 成功后给出云端查看地址，例如 `https://ohmymermaid.com/p/{slug}`

**什么时候用**：

- 用户说 `omm push`
- 用户要求“上传架构文档”“部署架构图”“分享架构图”
- 本地 `.omm/` 已经准备好，并且用户明确允许走云端

**主要风险/边界**：

- 需要网络、账号登录和 GitHub OAuth
- 可能遇到云端权限、免费计划限制或网络错误
- 不能在用户未明确要求时主动上传或分享

---

## 三者怎么配合

推荐顺序是：

1. **D01 扫描**：把代码结构写成 `.omm/` 架构文档
2. **D02 查看**：本地打开查看器，检查图谱是否清楚
3. **D03 推送**：确认要分享时再上传到云端

也就是说：

- 没有 `.omm/` 时，先 D01
- 已有 `.omm/` 但只想看，走 D02
- 想给别人看云端版本，才走 D03

---

## 最简单的判断法

如果你脑子里问的是：

- “这个项目架构是什么？” → D01
- “已经生成的架构图在哪看？” → D02
- “怎么把架构图发给别人？” → D03

这三个 skill 不是互相替代关系，而是“生成、查看、发布”的流水线。
