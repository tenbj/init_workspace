# Skills 管理系统解决方案

> 系统性分析当前 Skills 体系面临的管理困境，从用户视角和 AI 视角分别拆解问题，提出分层解决方案。

---

## 一、问题全景

用户提出了四个关联问题：

1. **用户查找效率**：斜杠命令调用 Skill 时，15 个 Skill 已经难以快速定位
2. **规模趋势**：Skill 会持续增长，问题会恶化
3. **AI 模型调用**：大模型是否也有同样的困难
4. **版本管理缺失**：Skill 有升级但无版本号，无法追踪变更

## 三、AI 模型如何调用 Skill

### 3.1 机制说明

当用户在对话中提出请求时，AI 调用 Skill 的完整流程如下：

```
用户发送消息
    ↓
系统 Prompt 注入所有 Skill 的 name + description（摘要列表）
    ↓
AI 根据用户意图匹配最相关的 Skill
    ↓
AI 用 view_file 工具读取该 Skill 的 SKILL.md 完整内容
    ↓
AI 按 SKILL.md 中的指令执行操作
```

**关键机制**：
1. **每次对话开始时**，系统 Prompt 会注入所有 Skill 的 `name` + `description`（即 YAML frontmatter 中的两个字段）
2. AI **不会**提前读取所有 SKILL.md 的完整内容——那样会消耗太多 Token
3. AI 依赖 `description` 字段进行**语义匹配**：用户说"帮我查建表语句"→ AI 扫描所有 description → 匹配到"Doris建表语句查询"
4. 只有匹配成功后，AI 才会去读取 SKILL.md 全文

### 3.2 当 Skill 数量增长时，AI 会有困难吗？

**短期（15-30 个）**：**基本无困难**。

- 每个 Skill 的摘要（name + description）约 50-100 字
- 30 个 Skill 的摘要总量约 1500-3000 字 ≈ 2000-4000 Token
- 对于 128K-200K 上下文窗口的模型来说，这是微不足道的开销
- 语义匹配在这个规模下准确率很高

**中期（30-80 个）**：**开始出现边际效应**。

- 摘要区膨胀到 4000-8000 字，仍在可接受范围
- 但 **description 歧义度上升**：多个 Skill 的功能描述可能重叠
- AI 可能出现 **误匹配**：把"DWD字段信息Excel生成"和"1对1DWD单表SQL生成"搞混
- **解决方案**：更精确的 description + 分域前缀 + tags

**长期（100+ 个）**：**需要结构化索引**。

- 摘要列表变成"大海捞针"
- 需要引入 **分层索引**：域 → 子域 → 具体 Skill
- 或引入 **Skill 路由器**（meta-skill）来做二级分发

### 3.3 AI 的核心优势与劣势

| 维度 | AI 的情况 | 人类的情况 |
|------|----------|----------|
| 列表扫描 | ✅ 每次都完整扫描所有 description，不遗漏 | ❌ 肉眼扫长列表容易跳过 |
| 语义理解 | ✅ 能从模糊描述中匹配意图 | ⚠️ 需要记住每个 Skill 的名字 |
| 名称记忆 | ❌ 不记忆上一次会话用了哪个 Skill | ✅ 人类有肌肉记忆和使用习惯 |
| 歧义处理 | ⚠️ description 重叠时可能选错 | ✅ 人类凭经验知道该用哪个 |
| 扩展性 | ⚠️ Token 开销随数量线性增长 | ❌ 人类注意力有限，超过 20 个就很难管理 |

**结论**：AI 在 30 个以内基本没困难，但超过 50 个时需要分层索引。**用户的痛点比 AI 的痛点来得更早、更急**。

## 四、Skill 版本管理缺失分析

### 4.1 为什么现在没有版本号

- 当前工作区的版本控制体系是为 **output/ 子项目** 设计的
- `.agents/skills/` 的备份使用 FOLDER 模式——整文件夹快照到 `.history`，但 **live 文件夹不改名**
- Skill 文件夹名不含版本号（唯一例外：`01_同步代码仓库_v1.0` 是手动加的旧格式）

### 4.2 为什么 Skill 需要版本号

| 需求 | 说明 |
|------|------|
| 变更追踪 | 哪些 Skill 改过了？改了什么？ |
| 回滚能力 | 改坏了能回到哪个版本？ |
| 跨工作区同步 | 当前版本是否比另一个工作区的版本新？ |
| 依赖兼容 | Skill A 调用 Skill B，B 升级后 A 是否还兼容？ |

### 4.3 版本号应该放在哪里

两种方案对比：

| 方案 | 位置 | 优点 | 缺点 |
|------|------|------|------|
| **A：文件夹名** | `子项目管理_v2.3.0/` | 视觉直观，和 output/ 子项目风格一致 | 改版本号要 rename 文件夹，引用路径全变 |
| **B：YAML frontmatter** | `SKILL.md` 内 `version: 2.3.0` | 不影响文件夹名和路径引用，机器可读 | 肉眼不如文件夹名直观 |

**推荐方案 B**：version 写入 YAML frontmatter。

理由：
1. Skill 被多处引用（Rules、其他 Skill、脚本），文件夹改名的级联成本很高
2. `workspace-spec.json` 的 `bomCheck.files` 等字段引用 Skill 路径，路径变动需要同步修改
3. YAML frontmatter 是 Skill 的标准元数据位置，version 放这里最自然
4. 可以用脚本批量读取所有 Skill 的 version 生成报告

## 五、系统解决方案

### 5.1 方案总览

分三层解决三个问题：

```
┌─────────────────────────────────────────────────┐
│  第 3 层：Skill 注册表（技能清单.md）             │  ← 人类友好的索引
├─────────────────────────────────────────────────┤
│  第 2 层：Skill 元数据标准化                      │  ← 机器可读的分类+版本
├─────────────────────────────────────────────────┤
│  第 1 层：YAML frontmatter 扩展                  │  ← 数据源头
└─────────────────────────────────────────────────┘
```

### 5.2 第 1 层：扩展 YAML frontmatter

在每个 SKILL.md 的 frontmatter 中，新增标准化字段：

```yaml
---
name: 子项目管理
description: 子项目文件夹创建与管理技能...
version: 2.3.0                    # 新增：语义版本号
category: 系统治理                 # 新增：所属域
tags: [子项目, 文件管理, 创建]     # 新增：检索标签
trigger: auto                     # 新增：触发方式（auto/manual/slash）
metadata:
  short-description: 创建并管理 output/ 下的子项目文件夹
  last-updated: 2026-05-08
---
```

**字段规范**：

| 字段 | 必填 | 类型 | 说明 |
|------|------|------|------|
| `name` | ✅ | string | Skill 显示名称 |
| `description` | ✅ | string | 完整功能描述（供 AI 语义匹配） |
| `version` | ✅ | semver | 三段式版本号，新建默认 `1.0.0` |
| `category` | ✅ | enum | `系统治理` \| `数仓开发` \| 未来可扩展 |
| `tags` | ⚠️ | string[] | 检索关键词，辅助 AI 匹配 |
| `trigger` | ⚠️ | enum | `auto`（规则强制）/ `manual`（用户调用）/ `slash`（斜杠命令） |
| `metadata.short-description` | ⚠️ | string | 一句话描述（≤20字），用于 UI 展示 |
| `metadata.last-updated` | ⚠️ | date | 最近修改日期 |

**版本号升级规则**（与子项目一致）：

- MAJOR：Skill 接口/行为不兼容变更（如参数改名、流程重构）
- MINOR：新增功能、新增步骤，向下兼容
- PATCH：修错别字、调格式、微调描述

### 5.3 第 2 层：Skill 分类体系

按职能域划分，当前合理分为两大类：

```
.agents/skills/
├── [系统治理域]
│   ├── 创建技能/          → 元 Skill（管理 Skill 自身）
│   ├── 安装技能/          → 元 Skill
│   ├── 子项目管理/        → 框架 Skill
│   ├── 版本控制备份/      → 框架 Skill
│   ├── 记忆管理/          → 框架 Skill
│   ├── 框架体检/          → 框架 Skill
│   ├── 课题研究/          → 方法论 Skill
│   └── 项目规范化/        → 框架 Skill
│
└── [数仓开发域]
    ├── 01_同步代码仓库_v1.0/  → 基础设施
    ├── 数仓生产库查询/        → 基础设施（底座）
    ├── Doris建表语句查询/     → 基础设施
    ├── 临时数据存储/          → 基础设施（沙盒）
    ├── 1对1DWD单表SQL生成/   → 开发流程
    ├── DWD字段信息Excel生成/ → 开发流程
    └── ODS-DWD-一键生成/     → 编排 Skill（调用多个子 Skill）
```

> **注意**：分类信息通过 YAML `category` 字段实现，**不改变文件夹的物理目录结构**。不创建 `系统治理/`、`数仓开发/` 子目录——那会破坏所有现有路径引用。

### 5.4 第 3 层：技能清单（人类索引）

在 `.agents/skills/` 下创建一个 `技能清单.md`，作为人类快速查阅的入口：

```markdown

> 按域分组，快速定位所需 Skill。斜杠命令调用时参考此表。

## 系统治理

| Skill | 版本 | 一句话 | 触发方式 |
|-------|------|--------|---------|

| 版本控制备份 | v3.1.0 | 修改文件前必须备份 | 自动 |
| 记忆管理 | v2.0.0 | 回复后写入对话记忆 | 自动 |
| 子项目管理 | v2.3.0 | 新话题时创建子项目 | 自动 |

|-------|------|--------|---------|
```

### 5.5 版本控制与备份整合

Skill 的版本控制应与现有备份体系**对齐但不耦合**：

```
修改 Skill 时：
    1. 调用 backup.ps1 -Mode FOLDER → 快照进 .history
    2. 修改 SKILL.md 中的 version 字段 → bump 版本号
    3. 更新 技能清单.md 中对应行
    4. 写入 .memory/系统记录/技能变更记录.md
```

**与子项目版本管理的区别**：
- 子项目：文件夹名含版本号，backup.ps1 自动 rename + bump
- Skill：文件夹名**不变**，版本号在 SKILL.md 内部管理，手动 bump

这是**刻意的设计差异**——Skill 路径被多处硬编码引用，改名成本太高。

### 5.6 自动化脚本建议（未来）

当 Skill 超过 30 个时，可以考虑增加：

1. **`skill-catalog.ps1`**：扫描所有 SKILL.md → 自动生成/更新 `技能清单.md`
2. **`skill-version.ps1`**：批量查看所有 Skill 版本号
3. **`skill-search.ps1`**：按关键词搜索 Skill（基于 tags 和 description）

## 七、结论

1. **用户痛点最急迫**：斜杠菜单中扁平列表 + 无分类 = 15 个就很难找了。解决方案是创建**分域技能清单**，作为人类的快速索引。

2. **AI 暂时没困难**：当前 15 个 Skill 的 description 摘要总量约 2000 Token，语义匹配准确。但超过 50 个后需要分层索引。

3. **版本管理必须补上**：在 YAML frontmatter 中加 `version` 字段，不改文件夹名。利用现有 FOLDER 备份模式做历史快照。

4. **分阶段实施**：先标准化元数据 + 建清单（1 小时内完成），再按需扩展自动化工具。
