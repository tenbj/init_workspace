# 输出契约

## 先给结果总览，再确认补数，最后分段执行

主表固定七列，不增设“数据关系”列，也不把长段技术解释塞进补数基准：

| 时间分类（含两端） | CK记录数 | 源记录数 | Doris记录数 | 差异说明 | 补数基准 | 备注 |
|---|---:|---:|---:|---|---|---|
| 起止日期：简短分类 | 实际数量 | 实际数量 | 实际数量 | 已确认差异及未查明原因 | CK / Doris源 / 无法确定 | 影响补数的风险或待处理事项 |
| 合计 | | | | | | |

- 首列按差异模式变化划分真实、互不重叠的日期区间，日期左右闭合；同一行三方数量必须来自相同日期过滤。不可用“源有/源无”的隐含记录集合冒充一个时间段的全量记录数。日期为NULL不能纳入时间参数时单独列行，不能遗漏或伪造日期。
- 分类名称直接说明现状，例如历史缺口、混合缺口、Doris未同步、已覆盖。“Doris未同步”不能含糊写为“源未同步”。实际分界依证据，不照抄案例日期。
- 补数基准只允许 **CK、Doris源、无法确定**。Doris源指目标日常ETL实际源及其取数口径，不是当前可能缺数据的Doris实体表。基准是建议判断，不等于已获得执行授权。
- 差异说明回答为什么数量不一致：共有多少、哪边独有、是否模型归并/字段变化/同步窗口等。已证事实和推测明确分开；查不到成因时写出缺少的具体证据，不能用“缺键”代替原因。
- 备注放执行风险与待办，例如“Id=0会被唯一键模型合并”“需核实业务重复”“无需新增补数，未全字段验收”。Id覆盖一致不等于全字段验收通过。
- 同一天CK和源均有值时继续比较业务内容。技术Id不同不证明业务不同；须核对业务标识、字段映射和出现频次，防止换Id、历史重导或旧版本被重复补入。确认一个时间段必须保留两方不同记录时，不得为强填单一基准而丢弃一方：填无法确定，并在备注清楚写出混合保留方案等待用户裁决；可在用户同意后细分为有明确业务条件的辅助表，但不伪称纯日期分段。
- 用户明确决定“Id不同即保留”时，以该保留口径为准，不再把尚未确认的最小业务键当成继续补数决策的前提；仍检验Id占位、同Id频次及目标模型。双源均需保留但原枚举无法表达时，先解释可行方案与限制，不擅自增加枚举值，不把已查清的数据情况说成未知。
- 用户提示改表/切模型后，重新用C03取当前DDL并复查Doris数量及范围，旧主键与旧计数立即标为过期；不能沿用唯一键的重跑覆盖保证到明细模型。明细模型下同Id也可重复写入，必须设计删除范围和失败恢复。
- 主表先让用户快速判断补哪些。必要的逐日明细是辅助，不默认把主表展开成大量零散日期。表后只列影响执行的卡点、缺什么和需要决定什么。
- **用户确认补数范围后**，才生成每批StartTime/EndTime、删除/读取/写入量、六参数与执行计划。探查总览不是执行分批；不能上来按500万拆批代替现状分析。


## 每表必须产出

| 阶段 | 最小产物 |
|---|---|

| 定位与探查 | 工作簿/sheet/行、三方库表、源 ETL 版本与过滤、查询时间、三方计数及键频次证据、原因分类 |
| 范围确认 | 回复窗口完整范围表及用户确认记录；候选历史、实际缺口、删除/读取/写入量和固定保护 |
| 参数 | 完整普通 SELECT/preSql、与模板匹配的六参数文件、字段位置映射、真实读取检查结果 |
| 分区 | 现状、完整审阅 DDL/失败恢复语句、权限证据、确认与执行人、执行后分区和属性回读 |
| 分段 | 每段两个日期、实际重写量、删除命中量、净补量、容量约定、状态和证据时点 |

查询失败、权限不足、证据不足、待确认、运行中、失败、数量通过、键覆盖通过、字段抽样通过与用户确认必须分别记录，不把它们压成一个“完成”。保留可恢复 checkpoint，交接时直接定位下一段与未完成检查。

## 数据验收门槛

1. 任务成功后独立查询目标。总数与逐日数验证首尾日期、占位/NULL、分区；有增量则记录共同水位及查询时差。
2. 按已确认记录粒度比较全部需要保留历史的键和出现次数。没有可靠键时使用规范化行频次等可解释方法。抽样不能证明全历史覆盖。
3. 核对原有近期数据和 Doris 独有数据是否被误删/覆盖。日常 ETL 的滚动窗口、保留策略也不能随后删除刚补历史；有风险时需另行确认修复。
4. 业务字段按映射、精度、时区和已知 NULL 默认化比较，明确哪些做全量、哪些抽样，哪些审计时间排除。出现差异需报告，不能仅凭记录数验收。
5. 无缺口仍需给出依据。用户确认验收结果后此表关闭；后续 Skill 沉淀不再重复执行生产补数。

6. 用户确认保留的断档/独有日期区间单独验收，与写前数量、键及日期/频次比较；不能只查近期保护区。最终期望集合按已确认各时间段基准组合，按本表键及重复规则处理跨段交集，不能盲目相加。解释全表CK与Doris剩余数量差，不把分段验收通过说成全表完全相同。

### 已接受差异与待办

用户选择“不补、先这样、等视图处理”时，分别记录未处理量、原因、用户决定、待办归属及已验证范围。允许结束当前例并按授权继续，不将这些记录写成“已补齐/问题已修复”。用户接受现状不证明历史由谁处理过。

允许忽略毫秒等差异时，记录适用表、字段、精度和用户确认；同时保留原始差异证据，按确认精度重新核对。不把该容差推广到其他表、业务日期边界或未接受字段；若仅键/抽样通过，应明确未全量验收业务字段。

## Excel 回写

每完成一表立即回写，不等整批。先读实际列头及已有结果位置，保留原清单；本次交付簿 R 为摘要，Z/AA 为当前 CK/Doris 数量，AB 数量结论，AC 执行状态，AD 原因，AE 证据/时点，AF 分类。该映射仅为本次实际工作簿约定，新文件应重新确认。

分类建议：历史数据差异、增量时差、模型主键归并、取数/转换口径、同步失败、混合原因、待核实；完成后可加“已补齐”。原因栏说明因果与证据，分类栏保持简短可筛选。不能把“缺键”当业务原因。

使用适用的表格技能，仅改授权单元格，避免影响其他负责人、已解决 DWD、公式、样式、筛选、合并等。全部当前数量与状态同步更新，不只更新文本；验证改动区域并提供可打开文件路径。失败时如实写当前缺口和恢复进度，不保留旧的“完整”。

## 交付与保密

用户要求经验沉淀或复盘时，逐项标明“已有规则位置、补充位置、仅本案例适用、未验证建议”。只写进案例报告或记忆不等于已加入Skill；应更新相应阶段的规则和记录模板，检查入口能否路由到它，不重复堆叠相同要求。

回复直接给出本表范围和结论，不要求用户自行从长文件寻找关键量；完整过程、参数、分段和证据落入本任务子项目。引用文件用真实完整路径。凭证、登录链接 token、原始连接配置和未脱敏日志不放入 Skill 或交付报告。说明查询时间与覆盖限制，避免把旧案例数据当实时结论。
