# 报错教训与恢复

以下为本轮真实案例，日志名和实例号仅用于追溯，不作为运行目标。

查询尚未连接就报依赖错误时，先按[查询环境与异常停点](查询环境与异常停点.md)区分包缺失与解释器搜索路径遗漏。不要直接照通用报错执行 pip install。停点统一遵循查询环境分册：无数据影响的操作/工具问题自行修复；已提交执行失败先只读诊断并报备确认，再修复重跑。

## BR明细模型的已验证教训

- BR实例623826：平台值误写两个反斜杠加u0027，DELETE收到字面转义而失败。成功模板的实际字符是一个反斜杠加u0027；核对实际字符，不数JSON展示层的反斜杠。v4成功实例623844/623845证明本模板修正后可用，不推广到其他模板。
- BR实例623841：DUPLICATE表DELETE使用CAST(Date AS DATE)被拒绝，日志明确要求二元谓词左侧为列名。本例最终以反引号包裹Date并直接比较StartTime 00:00:00至EndTime 23:59:59.999，且Date<已确认固定上限，成功。仅加反引号不能消除CAST表达式限制；不要把两个同时实施的修正说成单独验证了其中一个。其他表按类型和当前引擎验证，不试探性执行DELETE。
- 两次失败后均独立查当前数据，证实当时历史仍0、近期712738未减少，再按授权恢复。错误发生阶段必须用日志与数据验证，不能凭失败状态猜测未删。
- 全量业务行哈希及频次校验值可用于无可靠Id的明细验收，但需处理NULL、空串、空格、日期精度、小数及字段映射；说明哈希碰撞限制，不冒充逐条JOIN或把抽样称全量。BR的5991236条Id=0按行保留，不能去重。

## 1925 与空日期（业务含义）

用户确认财务 CK 的 1925-01-01 为旧写入机制产生的空日期占位，不是真实业务年份。当时源 Date IS NULL=0，CK 占位 257,445 条，源已不保留这些记录。不能凭日期异常删掉或自动改 NULL，也不能推断所有表 1925 都有相同含义。

若只补该日，StartTime=EndTime=1925-01-01；SELECT/preSql 同一范围，并使用该次确认范围的固定保护，避免节点默认宽范围误删正常历史。参数默认按源无、CK 有的范围生成，但本次启动仍必须显式传分段日期。占位记录是否应该原样保留或转换由已确认业务口径决定。

## 失败后的闭环

1. 不提交后续批次。保存实例、定义版本、启动参数、日志错误阶段及实际展开 SELECT/preSql（脱敏），检查任务是否仍在执行。
2. 判断发生在提交前、preSql 前、删除后、部分导入后还是完成后；日志读取进度如“已读768”不等于已写入768。
3. 独立查询受影响日期、NULL/占位、近期保护区的当前数量与键差异。记录删除已提交、部分落库、失败重试等可能状态，不能假设回滚。
4. 修复已证实根因，重新核对参数六件套和实际投影；预估本次重写全量，不沿用首次删除命中0。
5. 已提交失败的修复重试先报备并取得本次恢复确认，证据和参数检查完成后继续；若需恢复额外历史、扩大删除范围、改变目标或重建模型，打印新的范围和影响量并重新确认。
6. 重试只按重新设计的一段提交，回读新实例参数，成功后再查数据；误删恢复完成才能说完整。

固定保护 SQL 能限制日期范围，但不能替代字段映射、分区、实际参数和当前数据检查。节点 SUCCESS、数量相同、键覆盖和字段相同是四种不同证据，报告不可混用。
