# 三方探查与范围确认

## 输入与定位

输入是 Excel 中的 CK、Doris 对应清单。先核对实际列头；本次成功清单 F/G 为对应表、I 为层级、Q 为负责人。用户曾限制 Q=刘益廷且 I 为 ODS/DWD，之后也曾要求全量；每轮以当前指定范围为准，不把旧筛选永久写死。

记录工作簿路径、sheet、Excel 行号、完整库表名和已有进度。同名不存在先核对库名和元数据：已遇到 Doris 实际在 glcd、CK 实际在 cbebg 的情况，不直接归为缺表，也不盲目换库。优先恢复原交付工作簿，避免多份结果分叉。

批量清单按用户给定顺序推进；每组开始和阶段更新明确“第几组、目标表、当前阶段”。同一CK对应多个Doris或同一Doris出现在多行时，用完整表对及行号定位，不能只凭一侧表名覆盖记录。用户另行指定顺序时以最新指令为准。

“源”始终指 **Doris 日常 ETL 实际读取的源**。从平台目标模型→关联 ETL→跳转工作流读取线上 SQL、连接、过滤、参数、调度和 preSql，再使用 input 中相应连接核实；source_db.md 可含 SQL Server 连接。CK 代码读同名表只证明逻辑同源，仍需区分服务器、租户、库、视图和运行过滤。旧参数无法追溯时记录不确定性。无 VIEW DEFINITION 权限且用户接受按表分析时，从视图数据直接探查，不反复索要定义。

## 探查顺序：先适配、再总览、只深查决策缺口

探查的交付目标是让用户决定“补哪些、以谁为准、能否安全重跑”。每个追加查询先明确它可能改变哪项决定；不能说明用途时，暂不扩展调查。耗时增加时报告已确定范围、剩余卡点及下一条查询解决什么，不只说“继续排查”。

1. **先判适配。** 恢复本表最新用户决定和有效证据，核对CK实际来源、Doris实际源、时间字段含义、刷新SQL/preSql、当前DDL。不同来源/不同业务对象先讲清，不继续把更新时间分布当历史缺口。整表刷新按约定停下确认。相同字段名不代表同一时间口径。
2. **先交总览。** 批量取得三方总数、日期范围、NULL/占位及日期分布，用已有证据划分七列总览；同一行三方采用同一时间过滤。根据差异模式合并连续时间段，只有改变补数基准的边界才拆行。先报可确认部分和局部待定项，不因一段未查清扣住整张表。日期分布仅定位候选，不用总量相减冒充键覆盖。
3. **只查决策缺口。** 只在候选缺口、共同窗口或混合段按已确认键/频次核验；先给一条可解释的实际案例，再统计同类影响量。若用户只要结果表对照，先用结果记录；需要源SQL时才在原SQL外套案例条件，不默认倾倒长SQL。更新日期仅在语义可比且用户选择时用于辅助，不用采集时间/创建时间代替业务日期推导补数。
4. **证据足够就交决策。** 明确源有而Doris无、CK有而源无、Doris已覆盖的范围；混合段先量化共有/各自独有和冲突。原因未证实可写“当前源无，删除/归档机制未证实”，但若已证明重建来源、目标保护和范围安全，不强求物理删除日志才能给补数建议。反之仅靠总数、Id不同或时间先后，不能宣称已证明安全。

### 常见分支及调查终点

| 发现 | 下一步必须回答 | 何时不再扩展 |
|---|---|---|
| 两端不是同一来源/口径 | 具体源与业务差别、是否可直接补入 | 用户决定不补后记录并结束本例，不继续做无意义日期差值 |
| 源有，Doris无 | 源同步缺口时间和量、取数及删除窗口 | 足以给出源同步范围后，不先追每条为何历史漏采；原因影响重跑可靠性时才继续 |
| CK有，源无 | Doris是否已覆盖、哪些目标记录会被删除及能否重建 | 范围/保留口径已确认后，不将源删除机制研究挡在参数交付前 |
| 同窗两边都有且不一致 | 共有/独有/版本冲突、具体案例、单源或双源重建及日常覆盖风险 | 用户选定保留口径后停止旧分支；不能继续围绕已取消的294条方案争论 |
| 重复Id或Id=0 | 当前模型是否合并、实际受影响量、是否阻塞本次补数 | 现象本身不作为只查一半就结束的理由；在已授权只读范围内把范围和风险一起给出 |

发现重复、迟到、占位是探查结果；执行报错和确认不适配是停点。两者不能混称“异常”来替代范围交付。真实不适配、范围无法安全重建仍按用户约定暂停。若用户明确要求所有发现也先确认，遵从其更严格要求。

### 复用证据与用户裁决

- 维护本表一份当前结论：范围、补数基准、放弃部分、保护边界、是否可动日常、当前DDL/数量时点、下一步。旧方案留作过程记录，明确已被哪次决定替代，不同时拿两套方案指导执行。
- 同一有效快照内不重复查已验证的静态映射。用户改表/重跑/补数后重新查DDL或对应受影响数据；每次写入前复核当前删除命中和活动任务，不能为提速复用过期数量。
- 用户指定Id不同就保留后，按该业务口径实施，但仍检查Id=0/空键、重复频次、同Id冲突和模型能力；不再把证明所有不同Id的业务含义都不同设为决策前置条件。
- 提出双源方案时，必须先检查日常重跑会不会删掉CK历史、失败重跑会不会重复。不能先让用户确认“CK＋源”再发现模板/日常流程无法保留。
- 七列表中“补数基准”仍只填CK、Doris源或无法确定；它表达业务保留判断。可执行性和具体卡点写备注，不能把已确定业务基准仅因工具未准备就写成无法确定。双源枚举仍须用户同意，不自行扩展。
- 若不能输出补数范围，明确缺的是哪个连接/映射/业务裁决、哪项证据失败、影响哪一段及最短解法。不得泛称“缺键”“存在风险”，也不报无依据的完成比例或耗时保证。

## 四项必查与其他原因

先识别日常刷新方式：联合检查StartTime/EndTime等参数定义、源SELECT过滤、preSql/postSql和writer配置，区分只追加、主键更新、滚动日期窗口删后重取、整表刷新。日期窗口内全量重取不等于整表刷新；窗口按业务Date还是更新时间必须说明。不能只看SQL有无WHERE或表模型判断。遇到TRUNCATE、无范围DELETE、整表覆盖/替换等整表刷新证据时，向用户展示实际语句和历史补数会被清除的影响，停止补数并确认方案；不自行修改日常任务。运行实例实际参数与节点默认定义分开验证。

| 问题 | 所需证据 | 不能据此推断 |
|---|---|---|
| 是否同源 | Doris 线上 SQL/连接，CK 取数代码及可得运行参数 | 同名表不等于同一物理源和过滤 |
| 记录数是否与源一致 | 三方总数、逐日数、时间边界、NULL 与异常日期 | 数量一致不等于同一批记录 |
| CK 多出的是否为源已不保留历史 | CK 历史键在当前源缺失，当前共同窗口覆盖情况 | 当前缺失不等于已证明物理 DELETE；机制需日志/保留策略 |
| Doris 主键模型是否合并记录 | CREATE TABLE、源真实粒度、候选键重复频次与缺失特征 | DUPLICATE KEY 是排序键，不执行唯一归并；Id 唯一不等于最小业务键 |

根据差异证据按需检查增量时间差、时区、过滤条件、失败批次、类型转换、NULL 默认化、重复写入、分区遗漏及动态淘汰；不对每张表无差别展开全部根因。DWD 应复核加工口径，不能直接用 ODS 原始行补入。需要确定业务粒度时进入 C11，未经授权不自动重建为明细模型。

## 比较方法

1. 获取三方 DDL/字段、总数、日期最小最大值、NULL 数、异常占位日期数，按日分布。记录各查询时间，增量活跃区必要时选共同水位重查。
2. 对候选历史和当前共同窗口，按已验证键+必要日期比较出现频次。支持按月导出/分块累计，但必须核对分块总量、分页完整性、查询上限和截断标志；不能以 DISTINCT 去掉合法重复。
3. “缺键”应解释为具体记录键在另一端没有或出现次数不足。业务键非唯一时保留多重集合，必要时按标准化行及频次比较；不要默认所有表都按 Id。
4. 键相同字段不同时，追源与更新时间判定新旧。技术Id不同但日期重叠时，按业务标识和字段/频次继续核对是否同一业务记录换Id，不能据Id无交集就认定双方全是独有业务。历史 CK 不能覆盖源端更新后的正确值。需要业务裁决的冲突先列样例和影响量。

用户明确Id不同即保留时遵循已确认口径，记录例外：Id=0等占位值不能作为真实业务Id去重。创建时间晚于业务日期可以支持迟到历史判断，但仅靠当前滚动窗口无法证明当时任务具体为何未读取，运行日志/保留策略证据不足时保留限制。

设 H 为 CK 中当前 Doris 实际源没有的记录（按已确认粒度及出现频次）；G 为 H 中 Doris 仍缺少的记录。H 用于识别历史保留范围，G 用于识别本次实际缺口。**不能仅用总数相减或两个 MIN(Date) 推导 H/G。**

默认 StartTime/EndTime 取 H 的日期始末；实际运行按 G 所在可安全重写日期窗口分段。某天部分源数据仍在、部分 Doris 数据已在时，要明确哪些记录可重建，不能把整天标记为“源无、Doris 无”。整窗 DELETE 前必须证明窗内 Doris 独有或较新记录不会丢失；否则设计保留/重建方案并确认，不能直接照用样例。

当前源与 Doris 的问题应单独处理：源有但 Doris 没有属于当前同步缺口；CK 多但源和 Doris 已一致可能是历史；CK/Doris 键齐而字段不同可能是更新或默认化。最终目标是 Doris 覆盖经确认应保留的当前源与历史，未必等于 CK 全表。

### 历史内部断档与精准日期保留

在候选历史最小/最大日期之间检查逐日分布，不能把整个外包日期区间都当成CK可重建的连续历史。发现CK为0而源或Doris有记录的连续日期时，单列三方数量、日期边界和拟保留量，区分“CK自身断档”和“Doris漏同步”。源也为0时不能推断业务本来没有记录；Doris独有记录也须列出。

是否保留由用户决定。用户要求不按Id保护、但允许精准日期保留时，优先提出能够由日期完整表达的例外区间；不能将它扩展为全部混合历史都保留。用户确认断档且不再追查后，记录证据限制并停止根因扩展，继续其他可执行区间。

确认保留的区间必须同时进入取数/删除保护和分段，具体见六参数分册。相同日期内两侧混杂时，不能假装用两日期已实现逐条保护，应说明仍需的记录条件或裁决。

### 证据对象不能混称

每项比较标明对象是“CK实际落地表”“旧CK取数SQL在当前源复算”“Doris实际源”还是“Doris落地表”，并记录时点。复算用于定位逻辑，不能当作旧CK已存数据；用一条CK落地记录印证案例，也不能升级为CK落地全表已验收。视图定义不可见时，实验结果等价只证明本次数据结果一致，不证明视图内部实现。

一段Doris数据与CK或当前源一致，说明它们可作为当前验收依据，不证明这些数据过去一定由CK或某人导入。实际导入来源需任务记录；用户接受现状时无须为此继续追溯。

## 必须打印在回复窗口的确认内容

使用 assets/范围确认与执行记录模板.md，至少展示：

- 完整表对、Doris 实际源、证据时点与来源确定程度。
- 按输出契约七列时间总览展示三方数量、差异说明、补数基准（CK/Doris源/无法确定）与备注；候选历史H、实际缺口G及其业务比较依据另作简短说明。
- 明确能否得出可供决策的结论、卡在哪以及还缺什么，不把只查到重复Id等中间现象当作范围交付。
- 先确认需保留范围，之后才列每批StartTime/EndTime、读取/预计写入/删除命中/净补记录数、保护边界及分区变更；执行前确认具体删除与重写范围。

用户需在这里确认本表补数范围，不能只给附件让其猜范围。确认后的同一计划继续执行；新缺口、扩大删除窗口或改变冲突处理需要重新确认。没有缺口则只验收回写，不创建运行实例。

范围或分段与上次展示不同时，先列“原方案→新方案→调整依据”，明确新增/排除/保留的区间、数量及净补量变化。业务范围或保留基准改变仍需确认；仅在已授权范围内按容量拆分时说明拆分依据，不将技术分段冒充业务边界变化。确认后同步六参数、分段表及验收期望，旧稿注明被替代。
