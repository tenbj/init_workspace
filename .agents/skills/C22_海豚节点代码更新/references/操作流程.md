# 操作流程

## 输入和职责

最小输入：模型完整表名、环境、目标代码文件与来源提交/分支、更新意图和当前授权停点。模型关联可从平台读取，不重复索要已有证据。记录项目、工作流、节点真实名称和代码，不凭截断名称操作。

- 承接 C19 已发布代码和提交；需要同步本地仓库时按 C01 适用范围处理，不为读取文件执行强制覆盖。
- 优先使用既有本地GitLab仓库。核对远端和提交，需要最新远端时fetch后取指定ref文件；不能把旧本地master当最新，不强制切分支或覆盖工作区。
- 用户指定本次MR代码则核对MR提交；指定最新已合入主线则核对远端主线。来源有实质差异时问清，不自作选择。
- 已有模型加字段不额外套用等待MR合并的门；新模型创建归 C20，实体字段增加归 C21，SQL不能代替建字段。

## 1. 定位与准备

1. 列出**当前执行代理自己的**浏览器页，将数据平台目标页置前；每次切页后，在下一次交互前重新置前并确认页面身份。浏览器页、pageId和登录态不默认在代理间共享；子代理应自行列页和取快照，不能直接使用主代理的pageId或UID。使用已授权登录方式，不输出访问密钥、Cookie或密码。
2. 数据平台模型列表按完整库表定位唯一模型，从目标模型行打开关联ETL→跳转工作流。本次实测入口为模型行菜单→关联ETL→跳转工作流，以现场标签和悬停提示为准，不固定坐标或UID。禁止默认从侧栏独立海豚入口或裸URL开始查找关联工作流。
3. 若误入独立入口并看到登录页，停止输入凭据，回到数据平台模型记录按上述关联路径进入；该登录页不证明既有平台登录态失效，也无需要求用户重复登录。只有正确入口实际要求登录且当前会话确无可用认证时，才请求用户处理登录。
4. 详情复制完整名称，回工作流定义页，在右上角搜索框粘贴完整名称并点击查询。核对目标行完整名称、项目、工作流ID和节点归属。搜索可能同时命中带后缀的存量或测试流程，只能操作完整名称完全一致且ID匹配的行；无法唯一确认则停止写入。
5. 记录工作流及原定时状态、原调度配置。检查活动实例；有同范围写入冲突时不强停或叠加运行，说明实际冲突并问清处理方式。
6. 读取当前代码与参数，和来源比较。已有新字段不重复添加；处理期间来源变化则重做差异核对。下线前确认整块粘贴、编辑器全文回读及实际停止的可用方式；只有逐字输入能力时，不先下线原流程。

AI新开的辅助标签用完后，切回并置前保留的工作标签；确认只关闭AI新开的辅助标签，不关闭用户原有标签或未保存配置的工作流窗口。返回工作页仅指激活保留的标签，不使用浏览器Back或重新导航。

## 2. 下线和编辑

1. 每次下线前重新在右上搜索框定位完整工作流名称，查询后以最新页面核对准确目标行，再点该行下线；确认弹窗前再次核对来源行，确认后回读。工作流下线可能连带定时下线，记录实际结果。
2. 点击编辑、打开节点，找到真实运行内容：SQL节点的SQL、DataX参数/JSON、Shell代码或引用资源等。资源更新方式未确认时不擅自替换公共资源。
3. 仅改授权代码及必要映射，保留连接、环境、Worker、租户、前后置SQL、日期、依赖和其他节点，除非任务包含这些修改。
4. DataX走专门分册；其他类型按现场证据处理，不把DataX表示法套给SQL/Shell。
5. 用户要求先填好、先到这里、不要提交，即停在对应阶段，不能继续点确定/保存/上线。明确授权后常规确认继续，不反复请求批准。

## 2.1 代码整块录入与保存前回读

这是每次代码替换的必经步骤，执行共用规则的“多行代码整块录入与双重回读”；不能把读取了正确文件等同于录入方式正确。

1. 锁定已确认的本地代码文件及ref，读取完整文本，记录来源哈希、字符数和换行数；不从会压成一行的预览重建代码。SQL、DataX JSON、Shell均整块录入，禁止用`type_text`、`keyboard.type`逐字符发送整个文件。
2. 目标标签置前，打开准确节点的代码框，将源文件完整复制到剪贴板，在编辑器全选并粘贴一次。工具名称包含“填入/输入”不代表整块粘贴，先核对实际行为；能力不可用就停下说明，不更换成逐字输入，不靠分段键入拼整份代码。
3. 粘贴结束后把剪贴板改成**本次唯一临时标识**，再在目标代码框全选复制，确认标识被替换且取得全文，排除源文件旧值造成的假一致。不要把Monaco虚拟textarea的一段值、当前可见行或行数相同当作全文。
4. 源文件与复制结果只统一CRLF/LF后进行区分大小写的逐字比较；保留缩进、注释、末尾换行及其他空白。差异不为0、标识未被替换或全文未取到时，不点节点“确定”，也不保存、上线或运行。记录比较结论和字符数、换行数或文本哈希；含敏感配置时不输出或保存原始正文。
5. 一致后才进入第3节的节点确定和工作流保存。保存后从持久化定义再核对完整代码、版本及其余参数。编辑器验收和保存回读必须分别成功。

### Windows实测整块粘贴方式

使用现有工具能力，不安装软件、不改浏览器权限或编辑器设置。变量由本任务的已确认文件指定；其他系统使用等效整块粘贴/全文复制能力，执行相同验收，不照搬Windows命令。

```powershell
$codeSourceText = Get-Content -LiteralPath $codeSourcePath -Encoding UTF8 -Raw
Set-Clipboard -Value $codeSourceText
```

随后通过浏览器工具点击准确代码框→`Control+A`→`Control+V`。粘贴完成后：

```powershell
$codeCopyMarker = 'CODE_COPY_CHECK_' + [guid]::NewGuid().ToString('N')
Set-Clipboard -Value $codeCopyMarker
```

通过浏览器工具在**同一代码框**执行`Control+A`→`Control+C`，再比较：

```powershell
$codeEditorText = Get-Clipboard -Raw
if ($null -eq $codeEditorText -or $codeEditorText -ceq $codeCopyMarker) {
    throw '未取得编辑器全文，禁止确定或保存'
}
$codeSourceLf = $codeSourceText.Replace("`r`n", "`n")
$codeEditorLf = $codeEditorText.Replace("`r`n", "`n")
if ($codeSourceLf -cne $codeEditorLf) {
    throw '编辑器与来源文件不一致，禁止确定或保存'
}
[pscustomobject]@{
    exactMatch = $true
    markerReplaced = $true
    sourceCharacters = $codeSourceLf.Length
    editorCharacters = $codeEditorLf.Length
    sourceNewlines = ([regex]::Matches($codeSourceLf, "`n")).Count
    editorNewlines = ([regex]::Matches($codeEditorLf, "`n")).Count
} | ConvertTo-Json -Compress
```

命令跨进程执行时，源路径、源码文本与临时标识应由本次已确认状态重新取得或由受控会话保存，不能假设前一进程变量仍存在。末尾换行可能使编辑器多显示一个空行，按全文比较判断，不为匹配显示行数删除换行。没有全文一致证据，不把“粘贴动作完成”报告成代码更新完成。

## 3. 保存与回读

1. 在节点设置中点击“确定”，回到工作流编辑页。
2. 点击编辑页顶部“保存”，打开“基本信息”弹窗，核对完整工作流名称，保留原执行策略和全局参数。运行补数的并行度只在运行弹窗配置，不能为了补数把此处“串行等待”改成“并行”；若误选但未保存，恢复原值后再保存。用户另行明确授权修改定义策略时，作为独立变更处理，不从补数授权推导。
3. 已授权上线时，勾选弹窗最下方的“是否上线工作流定义”，再点击“确定”。此动作保存并直接上线工作流，随后返回工作流定义列表，无需再另点工作流上线。
4. 从持久化定义回读SQL、参数、版本和ONLINE状态；定时上线是独立动作，保存时勾选上线不等于恢复定时。

保存后回读比较沿用第2.1节的完整源文件，只统一CRLF/LF，不忽略其他差异。编辑器中一致不等于持久化一致；自动预览压成单行、内容丢失或回执不明时，停止后续动作，先核对真实保存版本和代码，不能连续点击保存或直接试跑。

读取可复用已登录页面中观察到的同源查询请求；生产写入沿可见界面完成，不绕过带教流程。凭据仅用于获准访问，不打印请求头。

## 4. 上线与试跑

1. 返回工作流定义后重新在右上搜索框定位完整名称，核对目标行再点上线、确认。提示配置定时可先取消，按授权阶段恢复原定时；取消不是完成收尾。用户要求不试跑时，禁止点击运行或触发新实例，保存回读通过后转第5节恢复原定时。
2. 试跑：完整名搜索定位目标行，点击“运行”，在“启动前请先设置参数”弹窗直接点击“确定”；保留现有默认配置，不自行修改租户、Worker、环境、通知、补数、空跑或测试选项。节点已有环境配置时，不因运行弹窗环境为空而主动补改。若发现有证据的配置冲突，说明冲突后再按授权调整。
3. 日期参数和preSql写入范围一致。一次普通运行不等于全历史补数，不擅自勾选补数、空跑、测试或扩大日期。
4. 点击一次运行确认，记录新实例。页面成功只说明提交成功，不代表作业完成。
5. 确认已启动后点击左侧“工作流实例”，按完整名称、本次启动时间和实例ID定位；刷新观察状态直至终态。齿轮转动只表示运行中，不能据此宣称成功。实例整体SUCCESS即通过运行状态验收，直接进入下一步，不再打开成功节点详情或日志。数据范围及数量核验放在正式更新验收阶段，已知零行成功不能替代有数据验证。
6. 失败时进入本次实例，打开失败节点的日志，保留脱敏报错和上下文，分析原因并反馈；已授权修复至成功时，针对原因最小调整、重新保存上线后再试跑，重复到成功或确有外部阻塞。每次重试记录原因、改动、日期与实例，禁止未分析就原样循环运行。

## 5. 恢复定时并收尾

**试跑成功后必须恢复本次编辑前在线的定时**：右上搜索框重新查询完整名称→核对目标行→定时上线→确认→回读。保留原调度配置，不新建定时。用户明确要求“更新、上线并恢复原定时，先不要试跑”时，保存回读通过后直接恢复定时，不以试跑作为前置条件。完整更新授权包含恢复原定时，用户另有停点则遵守并记未恢复原因。

要求试跑的任务以工作流和各节点成功、原定时恢复作为完整验收；明确不试跑的任务以持久化代码一致、工作流上线、原定时恢复作为本轮验收，明确注明“未试跑，运行结果未验证”。原无定时、原有意下线、用户要求保持关闭的情况，记录不适用/保持关闭，不擅自启用。失败阶段如实记录当前状态，修复成功后继续收尾，不能遗忘定时。

## 6. 正式历史更新与最终验收

**提交前必须在对话中公布完整计划**：模型、补跑总范围、参数名和实际值、分几段、每段数据量/预计运行次数、执行顺序、已完成与待执行部分、失败后的缩批或修复策略。不能只说“逐日跑”“分批跑”，也不能仅落盘后立即提交。区间进度分组与真正一次SQL执行的范围必须区分；参数能力与期望批次不匹配时，先说明并确认处理方式，再执行依赖该选择的剩余任务。

1. 用户已授权历史更新时，试跑成功、原定时恢复后仍不算模型结束。读取SQL中的真实参数、DELETE与INSERT日期条件、源数据保留范围和目标业务日期最小/最大值，确定本次应更新的完整范围；用户指定范围优先。近期试验范围不能替代正式历史范围。源数据缺失时不能先删目标历史。
2. 统计各日期或月份的数据量，结合字段宽度、关联和排序开销拟定批次。约500万行是同时运行任务合计处理量的经验尺度，不是历史范围总量或内存保证。区间SQL可评估半年、季度等批次；逐日补数已由调度器拆成单日任务，整段累计超过500万不等于一次SQL处理500万，不必因此另按半年拆日期。两种方式均以实际运行证据调整负载。
3. 回到“工作流定义”，先清空右上角搜索框，输入完整工作流名称，点击查询，核对唯一准确行和ID，再点“运行”。
4. 正式运行分两类，不可混为一谈：
   - **按代码区间参数运行**：在“启动参数”中逐项添加代码使用的起止日期等参数和值，其余默认配置不改。适用于SQL自身处理日期区间。
   - **按调度日期补数**：单日SQL使用默认日期表达式（如`$[this_day(yyyy-MM-dd)]`）时，点击“运行”→勾选“是否是补数”，设置调度日期，由调度器按日期生成每日实例；本案例不填启动参数，不能固定bizdate使所有实例处理同一天。无需为此修改SQL为起止日期，也不逐日手工点击数百次。
   - 对照SQL中参数实际含义、原cron和时区核算每个实例的业务日期及实例数。日期范围按调度时刻覆盖首尾日，例如每日14点的流程，末日00点会漏掉末日14点。按日历补数会包含原目标无数据的日期，不能把现有有数据天数直接当作生成实例数；需明确补齐或排除这些日期。
5. 每批只提交一次并记录参数、实例ID和状态，进入“工作流实例”刷新跟踪。失败查日志；内存不足时先缩小受支持的范围，其他错误按原因处理，不把所有失败都归因为内存。只重跑失败或未完成范围，不重复提交仍运行的同范围实例。
6. 所有计划批次成功后，核验日期覆盖、数量与新增字段结果，确认工作流和原定时状态。按调度/业务日期去重计算完成量，另记成功、运行、等待、失败实例数；重复实例不能抵消未执行日期，最早成功日期也不代表到该日的连续区间全部成功。最终分别交付代码上线、默认试跑、正式历史更新和数据核验结果，未完成范围必须明确列出。

## 6.1 按运行方式分流：原流程参数运行与专用补数副本

**最新规范（2026-10-16用户再次明确修订，替代此前“历史运行一律复制”）**：

- **时间区间参数运行**：原工作流搜索定位→检查实际DAG及节点内容→确定运行起点、执行方向和节点范围→启动参数填写代码真实使用的起止日期。不勾选“是否是补数”，不建副本，不删除原依赖，不改原策略/定时。分批串行，前批成功再提交下一批；不同分层可以采用不同批次范围，不为操作统一强行同批。
- **海豚补数模式**：试跑成功后才复制专用补数副本，删除副本内的DEPENDENT依赖节点及相应连线，确认剩余执行关系完整、目标SQL及必要后续节点仍在，再保存上线并按调度日期补数。原工作流及其依赖保持原样。原生补数才按日任务负载评估并行度。
- **无有效区间参数的整表重算**：同样先判断节点范围，在原工作流执行一次所需链路，不因节点参数列表残留StartTime/EndTime而填入无效值，不拆成多个全表覆盖任务。等待上游正式更新完成。

**执行节点范围必须判断，不能套固定选项**：

1. 读取当前持久化DAG，检查SQL前后的节点类型、代码/动作、参数传递和分支汇合。允许绕过前置调度依赖检查，不等于可以省略前置业务准备；确认数据和业务前提已具备。
2. 逐个判断SQL后续节点是否属于本次更新所需步骤，例如继续加工、统计、质量校验或结果发布；核对历史日期是否传递正确、是否会全表操作或触发额外外部动作。必要节点必须纳入执行范围，不能因其不是SQL而跳过；明确无关的节点说明排除理由。额外外部动作遵守既有授权边界。
3. SQL及所有后续节点都需要执行、分支前提已满足时，选“向后执行”（TASK_POST），并核对实际起点与覆盖范围。没有后续节点，或后续节点已逐项确认不属于本次范围时，才可选择“仅执行当前节点”（TASK_ONLY）。混合分支不能用两个选项强行简化；核实平台可支持的选择方式，无法实现所需范围时先说明具体限制，不擅自漏跑、扩跑或改原定义。
4. 运行前在对话公布起点、执行方向、执行与跳过的节点及理由。提交回执核对范围；所需节点所属实例整体成功才进入下一步，不能以SQL单节点成功替代整条必要链路成功。整体成功仍无需打开节点详情或日志。

上述判断也适用于原生补数副本：删除依赖后，仍需保留并执行必要业务节点。只跳过依赖检查，不应机械推导为“仅执行SQL”或“一律向后执行”。

依赖模式OFF_MODE是关闭下游工作流联动，不等于删除内部DEPENDENT；补数副本的依赖节点必须实际删除并回读。删除范围仅限副本中的依赖节点，不连带删除SQL或其他业务节点。遇到非线性DAG先确认保留节点的执行路径，不能把删依赖等同删除全部非SQL节点。

需要复制时，先查已有副本与活动实例，能安全复用则避免重复创建。用完整名称和原工作流ID锁定来源，复制后加明确补数用途及任务日期标识（backfill即历史补数，可用清楚的中文说明）；记录源/副本项目、工作流和SQL节点ID映射。回读SQL换行、参数、前后置SQL、连接、环境和Worker与来源一致；节点关系仅允许本次删除依赖造成的预期变化。复制后的节点ID重新读取，不沿用原节点ID。平台实测批量复制会连带复制定时配置但保持OFFLINE，必须核验副本定时关闭，不把副本接入日常下游依赖。原定时保留，补数范围若与正常写入冲突，先协调窗口。

副本根据计划设置串行或PARALLEL，保存上线；运行时按已公布计划选择补数、并行度和日期。复制只隔离调度配置，写入的仍是同一生产表，范围与负载核验不能省略。全部成功、数据核验通过且无活动实例后，下线副本，保留实例和映射；回读原工作流及定时。没有明确删除要求不删除副本或实例。本次已实测复制副本参数运行成功；新指定的“删除依赖后原生补数”路径尚待后续现场验证，不能混称已实测。

下述为历史已授权仅SQL补数的操作记录与例外路径，不是参数运行或专用补数副本的默认节点范围。仅在源数据已具备、实际DAG判断支持仅SQL且用户授权覆盖该范围时适用；不能据此遗漏必要后续节点。原流程参数运行保留全部依赖定义；原生补数副本按上文删除依赖并执行判断后的必要链路。临时修改原策略的第4–6步仅作为用户另行明确指定的例外，不是新任务默认路径。

1. 右上角完整名搜索、核对项目与工作流ID后打开当前持久化版本。图中右键目标SQL节点→“运行”→选择“仅执行当前节点”→勾选“是否是补数”。依赖模式关闭，只补当前模型；根据代码设置执行方式、并行度和顺序。单日默认日期表达式不用另填启动参数。不能从普通列表运行默认就推断为仅SQL。
2. 连续日期用开始日00:00:00至结束日23:59:59，结合cron和时区核对首末调度时刻；不连续缺口可用“手动输入”填写明确的调度时间列表。输入框先清空再填写，日期输入后按Enter提交。提交前读取实际选中值，避免并行度2追加5变25、日期失焦回退、复选框未选中。自定义控件若填表工具不生效，改用可见点击/键盘选择并重新核对，不能带错值保存。
3. 提交一次后确认业务回执成功，核对本次实例的SQL起点、TASK_ONLY和补数日期，再到工作流实例观察。接口HTTP成功不等于业务成功；旧标签页可能提交过期版本，业务拒绝时先核对无新实例，再从当前定义重开。整体SUCCESS后不打开成功节点详情或日志。
4. 定义SERIAL_WAIT可能使补数配置5仍实际串行。默认保留策略；只有用户另行明确授权临时改并行时，才先停止本批未完成队列，确认无活动实例，按日期去重统计成功量并发布剩余缺口计划。停止操作用明确的停止按钮，不能混用删除；STOP不算成功，也不据此断言SQL完全没写数据。
5. 按授权下线、编辑，保存基本信息中的执行策略改为PARALLEL，勾选底部“是否上线工作流定义”保存。回读策略、版本、SQL及依赖节点未变，恢复原本在线的定时。只对缺口提交TASK_ONLY补数，通常最多5；多段或手动日期批次前一批全部终态后再提交下一批，避免总并行量叠加。记录实际同时运行数，不能只记录配置数。
6. 全部日期成功、无活动实例后，核验数据；按约定恢复原定义执行策略，保存上线并恢复原定时，回读cron、时区、策略和代码。临时改策略不改变长期调度约定。原始快照、临时版本、恢复版本均需留证。
7. 按实例ID去重后再按成功调度日期计算覆盖。分页排序不稳定可能出现相邻页重复和遗漏；终态核验若发现缺口，先扩大单页容量或按日期查询验证，不能立刻重跑。源表有记录但目标零行时，使用同版加工SELECT只读复算该日结果，区分业务过滤与漏跑。

## 7. 持续检查与通知

- 用户要求定期检查时，复用本次提交的工作流ID、版本、提交时刻、实例ID及日期范围，分页读取全部相关实例，不只看首页。记录检查时刻、去重成功日期数/计划日期数、活动实例、失败日期和最近进展；不重新点击运行来检查。
- 当前会话内按任务耗时合理间隔刷新。若需结束会话后继续检查，先查找可用定时/唤醒工具，创建或复用监控并确认成功；监控只读，正常推进或状态无变化保持安静，仅在全部完成、失败、持续无进展或需要用户处理时通知。完成后关闭对应监控；不能自动重跑、改策略或停止生产实例。
- 没有可用后台工具或创建失败时，明确只在当前会话内检查，不声称已设置定时，也不承诺离开会话后主动通知。保存恢复信息以便继续。
- 等待状态不等于失败。结合多次检查中是否新增成功日期/运行实例判断停滞；若确有异常，定位原因。只有失败才看失败节点日志，整体成功不进入节点详情。完成通知须区分调度运行全部成功和数据核验是否通过。

## 防错位检查

### 补数选项的判断依据

- **依赖模式**：官方语义是联动直接下游工作流补数，不是关闭或开启本流程内部的DEPENDENT节点。本轮仅处理当前模型时关闭；确需联动时先公布扩展范围，不能默认为所有下游一起跑。
- **执行方式**：检查主SQL及前后置SQL。区分SELECT/FROM/JOIN读取本表历史结果，与DELETE/INSERT/UPDATE以本表为写入目标；出现本表名不等于存在按日前后依赖。再检查日期隔离、全表覆盖、无日期后置更新、共享文件等副作用；无跨日依赖且资源可承受时优先并行，不能仅凭“日分区”推导全流程安全并行。
- **并行负载经验尺度**：约500万行指同时运行的并行任务合计处理量。常用3，通常最多5；数据量明确很小时可直接选5，不强制先串行或先3。例：15天总共约15万行，每日约1万，5个并行任务合计约5万，按数据量可选5。任务大则减少，单任务已近500万则串行；超过5需有用户授权及资源依据。结合最大日期偏斜、字段宽度、JOIN/排序、共享写入和实测耗时/内存评估，不把目标行数等同所有中间处理量，也不把500万视为保证。
- **工作流策略**：保存弹窗的执行策略与运行补数弹窗的并行度是两层配置。保留定义原值，只配置本次补数；即使看到SERIAL_WAIT，也不能自行下线修改策略以追求并行。分别记录提交配置与实际运行/等待状态，不能仅凭选择并行就宣称始终有5个任务同时执行。
- **执行顺序**：读取前日结果的链路按日期升序；每日独立且优先更新近日期时可降序。并行模式下排序不保证完成顺序。
- **依赖节点**：保留并核对内部运行依赖。依赖上游历史实例时，检查计划调度日期对应的成功记录；源表有数据不等于调度依赖一定通过。仅调研或配置草稿时不点击最终“确定”。

- 下线、进入编辑、上线、定时上下线等模型操作，都必须以右上角完整名称搜索结果为入口。返回列表、刷新、保存导致列表重排或切换模型后，重新查询并取得最新页面元素。
- 不沿用其他模型的按钮UID、列表行号或屏幕坐标；搜索后仍有多个相近名称时，按完整名称与工作流ID双重匹配。
- 搜索输入前先全选清空，输入后回读框内完整文本，防止填表工具把新名称追加到旧名称后；运行及正式补跑也必须重新搜索定位。
- 记录搜索词、匹配完整名称和工作流ID作为操作证据；节点编辑时再核对节点名与目标表，保存前复核只变更授权内容。

## 中断停止与恢复

用户要求停止时立即执行共用规则“停止、工具恢复与状态报告”，先停止实际动作，后分析和写记录。区分“停止派发”“结束等待”“实际输入已停止”三个状态；只有最后一项经核验才能说“已停止”。外层exec结束、工具超时或取消等待均不充当停止证据。

优先使用正常取消能力；已知当前输入占用同一服务串行锁时，不把向该队列追加快照或读取当成紧急停止。正常取消无效且需终止本任务自动化进程时，按现场窗口与进程关系核验独占归属后处理，仅停止准确对应的自动化，不批量结束node/chrome或使用旧PID。涉及其他任务、归属不明或无法确认停止时如实报告；不得继续保存/运行，不提前宣称已停。

停止后的B08 checkpoint记录：实际停止证据、浏览器/草稿状态、是否节点确定或工作流保存、是否已启动实例、最后确认的定义版本和原定时状态、下次恢复入口。紧急停止不得被这些记录动作延误。下线后中断必须保留“原定时待恢复”，不能仅说停止而遗漏生产状态。

用户授权继续后，先自行恢复可用的原工具连接、重新列页置前，从目标模型关联入口接续。正常重连不等于允许修改config.toml、软件版本、权限、MCP源码或无关服务；这些仍按用户环境授权边界确认。连接建立后先回读真实状态和已有实例，防止补录旧草稿、重复保存或重复运行。

| 情况 | 恢复动作 |
|---|---|
| 浏览器卡死/重启 | 重新列页、置前、定位；先查持久化状态和已有实例再恢复草稿，不重复启动 |
| 用户要求停止，但浏览器仍输入 | 优先核验并停止实际动作，不继续分析或排队读取；未确认前报告正在停止，不报告已停止 |
| 取消等待或exec结束 | 不能据此认定后台输入结束；按执行层证据核验，阻断保存/运行 |
| 因本任务停止工具后Transport closed | 授权继续后自行尝试现有启动/重连入口；不自动改环境，不把短暂连接错误直接推给用户 |
| 保存回执不明 | 查版本与参数是否落库，再决定是否保存 |
| 运行回执不明 | 查同时间、版本、参数的新实例，不能再次运行来验证 |
| UID失效 | 取新快照，无标签图标先悬停识别 |
| 未保存草稿 | 不随意刷新/关页；丢失后从确认来源恢复并重新比对 |
| 外部改动 | 重读版本、代码、定时，保留其他人的修改，不直接覆盖 |

关键阶段按 B08 checkpoint，最终件落当前子项目并按 B03 提炼。不额外发消息或增加运行。
