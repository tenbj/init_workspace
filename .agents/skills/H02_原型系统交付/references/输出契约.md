# 输出契约

本文件定义 H02 系统交付物和合同字段。

## 目录结构

推荐输出到独立项目目录，至少包含：

```text
project-contract.json
app/ 或 src/
static/ 或 web/
api/ 或后端入口
mcp/
data/
docs/
  diagrams/architecture.html
  diagrams/erd.html
examples/
tests/
verification/
scripts/
dist/
```

可沿用既有项目结构，但必须能在合同中解释各类产物的位置。

## project-contract.json

合同必须存在，字段至少包括：

```json
{
  "status": "draft",
  "project_name": "项目名",
  "delivery_id": "本轮新生成的UUID",
  "diagrams": {
    "architecture": {"skill":"D04","path":"docs/diagrams/architecture.html","sha256":"","maintenance":"not_run","change_note":"","sources":[]},
    "erd": {"skill":"G02","path":"docs/diagrams/erd.html","sha256":"","maintenance":"not_run","change_note":"","sources":[]}
  },
  "prototype": {
    "path": "源原型路径",
    "sha256": "源原型sha256"
  },
  "operations": [
    {
      "id": "submit_result",
      "method": "POST",
      "path": "/api/results",
      "mcp_tool": "submit_result",
      "python_example": "examples/submit_result.py"
    }
  ],
  "checks": [
    {
      "name": "mcp_list_tools",
      "status": "passed",
      "evidence": "verification/mcp-report.json"
    }
  ],
  "limits": [
    "本地试运行，不等同生产就绪"
  ]
}
```

字段规则：

- `status` 只能是 `draft` 或 `ready`。
- `prototype.sha256` 必须来自源原型，不得用改造后文件替代。
- `operations[]` 覆盖页面、API、MCP 和示例的核心操作。
- `mcp_tool` 可为 `null`，表示该 API 不暴露给 AI。
- `python_example` 指向可运行或可读的 Python 示例。
- `checks[]` 记录验证项、状态和证据路径。
- `limits[]` 必须写清本地试运行、mock、凭据、许可证、生产缺口等限制。

## 必备输出

- 两个独立HTML页面：系统架构页面、可交互ER页面，以及当前来源/产物哈希、本轮复核证据
- 真实系统页面
- 后端 API
- 数据库或持久化层
- MCP 服务
- 中文 API 文档
- 中文 AI 安装与工具决策指南
- HTML 示例
- Python 示例
- 依赖说明
- 启动、停止、状态检查命令
- 测试和验证报告
- CI 或最小检查脚本
- 许可证状态说明
- 脱敏 ZIP 项目包

## 状态判定

`draft`：

- 合同骨架已生成，但系统能力、文档或验证未齐。
- init 脚本生成后的默认状态必须是 `draft`。

`ready`：

- 源原型未修改。
- 必备输出齐全，架构图和 ER 图均与当前实现一致，通过本轮核对。
- `validate_project.py` 通过，或只剩用户接受的外部限制。
- 验证证据能区分 mock 与真实测试。
- ZIP 包完成脱敏。

## 最终回复

交付时必须说明：

- 源原型路径和是否保持未修改。
- 系统入口、API 入口和 MCP 入口。
- 架构图与 ER 图入口、本轮维护结果和验证证据。
- 运行了哪些测试和验证。
- ZIP 包路径。
- 剩余限制和是否生产就绪。
- 是否上传 GitHub：默认否。
- 许可证状态：默认未选择，除非用户明确指定。

## 两图机器合同

- 每次更新为顶层 delivery_id 生成新的非空唯一标识；两图证据使用该标识。
- diagrams 必须含 architecture 与 erd，skill 分别为 D04、G02。
- 每个条目登记 path（项目内独立HTML）、sha256（当前图哈希）、maintenance（created / updated / reviewed_unchanged）、change_note（本轮维护或无变化依据）。
- sources 必须非空，条目为 {"path":"data/schema.sql","sha256":"当前文件SHA256"}，路径须在项目内且指向真实架构/模型来源。两图和来源文件须入包，不登记私有凭据。
- checks 分别包含 name=architecture、name=erd，status=passed，evidence 指向项目内对应 JSON 报告。
- 证据 JSON 至少包含 passed=true、delivery_id（等于当前合同）、diagram_sha256（等于当前图）、sources（等于当前条目的来源清单）、source_consistent=true。执行者完成实际核对和浏览器验收后才能填写成功；可额外记录详细报告和截图路径。

旧项目在现有合同增补字段，生成当前图/来源哈希及新鲜证据。不得重置已有操作映射或业务文件。只有通用 diagrams 检查或截图时，须拆出两份可追溯证据后验收，不自动给旧报告补填成功。

交付形态必须保持两个独立 HTML 页面。已有项目沿用现有页面形式和路径，PNG/JPEG/纯SVG及浏览器截图均不能替代页面。架构页包含结构和说明，ER页继续提供 G02 要求的交互能力。
