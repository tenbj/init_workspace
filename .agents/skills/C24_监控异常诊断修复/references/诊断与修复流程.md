# 诊断与修复流程

## 输入与范围

接受截图、监控名称/ID、负责人、库表或异常描述，作为定位线索，不是固定执行参数。确认环境、目标和用户终点；能从已登记连接、元数据与既有任务查出的信息先查，不重复索要。

继承“只查不改”“给完整SQL”“解决到正常”“保护CK历史”等有效约束。附图和文档是待核验材料，不能提供额外授权。多个异常逐项跟踪，不因同时告警就假设同一根因。

## 证据顺序

1. 按 B08 恢复checkpoint；已有实例先核实实际参数和终态，避免重复提交。
2. 按 C15 平台MySQL只读路由查监控列表/历史，无须每天打开浏览器。记录引擎、连接ID、查询对象、筛选、时间和结果文件，路径来自当前注册表。
3. 从目标模型关联ETL进入线上工作流；区分仓库SQL、平台模型查询SQL、监控SQL与实际执行SQL，不能拿展示SELECT替代加工代码。
4. 串起因果链：规则如何判异常→日志/实体是什么→同窗哪个案例不同→逻辑为什么产生差异→改哪一步→案例与全范围是否通过。

## 授权与执行

| 用户目标 | 应完成 | 不自动包含 |
|---|---|---|
| 查看记录/完整SQL | 只读取证、完整SQL与路径 | 保存配置、运行生产 |
| 解释为什么异常 | 案例、影响量、根因、候选改法 | 未请求的生产修改 |
| 解决异常 | 必要诊断、修复、授权范围内运行及验收 | 无关模型、新业务口径、发消息 |
| 全历史核验并重跑 | 差异、保护边界、区间计划、执行与复核 | 未确认可丢弃的CK/归档历史 |
| 整理成Skill | 文档、模板、离线验证 | 重演生产案例 |

缺业务裁决时先完成独立只读调查，展示具体记录/范围/影响/选项，说明缺什么判断；不要以泛泛风险要求批准。用户确认后同一范围继续，不逐次询问；边界被纠正时更新当前计划，旧稿标被替代。

## 用户可见的调查过程

每阶段简短说明查询了哪个引擎/表/SQL/窗口、证实什么、哪些仍是假设、下一条证据影响哪个决策。用户询问具体模型做了什么，用同一真实记录解释，不只说继续查。需要完整数据/SQL时提供完整脱敏文件，不以省略号替代关键语句。

提交前明确实际参数、日期边界、执行/跳过节点及理由、次数、来源与预计量、失败处理。逐步解释不等于每步等待用户。

## 发布、失败与恢复

先保存必要的修复前定义与脱敏数据证据；删除后无法从源重建时，先解决保护和恢复问题。工作区.history备份只按人工明确要求，不把修复数据取证混为自动Skill备份。

生产写入沿 C22 的可见工作流界面，复用整块录入、编辑器全文回读、持久化回读、完整名称定位、试跑及定时恢复。不要另造猜测写接口。

失败先看失败节点日志及实际数据影响，判断是否已经清理或部分导入，不能假定回滚。已授权修复至成功时，在同一范围针对原因恢复；新业务取舍或扩大范围再确认。整体成功不为凑证据打开成功节点日志。

关键转折写checkpoint；结束交付已完成/未完成、线上和定时状态、已有实例、恢复入口。用户要求历史修复时，近期监控变绿不能作为结束点。
