# 历史保护与重跑决策

## 保护范围先于删除

全历史按日期、键/频次和字段核验，区分当前源、CK补入、归档保留与无效旧版本。“源现在没有”不证明目标可删。

优先寻找导入任务实际参数、成功实例和写入键清单，其次是可核实的CK对应表三方逐键核对、不可变来源字段/导入批次；日期分界、加载时间关联只能辅助判断。

业务task_id可能只是源采集批次，不能凭名称当CK/PG标志。etl_dt落在PG任务时段支持PG加载解释，但CK导入可能保留旧etl_dt，不等于不可变来源证据。未找到CK表/任务不等于从未导入。

用户接受较弱证据作为本表裁决时记录限制与明确决定后继续，不反复索取同一确认，也不推广成下一表默认规则。保护范围未定不做整窗DELETE，独立只读继续。

某日以后与源一致不证明此前来自CK，尤其不能拿刚修复后的相等日期倒推切源分界。同日混合CK和PG时，日期切分不能实现逐行保护，须明确保护键或其他可安全重建条件。真正历史补入按 C23。

## preSql参数化

只在确认可重建且允许清理的范围采用同窗删除重载。DataX下方独立配置preSql为IN/VARCHAR参数，模板引用：

```json
{"writer":{"parameter":{"preSql":["${preSql}"]}}}
```

源WHERE使用真实时间字段的日期闭区间时，目标可用等价半开区间。以下为适配示例，不可直接用于新模型：

```sql
DELETE FROM ${db}.${table}
WHERE <真实参数时间字段> >= '${StartTime}'
  AND <真实参数时间字段> < DATE_ADD('${EndTime}', INTERVAL 1 DAY)
```

核对字段、精度、时区与开闭边界；源不是日期闭区间时按实际语义推导。删读同窗、columns顺序一致，JSON转义和运行参数展开按 C22 回读。源为空不自动允许清理；检查保护集合和冲突实例。

DELETE与导入可能独立提交，失败不保证回滚。重复重载保持的是业务结果，生成审计时间可能变化，不能声称每列严格不变。

## 批次决策

**先确定允许完整重建的范围，再按真实负载与依赖决定批次。**

差异日期用于定位和验收，不自动成为执行边界。“有差异日要重跑”不等于“禁止重跑正常日”。来源完整、保护边界已确认、删读同窗、SQL支持区间、无必须逐日推进的依赖且负载适合时，优先整段一次运行，允许包含中间正常日期。

正常日从同一源按同一口径重建仍得到正确业务结果；多读少量数据通常比增加提交、参数填写、调度和核对更经济。不要机械按日/月/差异岛切分，也不机械扩大到全表最早日期。用户指定范围优先。

实际拆批理由：源保留不完整、保护集合混杂、跨日加工依赖、单批内存/耗时/源负载或失败恢复成本。结合宽度、JOIN/排序、偏斜和实测，不用单例83万行当通用安全阈值。

## 运行与验收

- 回读DAG，逐项判断必要后续统计/监控/加工；不默认只跑主节点，也不联动无关流程。
- 参数区间运行按 C22 用原工作流，不为此建副本、勾原生补数或改策略/定时。原生补数另走对应分支。
- 提交前公布目标、参数实际值、边界、读删范围、量、节点、次数和失败处理；授权已有即执行。
- 每次仅提交一次，回读启动参数和实例；分批时前批成功才继续。回执不明先查，不重复点运行。
- 近期试跑不代替用户要求的全历史；最终逐日检查全量键/字段和保护集合，不只比较总数。
