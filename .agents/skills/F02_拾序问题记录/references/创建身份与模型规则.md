# 创建身份与模型规则

## 三层含义

| 含义 | 输入 | 要求 |
|---|---|---|
| 谁发起这条问题 | creation.initiatedByPersonId | 已确认的person身份ID；不知道或没有人类发起者则省略/null |
| 谁实际录入 | creation.identityId | 本次执行技能的agent身份ID，不用人类ID冒充手工录入 |
| 用什么模型录入 | creation.modelInfo | 每次显式传对象；与工具名称分别保存，不依赖档案默认模型 |

由实际AI身份档案的via表示工具：Claude Code → claude_code；WorkBuddy → workbuddy；Codex → codex；deepseek-harness → deepseek_harness。工具与模型不是一一对应。只有用户提到某工具不能证明当前运行于该工具；以可信运行上下文为准。遇到接口不支持的工具，保留草稿并报告接口限制，不伪装成其他工具。

actor仍是审计标签，不能替代上述字段。这些信息是声明的来源，不代表登录认证或已验证的模型执行证据。

## 来源依据与复用

1. 用运行环境的明确模型信息、用户明确提供的本次模型信息或可核对配置作为依据。不得从AI自称、示例、默认档案或工具品牌推断具体模型。提供方不确定可以只给name；两者均不明时传`{}`，回读为两个空字符串。不要写字符串“未知”充当模型名。
2. 人员从用户已确认的姓名/身份ID或既有明确绑定取值；不写死“我”“太太”或Elias。过去的展示示例不构成实际人员绑定。没有明确绑定时省略发起人，保留已知AI来源；用户特意要求区分人员而无法确认时只问必要的身份选择。
3. 先list_identities。已确认ID优先；只有名称、kind、via及会话绑定能唯一确认时才按档案复用。同名多项不可随便取第一条。
4. 为完成用户授权的问题录入，可新建必要的AI身份，以及已明确要求使用且不存在的人员身份。人员必须`kind=person, via=manual`，模型为空；AI必须`kind=agent`且via为实际工具。每个身份各自生成、落盘一个请求，成功后回读list_identities按ID核对，再准备问题请求；失败或不确定时先恢复身份请求，不能另建重复身份。
5. 不自动改已有档案，不为每次模型切换新建AI身份。当前模型写到问题的`creation.modelInfo`。没有明确长期默认偏好时，新AI档案modelName/modelProvider保持空。

## 示例：Elias委托Codex，使用GPT-6.1 Sol

这是字段示例，只有这些信息在实际会话中得到确认时才能采用。假设已查询或创建得到人员ID与AI身份ID：

```json
{
  "identityId": "<Codex实际AI身份ID>",
  "initiatedByPersonId": "<Elias实际人员ID>",
  "modelInfo": {"name": "GPT-6.1 Sol", "provider": "OpenAI"}
}
```

保存后应看到`creatorName=Elias`、`createdVia=codex`、`modelInfo.name=GPT-6.1 Sol`，并分别保存AI身份ID和人员ID。自主AI录入省略initiatedByPersonId，creatorName为AI身份名。未知模型仅模型为空，不丢弃已知人员和工具；真实资料不能为了看起来完整而仿照原型补齐。

## 回读与更新

get_issue的六项创建快照为createdByActorId、initiatedByPersonId、creatorName、createdVia、createdAt、modelInfo。核对请求中的两个ID和显式模型，再逐字段与写入响应resource比较；createdAt由服务生成，不自行填写。

快照不受档案改名或默认模型变化影响。update_issue只能改用户授权的业务内容，actor表示这次编辑者，不能把历史创建者改成编辑者。旧记录原有未知来源如实保留。

重放请求不重算模型、发起人、版本或任何字段。升级前已经发送、缺少creation的原请求才可以使用脚本`--legacy-retry`；它保留原文，结果可能依旧为未知来源。该开关不允许用于新的录入，也不允许用猜测来源修补旧请求。
