## 读者实际要完成的任务

用户提供六个模型的切换清单，认为“字段映射差异”尤其难读。核心阅读动作是：找到一个模型，马上看清它切换到哪张表、哪些字段下线、每个旧字段对应哪个新字段。

材料本身的困难并非只是字多：同一个单元格同时容纳了变更类型、旧字段、新字段和模型状态；一行代表一个模型，但一个模型内部存在多条独立变化。只加换行或缩小字号，仍需读者逐句拆解。

## 输入前后的字段结构设计

### 输入：四列，一行一个模型

`旧模型表名｜新模型名称｜新模型表名｜字段映射差异`

原始“新模型名称”列实际存数据库表名，“新模型表名”列实际存中文名称，表头与内容含义错位。“字段映射差异”中同时混有四类信息：

- 下线字段，例如“顶级分类、基础Sku”。
- 字段对应，例如“SPU → 五级分类”。
- 模型适配状态，例如“已适配”。
- 数据源切换说明，例如“金蝶直连 SQL，数仓已有模型但报表尚未切换”。

### 输出：八列，一行一条变化，模型信息按组共享

`编号｜模型名称｜旧模型表名｜新模型表名｜变更类型｜原字段｜新字段｜备注`

| 输入信息 | 输出去向 | 结构设计的作用 |
|---|---|---|
| 旧模型表名 | 旧模型表名 | 保留技术定位信息；长名称按语义换行 |
| 新模型名称中的数据库表名 | 新模型表名 | 校正表头语义，保留原值 |
| 新模型表名中的中文名称 | 模型名称，放第二列 | 先用业务名称识别对象，再看技术细节 |
| 字段映射差异中的“下线/变动” | 变更类型 | 变化动作独立成列，不藏在长句中 |
| 箭头左侧字段 | 原字段 | 每条旧字段单独一行 |
| 箭头右侧字段 | 新字段 | 与对应原字段同行、相邻，直接横向对照 |
| 下线字段 | 原字段填写字段名；新字段填写“不再提供” | 区分字段消失与字段调整 |
| 已适配、尚未切换等状态说明 | 备注 | 保留状态，同时避免与字段对应关系混用 |
| 原表没有编号 | 新增编号 | 帮助识别六个模型分组，不创造业务事实 |

这里同时做了三种结构转换：把混合信息拆成有稳定含义的列；把模型行展开为多条字段变化行；把仍属于模型层的信息保留在这些行的共同分组里。改变的是表达粒度和阅读方式，未重写业务映射。

### 同一个周报的具体变化

原来只有一个“字段映射差异”单元格：

> 下线字段(顶级分类，基础Sku)；变动字段（SPU->五级分类，SPU编码->SPU，SKUID->MSkuID，上架日期->商品首单日期）

输出为同一个模型分组内的六行：

| 变更类型 | 原字段 | 新字段 |
|---|---|---|
| 下线 | 顶级分类 | 不再提供 |
| 下线 | 基础Sku | 不再提供 |
| 调整 | SPU | 五级分类 |
| 调整 | SPU编码 | SPU |
| 调整 | SKUID | MSkuID |
| 调整 | 上架日期 | 商品首单日期 |

Excel 左侧的编号、模型名称、旧模型表名和新模型表名分别纵向合并，覆盖这六行；右侧六条变化保持独立单元格。读者沿一行就能看到旧、新字段，又能沿分组识别所属模型。

## 典型失败：拆清了内容，却拆散了阅读关系

第一次方案把资料拆成“模型总览”“六组字段明细”“数据源对照”“维护方式”，并交付 Markdown。逐字段拆行本身有帮助，但读者要在多个位置重新关联中文模型、旧表、新表和字段变化，增加了查阅负担。

用户反馈：“首先，你整理的我更加看不懂了。然后，我依然还是需要excel的方式。重新给我一份excel”。

| 失败动作 | 为什么不适合本任务 | 后续修正 |
|---|---|---|
| 总览、字段明细、表名对照分开 | 将同一核对动作所需的信息分散，要求读者自行拼接 | 对象与其字段变化放在同一张表、同一个分组 |
| 把文档章节清晰当成阅读清晰 | 作者完成了分类，读者仍无法一次看完一个模型的变化 | 用“找到一个模型后能否立即逐行核对”检验结构 |
| 先给 Markdown 文档 | 没有形成用户期望的 Excel 表格工作面；用户随后明确了交付形式 | 使用 F04 生成实际 xlsx 并查看整表效果 |
| 附加变更计数、维护说明等内容 | 对本次逐字段核对帮助有限，增加阅读入口 | 让主要信息在主表中直接可见 |

失败点在这次任务的结构选择和交付载体，不是“Markdown 一定难读”或“概览＋明细永远不可用”。不要将本案例泛化成所有汇报只能一个 sheet。

## 成功：同表保留模型整体，组内展开字段变化

最终 Excel 只有一张工作表，六个模型依次分组，八列含义稳定。模型共享信息纵向合并，字段变化逐条拆行，旧、新字段相邻，必要的状态和核对说明放在备注。

- 原表六个模型展开为 28 行：23 条字段调整、4 条下线、1 条“已适配但未列字段明细”的状态记录。
- 两个模型里重复出现的“账号 → 账号名称”分别去重；原始输入保留重复项，方便追溯。
- “已适配”没有被解释成“零字段变更”；该模型的变更类型写“未列明”，具体字段留空，备注保留已适配状态。
- 金蝶直连 SQL 与“报表数据源尚未切换”的条件保留在同一模型分组。
- 使用现有 F04 引擎生成，保存后检查 224 个业务单元格及原生样式，整张预览复核通过。Excel 和预览按原文件归档。

用户最终明确反馈：“尤其是输入前和输入后的字段结构的变化设计。很棒。这个就很清楚”，并要求连同失败方案作为 Skill 案例留下。

## 次要教训：颜色不能代替业务证据

成功 Excel 中“三级分类 → 商品/物料四级分类”的新字段曾被 AI 标红，仅依据层级名称不同，备注写“按原文保留；分类层级映射待核对”。之后已向用户说明：没有查询数据或得到业务证据，不能认定映射错误；不同分类体系完全可能正常对应。普通的名称疑问不自动构成红色重点。

案例成品保留当时的红字以忠实记录实际交付。结构获得用户认可，不表示这处红字被验证为业务异常；复用时应重新判断证据与强调必要性。

## 复用边界与验收问题

当读者要核对同一对象的多条前后变化，可考虑“对象分组＋变化拆行＋旧新并列”。制作前后检查：

1. 一行现在代表什么？对象层信息和变化层信息是否已分清？
2. 原来长单元格里的每类信息是否都有稳定列位，是否遗漏状态或条件？
3. 读者找到一个对象后，能否不跳到其他区域就核对每条变化？
4. 纵向合并是否只覆盖真实共享的信息，是否会妨碍本次编辑任务？
5. 用户需要筛选、排序或持续录入时，是否应改为每行重复对象信息并取消正文合并？
6. 字段名、模型数量、映射关系和未确认项是否完整保留？是否因名称差异擅自改动了业务事实？

不固定六个模型、八列、28 行、具体表名、列宽或红字数量。其他任务按自己的对象、信息角色和阅读动作重新设计。
