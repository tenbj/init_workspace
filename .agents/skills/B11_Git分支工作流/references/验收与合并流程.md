# 验收与合并流程

## 动作与授权

| 用户意图 | 执行范围 |
|---|---|
| 修改、修复、增加功能 | 定位、工作分支、实现、必要检查；已有授权包含提交/推送时一并执行 |
| 提交一版、commit | 创建本地提交；不自动推送、合并、发版 |
| 推送、push | 推送已确认分支和目标远端；不自动合并、发版 |
| 验收通过、确认无误、OK | 确认验收状态；只有上下文已明确这些答复授权合并时才合并 |
| 可以合并、合并到明确目标 | 执行该目标的合并；关联远端操作按既有授权处理 |
| 发布、打标签、创建Release | 按用户明确的发布对象、版本和仓库流程执行；目标不清时先澄清 |
| 清理分支 | 确认分支已安全合并且不被任务使用，再按明确范围清理 |

用户已经给出的明确授权持续有效，不因阶段变化再次索取同一批准。单纯查看或改写本技能，不等于为未来所有任务预先授予推送、合并或发布权限。

## 提交与推送

1. 提交前检查暂存内容、忽略规则、敏感信息和本次验证证据；只纳入任务相关文件。
2. 保留用户已有暂存边界；不得用 `git add .` 把不相关内容带入提交，也不得自动 amend 既有提交。
3. 提交前读取目标工作区 `.agents/rules/version-control-rules.md` 的“Git 提交描述语言”规则；本骨架的标题、正文与合并说明必须中文，类型、作用域和代码标识可以保留原文。迁入其他仓库时遵循用户和目标仓库的明确约定；无语言约定时默认中文。
4. 推送先确定目标远端与分支：优先用户指明，其次当前分支已配置 upstream。首次推送且只有一个可用远端时可据此设置 upstream；多远端有歧义时询问。
5. 不自动更改远端 URL、Git 身份或凭据，不强推。遇到远端更新，用 fetch 检查差异，按授权合并或 rebase，不覆盖远端历史。
6. 只有提交及推送都成功，才称为“远端分支就绪”；否则分别说明本地提交和远端状态。

## 验收

- 验收人默认为当前用户，或由用户指定；不硬编码姓名、账户或组织角色。
- 提供可复查的文件、分支/提交、检查结果与必要的操作步骤；没有 UI 改动时不强行要求浏览器验收。
- 尚未收到验收结果时说明“待用户验收”；用户提出修改则在同任务分支继续处理。
- “没问题”“OK”等不独立构成推送、合并或发布指令；结合用户已明确接受的流程判断。

## 合并和收尾

1. 确认目标仓库、基线分支、源分支及用户授权，检查源分支检查状态和目标最新状态。
2. 优先采用仓库现有 PR/MR 流程、分支保护与合并策略；merge、squash、rebase 按仓库约定，不统一强制某一种。
3. PR/MR 不可用时，仅在用户授权允许直接合并且分支保护允许时使用本地 fallback；不可用的工具不等于绕过保护的授权。
4. 合并前按同一语言规则检查 merge / squash 的标题和正文，显式提供中文说明，避免采用 Git 默认英文消息。执行不会丢失工作的 fetch/切换/合并，冲突时保留双方意图并做对应验证；不使用 reset/clean 处理冲突。
5. 如获授权推送合并结果，推送成功后核验目标提交；不将本地合并说成远端已合并。
6. 普通合并不自动创建标签、Release、部署或删分支；这些动作各按已有明确授权与平台约定执行。
7. 若清理 worktree，使用宿主提供的管理工具并确认无其他任务依赖；若清理分支，先验证其工作已经保留。
