# 仓库定位与分支规则

## 输入与定位

输入是用户请求、目标文件或目录、所需动作，以及用户已给出的仓库/分支约定。

1. 以目标路径为起点，用 `scripts/inspect_repo.py --target <path>` 读取 Git 状态。目标尚不存在时，从最近的已存在父目录探测。
2. `git rev-parse --show-toplevel` 是仓库边界的依据；根目录、子仓库、子模块和 worktree 都通过 Git 识别，不要求 `.git` 一定是目录。
3. 不因目录名是 `.agents`、`output`、`docs` 就假定它不在 Git 中。任何文件都按实际仓库边界判断。
4. 多个目标属于不同仓库时，分别读规则、建分支、验证和提交；一个仓库的授权不自动覆盖其他仓库。
5. 无仓库时，明确说明该路径不需要 Git 分支，继续可做的文件任务。只有用户要求初始化 Git 才执行 `git init`。
6. Git 不可用、所有权或权限校验失败时报告原因，不把访问失败误报成“无仓库”，不自动更改全局安全配置。

辅助脚本只读取本地状态，不联网、不修改仓库、不读取或输出远端 URL/凭据。远端默认分支候选来自已有本地 symbolic ref，可能过期，不作为远端实时状态保证。

## 基线与工作分支

- 优先使用用户指定的目标基线和仓库规则；其次查询选定远端的默认分支。不要盲选 main 或 master。
- `main`、`master`、已确认默认分支、发布分支及仓库规则指定的受保护分支，都不能作为新实现的工作分支。
- main 上禁止直接提交；“可以”“继续”“发布合并”以及旧任务中的历史修复授权，都不构成绕过禁令的理由。执行提交保护参考 `提交保护.md`。
- 新分支遵循仓库命名规范；没有规范时用 `codex/<type>-<topic>-YYYYMMDD-HHmm`，type 为 fix、feature、chore 或 docs，topic 使用短横线短语。
- 先用 `git check-ref-format --branch <name>` 检查名称，用 `git switch -c <name>` 创建；重名时选择新名称或核实已有分支，不用 `-C` 重置分支。
- 已在同一任务的工作分支时复用；不因名称不够贴切而随意另开分支。
- detached HEAD 下需要写入时，从已确认的提交建工作分支；不丢弃该提交。空仓库先确认用户希望使用的分支，再创建首个提交。
- 若需从不同基线开始且当前有未提交内容，优先隔离工作；不要为切换分支自动 stash 或丢弃用户修改。
- 只读评审不要求切分支。仅提交现有修改而发现当前在受保护分支时，可从当前 HEAD 新建分支承接修改；不自动挪动已有主分支提交。

## 脏工作区和提交范围

- 开始前检查 `git status --short`、`git diff`、`git diff --cached`，记录已有修改与暂存边界。
- 无关修改保留原位；同文件混有他人修改时，按 diff hunk 选择本次内容，不用整文件暂存掩盖范围。
- 提交前核对最终暂存区；用户已有暂存内容不自动纳入本次提交，也不擅自清空。
- 不能安全区分改动归属或切分支会覆盖内容时，说明具体冲突并索取必要信息。
- 使用参数化调用，路径放在 `--` 之后；不将用户输入拼成可执行 shell 片段。
