# 发送流程

## 已授权输入

必须有收件人、正文和稳定业务请求 ID。C19 提供已核对 MR 链接和正式/测试模式；独立消息按用户本轮指定对象。不能因“测试”就向任何联系人试发，也不能把用户“可以发给测试联系人”理解成同时给正式联系人发。

消息附精确标注 `（codex自动发送）`，已含标注不重复添加。保留用户正文及换行。正式代码通知格式为 `帮合并代码：{真实MR链接}（codex自动发送）`。本技能不负责猜测或创建 MR。

## 复用现有环境

使用已知可执行路径或 PATH 中的 `dws`。官方 Skill 的存在不等于程序已安装。profile 应从已保存本地环境说明或 `dws profile list --format json` 的实际返回选择；多账号使用准确的 `corpId:userId`，不能按第一个或最近登录猜选。优先复用调用方已验证身份，正常情况下不运行安装、授权或全套网络排障。

来源案例曾验证特定组织身份，本项目必须重新核对实际账号。默认组织可来自用户已确认设置，但不把组织名当稳定 ID、不把好友关系当成示例组织B组织通讯录权限。联系人 ID 必须在当前发信账号下查询，不能跨账号复用。

## 查询、发送与回执

1. `dws contact user search --query <姓名> --profile <已验证身份> --format json`。唯一匹配并核对姓名/nick；多人同名时由用户提供部门或其他识别信息，再通过 CLI 补充核实。无法识别时不发送。目标为发信人本人也按真实 CLI 结果处理，不编造特殊 self ID。
2. 发送前记录 prepared 回执、正文摘要、收件人 ID 与固定幂等键。默认使用本技能脚本；脚本预检会联网查询联系人，但不发送。只有本次请求已获授权时加 `--execute`，不再额外要求重复批准。
3. 官方命令实际版本已验证：`chat message send --open-dingtalk-id <返回ID> --content <正文> --idempotency-key <固定键> --profile <身份> --format json`。使用子进程参数数组，正文含引号/换行也不拼 shell。
4. 从真实返回取 `openTaskId`，随后 `chat message query-send-status --open-task-id <返回任务> --profile <同一身份> --format json`。只认可 `success=true` 且 `sendStatus=SUCCESS` 为发送成功。
5. 单次查询仍 processing/pending 时有界重查，结束后保存 pending；后续调用同一回执只查状态。失败保留错误，未知保留 unknown，不向用户谎报成功。

所有 dws 命令包括诊断应带 `--format json`。`doctor` 额外需要 `--json` 才能稳定取得结构化输出；只有出现异常才运行。

## 防重与恢复

- 业务请求 ID 代表一条通知：代码发布用项目+MR+提交SHA+通知类型，同一恢复不更换 ID；真正新的发布或用户明确新测试才使用新 ID。
- 脚本以 profile、请求 ID 和正文锁定同一通知，并持久化发信前状态；并发同一回执有排他锁。
- 成功回执可直接复用；有任务 ID 只查询，绝不调用 send。
- 发送进程超时/EOF/断电且没有任务 ID，不知道服务端是否已接收；标记 unknown，保留同一幂等键，先通过 CLI 核查已有消息/审计或找回任务。不得换键重发。当前 CLI 相同幂等键防重有 24 小时边界，过期不能依赖它保证不重复。
- 两个不同回执路径可能代表同一业务请求，应由调用方固定回执位置；不能为了绕过成功/未知状态创建另一份回执。
- 结果只证明发送状态，不证明已读。若任务需要已读，须另有用户需求并查询真实消息 ID。
