# ODS 表粒度与主键核验流程

## 1. 先限定核验对象

独立ODS任务只核验用户指定ODS，不把DWD背景当作扩展范围的授权。由C17明确传入非ODS模型时，可将本方法和唯一性模板用于该指定实体，报告真实层级、实际写入表及来源；不混写成ODS结论，也不擅自扩大到上下游。

必须先明确：

- 表全名
- 是否为 Doris 表
- 是否需要读取源端同步脚本
- 用户是否已经说明特殊字段语义，例如采集时间、源端更新时间、数仓同步时间

## 2. 建业务解读，再建字段组合

不要先堆字段映射。先回答“这张表是什么场景下产生的数据”：

- 来源系统：例如领星、Amazon、ERP、采集任务等
- 业务对象：例如广告否定投放对象、订单明细、库存快照等
- 业务动作：创建、更新、删除、采集、同步、快照
- 表内主要类型枚举：对象类型、匹配方式、状态字段等

业务解读完成后，再把字段分成三类：

| 字段类型 | 判断方式 | 常见例子 |
|---|---|---|
| 业务识别字段 | 用来区分业务对象是谁 | 店铺、账号、活动、广告组、对象类型、对象内容、源端创建时间 |
| 排序/版本字段 | 用来判断哪条记录更新 | 源端更新时间、采集任务更新时间 |
| 技术/审计字段 | 用来保证落表唯一或记录同步过程 | `id`、`task_id`、`etl_dt`、`first_inserted_dt`、`last_updated_dt` |

## 3. 粒度字段组合的表达规则

粒度必须先用中文表达，再给技术字段：

```text
字段1中文 + 字段2中文 + 字段3中文 + ...
```

再写：

```text
field_1 + field_2 + field_3 + ...
```

如果某个字段是推导字段，必须解释来源。例如广告投放层级不能只写占位符，应拆成：

- `ad_scope_level`：投放作用层级，活动级 / 广告组级
- `ad_group_id_norm`：标准化广告组 ID，活动级为空，广告组级取原始广告组 ID

SQL 里的 `COALESCE(field, '<NULL>')` 只是空值参与拼接的校验写法，不是业务字段名，也不是源端真实值。

## 4. 业务主键判定规则

业务主键不是“看起来能解释业务的字段组合”，而是必须满足：

```sql
COUNT(*) = COUNT(DISTINCT 粒度字段组合)
```

结论规则：

| 核验结果 | 业务主键结论 |
|---|---|
| 原始表上二者相等 | 数据唯一性成立；还须有业务识别语义及范围/空值证据，才能确认业务主键 |
| 原始 ODS 上二者不等 | 当前候选不成立，继续探查其他业务字段 |
| 取最新后二者相等 | 只能说明可得到当前态唯一记录，不改变原始 ODS 业务主键结论 |

先在一个完整批次内探索：读取重复组全部业务字段，区分遗漏识别维度、缺失值、报表位置/排名、源端事件/版本等业务因素，提出可解释的新组合再测。不能把补充合理业务维度一概称为“凑唯一”。仅当完整业务行相同仍重复，或对全部可用业务识别信息已有充分排除证据，才能在该批给出“现有业务字段无法唯一识别”的结论，并据此否定全表业务键。仅“可能重复采集”不是证据。

若首批找到唯一业务组合，固定该组合检查下一批，依次直到全量；若某批失败，重新探查该批。扩展/修订组合后须回验之前批次。所有批次须用同一最终组合，不能用各批不同组合冒充全局业务键。保留候选演进、中文业务解释、各批结果和反例；完整业务行重复时提供至少两行的逐字段对照，可直接证明任何业务字段子集均不能唯一，无需继续盲目枚举字段组合。

### 4.1 最小性核验：找到唯一组合还不算结束

最终业务键须是能完整识别业务对象、在核验范围原始数据上唯一且没有冗余字段的组合。这里的“最小”指不可再删除字段；可能存在多组不同的最小键，不等同于已经证明在所有组合中字段数最少。不得仅凭一次逐字段剔除就宣称全局最少字段数。

1. 对已全范围唯一的候选K，依次查询去掉一个字段后的K−{f}，使用相同原始数据范围与NULL口径，不能缩小日期或忽略空值。
2. 剩余组合全范围仍唯一且能完整表达业务身份时，删掉该冗余字段，以缩减后的组合继续。最后对最终组合再次全范围验证，并复核各字段的必要性。
3. 删除后出现重复，保存实际SQL、范围、重复组数及至少一组反例，证明该字段在当前完整范围内不能删除。已出现真实重复即可否定该缩减组合；要证明缩减后唯一则必须覆盖全部范围。
4. 删除后当前数据碰巧仍唯一，但来源规则表明字段是业务身份必要部分（例如编码仅在组织内唯一），须提供明确来源约束并分别记录“当前数据唯一”和“业务身份必要”。不能凭猜测保留冗余字段，也不能把这一情况称为纯数据意义的最小候选键。
5. 大表分批时，对每个缩减组合重新检查分批安全性：若删除了分批字段，同一个缩减键可能跨批，必须重新分桶或补跨批核验。各批内唯一不等于缩减组合全局唯一。
6. 名称、审计字段、随机技术ID等仍按真实业务含义判断；不能靠属性差异凑出唯一后再以“删不掉”为由认定业务键。若多组最小键都成立，分别列证据，优先选来源清楚、稳定且便于业务解释的一组。

报告须列出：最终字段、每次剔除结果、保留/删除理由、SQL/反例路径、核验范围和最终全量结果。最小性未测只能写“唯一候选，最小性待核验”，不能结束为已确认业务键；执行失败继续分批补完。历史监控不会因规则更新自动变成“最小性已验证”，既有保存/运行事实保留，是否重跑按任务范围处理。

## 5. 技术唯一主键判定规则

### 原始值唯一与业务身份分开

字段角色取决于真实含义，不只由名称决定：人工记录编号可以是业务键，随机生成的unique_key不能替代业务键。名称仅因TAB、空格或不可见字符而区分两行时，保留原值、长度/字符差异及源映射，继续核实业务作用；全表计数唯一不证明这些字符代表不同业务实体。

去TAB、TRIM等规范化只能在明确标注的诊断分支使用；“规范化后重复”不等于“原始全部业务字段完全相同”。不擅自清洗生产数据或改变正式监控表达式。未确认组合仍是候选，不提前写已确认或无业务键。

全字段GROUP BY用于探查完整业务重复时，应提供直接单表反例并排除JOIN放大；不能直接当作正式业务唯一性配置。最终按已确认键套用输出契约模板，明确区分诊断SQL和监控SQL。

### 大表执行失败必须继续分批核验

全表聚合超时或触发内存保护属于执行问题，不能直接将模型标成不适配，也不能将失败的空返回当无重复。先检查必要业务键，保留原始候选和变更依据，再按业务日期/分区顺序拆批，过大批次继续按键内字段细分，不同时堆积多个重查询。

每批保存实际SQL、边界、时间、行数、组合数、重复组/额外行、空键及错误。批次必须互斥且覆盖原范围（含NULL分组），同一候选键所有记录必须落在同一批；分割字段不在键内时不能直接相加宣称全局唯一，必须补跨批重复核验。失败批次细分续跑，成功批次可恢复，不用采样代替全量。覆盖结束后与原范围总量核对；记录核验期间数据变化，必要时重验变化区间。

确认业务键需要完整覆盖证据；发现真实重复只否定该候选，并继续按上述步骤探查，不能用局部重复数冒充全表统计。正式监控仍按固定模板仅返回重复组数quality_value；允许补充有业务依据且实测的字段，不用随机值、行号或无业务识别意义的审计字段制造唯一，也不擅自缩小监控范围。

技术唯一主键必须同时看 DDL 和数据：

- DDL 中的 `UNIQUE KEY(...)`、主键或唯一模型定义
- `COUNT(*)`
- `COUNT(DISTINCT 技术主键字段组合)`
- 技术主键字段空值数

只有当 `COUNT(*) = COUNT(DISTINCT 技术主键字段组合)` 且关键字段无异常空值时，才能确认技术唯一主键成立。

## 6. 重复原因归属

不要单独把“重复为什么出现”放成一个孤立大章。它必须归入下列章节之一：

- 业务粒度章节：用于解释为什么某字段必须进入粒度，例如源端创建时间
- 业务主键章节：用于解释为什么粒度字段组合在原始 ODS 上仍不唯一
- 技术主键章节：仅当技术主键也重复或为空时才进入

重复分析至少说明：

- 重复组数量、重复行数、额外行数
- 组内技术主键是否不同
- 组内采集任务字段是否相同
- 组内采集更新时间是否相同
- 组内源端创建/更新时间是否相同
- 是否像重复采集、源端多版本、业务真实多次创建或技术脏数据

## 7. 取最新边界

取最新只在用户确认“某字段是采集任务更新时间或版本排序字段”后使用。常见排序：

```text
PARTITION BY 粒度字段组合
ORDER BY 采集任务更新时间 DESC, 源端更新时间 DESC, 技术主键 DESC
```

取最新结论必须写成：

```text
按粒度字段组合取最新后，可以得到当前态唯一记录。
```

不能写成：

```text
取最新后的业务主键成立。
```
