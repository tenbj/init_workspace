# 报告口径规范

## 1. 结论总览必须短

结论总览独立放在最前面，只保留最核心信息。推荐 4 行：

| 核验项 | 明确结论 |
|---|---|
| 业务粒度 | 字段1中文 + 字段2中文 + ... |
| 粒度字段组合 | `field_1 + field_2 + ...` |
| 业务主键 | 已确认组合 / 候选待核实 / 有充分反例证明现有业务字段无法唯一识别；附计数或反例，证据不足不得简写“无” |
| 技术唯一主键 | `id` 或其他技术字段组合，并给出 `COUNT(*)` 与 `COUNT(DISTINCT ...)` |

不要在总览里展开长篇字段映射、重复样例、DWD 建议。

## 2. 必须有业务解读

业务解读要回答：

- 这张表在什么业务场景下产生
- 一条业务记录应该被业务人员如何理解
- 表中关键类型字段分别代表什么
- 哪些字段只是采集、同步或审计字段

只有业务解读清楚后，字段组合才不会像凭空拼出来。

## 3. 章节顺序

推荐结构：

```text
结论总览
业务解读
1. 业务理解上的粒度
  1.1 原始表粒度
  1.2 业务对象粒度
2. 业务主键
  2.1 明确结论
  2.2 重复或争议字段说明
3. 技术唯一主键
4. 唯一性检验 SQL 配置（固定输出，未生成时写明原因）
5. 下游使用建议（仅用户需要时写）
```

“重复为什么出现”不要作为孤立大章；它应放在 1、2、3 的相关章节下面。

## 4. 字段组合表达

字段组合必须补中文释义，并按用户可读方式表达：

```text
店铺 + Amazon广告账户 + SP广告活动 + 投放作用层级（活动级 / 广告组级） + ...
```

对应技术字段：

```text
sid + profile_id + campaign_id + ad_scope_level + ...
```

如果技术字段来自推导，要解释：

- 推导字段叫什么
- 由哪个源字段推导
- 空值或层级如何处理
- SQL 占位符是不是业务概念

## 5. 主键措辞红线

禁止把以下概念混写：

| 概念 | 正确含义 |
|---|---|
| 业务粒度 | 一条业务记录在业务上表示什么 |
| 粒度字段组合 | 用于表达该业务粒度的一组字段 |
| 业务主键 | 具备明确业务识别语义，并在声明的原始表完整范围内实测唯一、核实空值的字段组合 |
| 技术唯一主键 | Doris / 数据库用于物理唯一的字段组合 |
| 当前态取最新键 | 对重复采集记录做窗口取最新的分组字段，不等于原始 ODS 业务主键 |

如果仅当前候选组合不唯一，结论写：

```text
当前候选不成立，业务键继续探查；不能据此判定没有业务键。
```

只有重复组全部业务字段仍相同、证明现有业务字段的任何组合都无法唯一识别等充分证据，才写“现有业务字段无法形成业务主键”，并展示实际批次和完整重复明细。首批找到唯一候选后，必须固定组合逐批覆盖全量才可写“已确认业务键”。

如果取最新后唯一，结论写：

```text
按粒度字段组合取最新后，可以得到当前态唯一记录。
```

## 6. 时间字段判断

时间字段必须按语义拆开：

| 字段类型 | 是否进入粒度 | 用法 |
|---|---|---|
| 源端创建时间 | 可能进入 | 区分同位置同内容的多次真实创建 |
| 源端更新时间 | 通常不进入 | 判断源端新旧，可用于取最新排序 |
| 采集任务更新时间 | 不进入 | 重复采集时取最新 |
| 数仓同步时间 | 不进入 | 只做同步审计 |

用户明确说明某字段语义时，以用户说明为准，并重新评估业务主键。

## 7. 输出语气

结论要硬，解释要短。尤其是总览，先给答案，再给证据；不要让用户在长段落里捞结论。

## 8. 唯一性配置章节

按[输出契约](输出契约.md)写出确认的业务键、检查范围、独立SQL链接、完整SQL和执行状态。SQL来自固定资产模板，保留dc中的 `COUNT(*) AS cnt`，最终仅输出重复组数 `quality_value`。主键未确认时保留本章，注明未生成原因，不把技术唯一键当作业务键。
