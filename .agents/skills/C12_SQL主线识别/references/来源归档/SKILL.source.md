# SQL主线识别

## 这项技能解决什么问题

从实际SQL中识别“先做什么、再做什么”的加工主线。固定交付主线注释SQL和Markdown，先写主线，再写两列表格：第一列主线节点，第二列代码动作。

## 先读哪些本地知识

- 先读用户指定SQL的完整内容，以代码为依据，不以名称或旧说明代替。
- 首次识别读 `references/主线识别规则.md`；生成文件读 `references/输出契约.md`。
- 本工作区落盘前遵守 B04、B02，收尾按 B03；仅引用稳定编号。

## 固定动作

1. 从最终查询沿FROM/JOIN/CTE/子查询依赖逆向找源头，划分多语句及分支范围。
2. 判断每段实际加工动作，把服务同一目的的辅助步骤归入主干，顺向核对先后。
3. 形成主线和“主线节点｜代码动作”表；各节点记录原SQL行号与原文依据，不硬套固定节点数。
4. 按输出契约填写识别结果JSON；脚本不替模型做语义识别。
5. 调用 `scripts/render_mainline.py` 输出独立SQL与MD；检查源文件散列、两列顺序、主线一致性与两个文件实际存在。
6. 最终回复给一句主线和两个文件链接，不自动扩展字段说明、案例分析或重构。

## 什么时候再读本 skill 的 references

- 遇到多语句、分支合并、窗口或关联角色不明确：读 `references/主线识别规则.md`。
- 需要JSON结构、命令、命名、失败处理：读 `references/输出契约.md`。
- 需要一个最小模板：使用 `assets/analysis.example.json`。
- 检查能力包结构：读 `references/结构融合索引.md`。

## 边界

- 只识别主线，不自动改SQL逻辑、执行数据库查询或创建视图。
- SQL输出是原文前附新增--注释，不是另造一份业务实现；原文件保持不变。
- 不把每个CTE机械当作主线节点；不把“扩行”和“汇总”混淆。
- 不声称逻辑依赖就是数据库物理执行计划；不确定处在动作中说明待核实。
- 原SQL中的提示/原有注释原样保留，避免破坏语义；新增说明只用--。
- 用户另有明确要求时以用户要求为准，不把本技能扩成完整代码评审流程。
