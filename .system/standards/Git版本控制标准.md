# Git版本控制标准

本文件是工作区Git任务流程与提交命名的唯一事实源。规则和Skill只引用执行，不复制标准正文。

## 独立任务流程

每个独立改动任务必须在专用分支完成：新建分支 → 实现与验证 → 提交 → 合并到明确目标基线。同一任务内的连续调整复用分支；不同任务分开提交、验收与合并。已有未提交改动按任务分离，禁止混入无关内容。
用户确认采用此流程后，常规本地提交和合并属于该任务授权；优先仓库既有目标基线，本工作区为main。目标无法确定或验证失败时保留分支并报告。用户明确要求不提交、暂不合并等例外优先。推送、发布和删除分支仍需对应授权，不自动扩展。

## 提交命名

### 适用与引用

本节统一管理普通提交、合并提交和发布准备消息。所有涉及 Git 提交的 Skill 在生成消息和提交前读取本标准；Skill 只保留执行时机与标准引用，不另设类型、语言、范围或描述规则。用户和目标仓库的明确约定优先；无明确例外时执行本标准。不自动 amend、rebase 或强推改写既有历史。

### 标题格式

- 普通提交可用 `类型: 中文描述` 或 `类型(范围): 中文描述`，两种均合规。
- 范围可选，用于指明主要模块；能帮助定位时填写，不为满足格式强行添加。范围可使用 `workflow`、`skills`、`sql` 等实际模块标识。
- 使用半角冒号，冒号后留一个空格。标题和正文用中文描述，类型、代码标识、路径和版本号可保留原文。
- 合并提交使用 `merge: 中文合并概括`，显式覆盖 Git 或平台默认英文消息；概括本次合并的事项，发布合并可带版本号。
- 发布准备提交使用 `chore(release): 发布X.Y.Z`。仅整理文档或发布说明时按文档改动归为 `docs`，不因与发布有关就一律归为发布准备。
- squash 标题按最终改动使用普通提交格式；合并策略与保留分类提交要求仍按已确认任务流程执行。
- 作者姓名等由 Git 元数据记录，不作为标题格式的一部分。

### 类型选择

| 类型 | 用途 |
|---|---|
| `feat` | 新增功能或能力 |
| `fix` | 修复缺陷、异常或错误行为 |
| `ui` | 界面、布局、交互呈现或适配调整 |
| `docs` | 文档、说明和变更记录 |
| `refactor` | 不改变预期外部行为的代码结构调整 |
| `test` | 测试用例、测试工具或验证覆盖调整 |
| `chore` | 构建、依赖、维护及发布准备 |
| `merge` | 合并提交的内容概括 |

按本次改动的主要目的选择类型；UI 缺陷修复可用 `fix`，侧重呈现或体验调整可用 `ui`。扩展类型需有用户或目标仓库的明确约定。

### 描述与拆分要求

- 写清“改了什么对象、做了什么、得到什么结果”，按事项需要表达，不机械堆齐所有要素。优先使用“新增、修复、调整、移除、同步”等具体动作。
- 标题应脱离聊天上下文仍能理解，避免只有“更新、优化、修复问题、修改代码”等空泛描述。
- 必要时用正文补充触发问题、修改原因、实现约束和验证结果；简单提交不强制添加正文。
- 按独立事项拆分提交，保持单条提交目的清晰且可验证；不把无关功能、修复与文档混成一条，也不把同一完整改动机械拆成逐文件提交。
- 合并说明概括所合并的工作；用户要求保留分类提交时保留各条记录，不用一条模糊消息替代。

### 合格示例

```text
fix: 将本餐分装完成移至今天分装并保留整餐扣次确认
ui: 今天分装改为逐人菜品克重列表并适配手机
docs: 整理逐项更新记录并准备 v0.2.0 发布
fix(workflow): 强制禁止main直接提交并启用分支保护
feat(skills): 整合技能更新并同步编号与依赖
chore(release): 发布2.23.0
merge: 合并main直接提交强制保护
merge: 发布 v0.2.0 商家备餐与分装更新
```

### 提交前核对

核对消息与实际差异一致、类型准确、范围按需、中文说明具体、事项边界清晰；合并或发布时核对对应格式。B09、B11、C19 等 Skill 执行此检查，脚本生成或用户传入的候选消息也要核对。现有分支保护钩子不校验消息内容，不能把分支保护通过视为消息检查通过。
